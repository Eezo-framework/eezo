# The shape of an application in the JavaScript frameworks

This document surveys where the JavaScript frameworks that render in code, with no separate template layer, put the four things a small shop needs beyond its routes: the page frame (the root layout), shared page pieces (a component used by several routes that is neither a route nor a layout), small formatters (money and time), and the logic behind a route (data access and the operation a form submission triggers). For each of Next.js (App Router), Remix and React Router framework mode, SvelteKit, Nuxt, the Redux style guide and the React documentation itself, it answers the same five questions: where the root layout lives and whether the framework reads its location; where a shared component goes and whether the framework reads that folder; where formatters live and what the folder is called; where the docs put data access and the form operation; and whether a component that holds state is kept apart, by folder or by name, from one that only renders data. A closing comparison sets the answers against the first survey of eight server frameworks, [The shape of an application in the frameworks eezo is modeled on](app-shape-in-other-frameworks.md): where the two groups agree, where they differ, and what each calls the pieces. Every claim links to a primary source: the frameworks' official documentation, the create scripts' templates on GitHub, and official examples (the Next.js Learn dashboard course, Next.js Commerce, the Stripe samples for Next.js, the React Router templates and tutorial, the `sv create` and `nuxi` templates, the Redux Essentials tutorial); where a claim could not be verified it is flagged in place and collected at the end. The survey was done on 2026-10-02 against the versions current on that date. It makes no recommendation for eezo.

### The page frame

The root layout is a file in a place the framework reads. The reference says: "The `app` directory **must** include a **root layout**, which is the top-most layout in the root `app` directory. Typically, the root layout is `app/layout.js`." and "The root layout **must** define `<html>` and `<body>` tags." ([layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)). The getting started page says the same from the other side: "The layout above is called a root layout because it's defined at the root of the `app` directory. The root layout is **required** and must contain `html` and `body` tags." ([Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages)).

A layout is a React component, but it only counts as a layout when it is the default export of a file named `layout` in a route segment folder: "You can define a layout by default exporting a React component from a `layout` file. The component should accept a `children` prop which can be a page or another layout." ([Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages)). The routing files table lists `layout`, `page`, `loading`, `not-found`, `error`, `global-error`, `route`, `template` and `default` with the extensions `.js` `.jsx` `.tsx` as the only names the router reads ([Project structure and organization](https://nextjs.org/docs/app/getting-started/project-structure)). Nothing on these pages describes registering a layout function from application code; the location is the registration.

The one freedom the application has is where the root lives inside `app`. "You can create **multiple root layouts**. Any layout without a `layout.js` above it is a root layout", either through route groups such as `app/(shop)/layout.js` and `app/(marketing)/layout.js`, or by "Omitting `app/layout.js` so layouts in subdirectories like `app/dashboard/layout.js` and `app/blog/layout.js` each become root layouts for their respective directories." The root layout can also sit under a dynamic segment, `app/[lang]/layout.js` ([layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)). The whole tree can move under `src/`: "To use the `src` folder, move the `app` Router folder or `pages` Router folder to `src/app` or `src/pages` respectively", with the caveat that "`src/app` or `src/pages` will be ignored if `app` or `pages` are present in the root directory." ([src Folder](https://nextjs.org/docs/app/api-reference/file-conventions/src-folder)).

Every official starter follows this. The `app` and `app-tw` templates of create-next-app generate `app/layout.tsx`, `app/page.tsx`, `app/globals.css` and `public/` ([templates/app/ts/app](https://github.com/vercel/next.js/tree/canary/packages/create-next-app/templates/app/ts/app)). The generated layout is:

```tsx
// packages/create-next-app/templates/app/ts/app/layout.tsx
export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en" className={`${geistSans.variable} ${geistMono.variable}`}>
      <body>{children}</body>
    </html>
  );
}
```

([layout.tsx, app template](https://github.com/vercel/next.js/blob/canary/packages/create-next-app/templates/app/ts/app/layout.tsx)). When the `src/` option is chosen, the installer moves exactly `SRC_DIR_NAMES = ["app", "pages", "styles"]` into `src` and rewrites the import alias to `"@/*": ["./src/*"]` ([templates/index.ts](https://github.com/vercel/next.js/blob/canary/packages/create-next-app/templates/index.ts)). The dashboard course starter has `app/layout.tsx` with the same `html` and `body` shape ([starter-example/app/layout.tsx](https://github.com/vercel/next-learn/blob/main/dashboard/starter-example/app/layout.tsx)), and vercel/commerce has an `async` root layout at `app/layout.tsx` that starts a cart fetch and wraps `children` in a `CartProvider` ([commerce app/layout.tsx](https://github.com/vercel/commerce/blob/main/app/layout.tsx)).

### Shared page pieces

The documentation declines to pick a folder. "Next.js is **unopinionated** about how you organize and colocate your project files. But it does provide several features to help you organize your project." The examples section adds: "In our examples below, we're using `components` and `lib` folders as generalized placeholders, their naming has no special framework significance and your projects might use other folders like `ui`, `utils`, `hooks`, `styles`, etc." ([Project structure and organization](https://nextjs.org/docs/app/getting-started/project-structure)). So no shared component folder is read by the framework; the only names the router reads are the routing files above.

Three placement strategies are offered, each as a diagram with one sentence. "Store project files outside of `app`": "This strategy stores all application code in shared folders in the **root of your project** and keeps the `app` directory purely for routing purposes." "Store project files in top-level folders inside of `app`": "This strategy stores all application code in shared folders in the **root of the `app` directory**." "Split project files by feature or route": "This strategy stores globally shared application code in the root `app` directory and **splits** more specific application code into the route segments that use them." The page closes the choice with "The simplest takeaway is to choose a strategy that works for you and your team and be consistent across the project." ([Project structure and organization](https://nextjs.org/docs/app/getting-started/project-structure)).

Colocation inside `app` is safe because only two file names make a URL: "a route is **not publicly accessible** until a `page.js` or `route.js` file is added to a route segment" and "only the **content returned** by `page.js` or `route.js` is sent to the client. This means that **project files** can be **safely colocated** inside route segments in the `app` directory without accidentally being routable." Private folders exist on top of that: "Private folders can be created by prefixing a folder with an underscore: `_folderName`. This indicates the folder is a private implementation detail and should not be considered by the routing system, thereby **opting the folder and all its subfolders** out of routing." They are optional ("private folders are not required for colocation") and serve for "Separating UI logic from routing logic" and "Avoiding potential naming conflicts with future Next.js file conventions"; the examples are `app/blog/_components/Post.tsx` ("Not routable; safe place for UI utilities") and `app/blog/_lib/data.ts`. Route groups are the other device: "Route groups can be created by wrapping a folder in parenthesis: `(folderName)`. This indicates the folder is for organizational purposes and should **not be included** in the route's URL path." ([Project structure and organization](https://nextjs.org/docs/app/getting-started/project-structure)). The `src` page notes that shared folders follow the router: "If you're using `src`, you'll probably also move other application folders such as `/components` or `/lib`." ([src Folder](https://nextjs.org/docs/app/api-reference/file-conventions/src-folder)).

The starters each pick one strategy. create-next-app generates no `components/` or `lib/` folder at all; the templates hold `app/`, `public/` and config files ([templates/app/ts](https://github.com/vercel/next.js/tree/canary/packages/create-next-app/templates/app/ts)). The Learn course uses the second strategy, shared folders inside `app`: "`/app/ui`: Contains all the UI components for your application, such as cards, tables, and forms" and "`/app/lib`: Contains functions used in your application, such as reusable utility functions and data fetching functions." ([Getting Started, Learn](https://nextjs.org/learn/dashboard-app/getting-started)). The course calls this colocation: "Next.js allows you to colocate UI components, test files, and other related code with your routes. Only the content inside the `page` file will be publicly accessible. For example, the `/ui` and `/lib` folders are _colocated_ inside the `/app` folder along with your routes." ([Creating Layouts and Pages, Learn](https://nextjs.org/learn/dashboard-app/creating-layouts-and-pages)). The `app/ui` tree is split by route name, not by component kind: `app/ui/dashboard/{cards,latest-invoices,nav-links,revenue-chart,sidenav}.tsx`, `app/ui/invoices/{breadcrumbs,buttons,create-form,edit-form,pagination,status,table}.tsx`, plus `app/ui/button.tsx`, `app/ui/search.tsx`, `app/ui/skeletons.tsx`, `app/ui/global.css` ([starter-example/app/ui](https://github.com/vercel/next-learn/tree/main/dashboard/starter-example/app/ui)). vercel/commerce uses the first strategy, root folders beside `app`: `app/`, `components/`, `lib/`, `fonts/`, with `components/cart/`, `components/grid/`, `components/layout/`, `components/product/` and leaf files like `components/price.tsx` ([vercel/commerce](https://github.com/vercel/commerce)). The Stripe example in vercel/next.js puts `components/` and `actions/` inside `app` and `lib/`, `utils/`, `config/` at the root ([examples/with-stripe-typescript](https://github.com/vercel/next.js/tree/canary/examples/with-stripe-typescript)).

### Small formatters

The Learn course keeps formatters in `app/lib/utils.ts`, next to `app/lib/data.ts`, `app/lib/definitions.ts` and `app/lib/placeholder-data.ts`:

```ts
// dashboard/starter-example/app/lib/utils.ts
export const formatCurrency = (amount: number) => {
  return (amount / 100).toLocaleString('en-US', {
    style: 'currency',
    currency: 'USD',
  });
};

export const formatDateToLocal = (
  dateStr: string,
  locale: string = 'en-US',
) => {
  const date = new Date(dateStr);
  const options: Intl.DateTimeFormatOptions = {
    day: 'numeric',
    month: 'short',
    year: 'numeric',
  };
  const formatter = new Intl.DateTimeFormat(locale, options);
  return formatter.format(date);
};
```

([starter-example/app/lib/utils.ts](https://github.com/vercel/next-learn/blob/main/dashboard/starter-example/app/lib/utils.ts)). The same file holds `generateYAxis` and `generatePagination`. Both formatters are consumed from two directions: `app/lib/data.ts` imports `formatCurrency` from `./utils` and applies it inside `fetchLatestInvoices` (`amount: formatCurrency(invoice.amount)`) ([starter-example/app/lib/data.ts](https://github.com/vercel/next-learn/blob/main/dashboard/starter-example/app/lib/data.ts)), and the invoices table component imports `{ formatDateToLocal, formatCurrency } from '@/app/lib/utils'` and calls both in its JSX ([starter-example/app/ui/invoices/table.tsx](https://github.com/vercel/next-learn/blob/main/dashboard/starter-example/app/ui/invoices/table.tsx)).

vercel/commerce has no money formatter function in `lib/utils.ts`; that file holds `baseUrl`, `createUrl`, `ensureStartsWith` and `validateEnvironmentVariables` ([commerce lib/utils.ts](https://github.com/vercel/commerce/blob/main/lib/utils.ts)). Money formatting is a component:

```tsx
// components/price.tsx
const Price = ({ amount, className, currencyCode = "USD", currencyCodeClassName }: {...}) => (
  <p suppressHydrationWarning={true} className={className}>
    {`${new Intl.NumberFormat(undefined, {
      style: "currency",
      currency: currencyCode,
      currencyDisplay: "narrowSymbol",
    }).format(parseFloat(amount))}`}
    <span className={clsx("ml-1 inline", currencyCodeClassName)}>{`${currencyCode}`}</span>
  </p>
);
```

([commerce components/price.tsx](https://github.com/vercel/commerce/blob/main/components/price.tsx)). `lib/constants.ts` holds sort options, cache `TAGS` and the Shopify endpoint ([commerce lib/constants.ts](https://github.com/vercel/commerce/blob/main/lib/constants.ts)).

The Stripe example in vercel/next.js uses a root `utils/` folder:

```ts
// examples/with-stripe-typescript/utils/stripe-helpers.ts
export function formatAmountForDisplay(amount: number, currency: string): string {
  let numberFormat = new Intl.NumberFormat(["en-US"], {
    style: "currency",
    currency: currency,
    currencyDisplay: "symbol",
  });
  return numberFormat.format(amount);
}

export function formatAmountForStripe(amount: number, currency: string): number {
  let numberFormat = new Intl.NumberFormat(["en-US"], { style: "currency", currency: currency, currencyDisplay: "symbol" });
  const parts = numberFormat.formatToParts(amount);
  let zeroDecimalCurrency: boolean = true;
  for (let part of parts) {
    if (part.type === "decimal") {
      zeroDecimalCurrency = false;
    }
  }
  return zeroDecimalCurrency ? amount : Math.round(amount * 100);
}
```

([with-stripe-typescript utils/stripe-helpers.ts](https://github.com/vercel/next.js/blob/canary/examples/with-stripe-typescript/utils/stripe-helpers.ts)). The archived stripe-samples repository has the identical file at the same path, described in its README as "Format amount strings properly using `Intl.NumberFormat`" ([stripe-samples README](https://github.com/stripe-samples/nextjs-typescript-react-stripe-js/blob/master/README.md)). `config/index.ts` holds `CURRENCY`, `MIN_AMOUNT`, `MAX_AMOUNT`, `AMOUNT_STEP` ([with-stripe-typescript config/index.ts](https://github.com/vercel/next.js/blob/canary/examples/with-stripe-typescript/config/index.ts)). None of these folders (`lib`, `utils`, `config`, `ui`) is read by the framework; the documentation calls `lib` a placeholder with "no special framework significance" ([Project structure and organization](https://nextjs.org/docs/app/getting-started/project-structure)).

### The logic behind a route

Reads happen in Server Components. "You can fetch data in Server Components using any asynchronous I/O, such as: The `fetch` API, An ORM or database", and "Since Server Components are rendered on the server, credentials and query logic will not be included in the client bundle so you can safely make database queries using an ORM or database client." The examples put the query inline in `app/blog/page.tsx` (`await db.select().from(posts)`), but also show a module `app/lib/user.ts` exporting `getUser = cache(async (id) => db.query.users.findFirst(...))` that `app/dashboard/page.tsx` imports ([Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data)). The layout reference likewise shows `app/lib/data.ts` with `getUser` imported by both `app/dashboard/layout.tsx` and `app/dashboard/page.tsx` ([layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)).

The security guide turns this into a recommendation. "There are three main approaches we recommend for fetching data in Next.js": "HTTP APIs: for existing large applications and organizations", "Data Access Layer: for new projects", "Component-Level Data Access: for prototypes and learning". "For new projects, we recommend creating a dedicated **Data Access Layer (DAL)**. This is an internal library that controls how and when data is fetched, and what gets passed to your render context." A DAL should "Only run on the server", "Perform authorization checks", "Return safe, minimal **Data Transfer Objects (DTOs)**". The examples live in a root `data/` folder: `data/auth.ts`, `data/user-dto.tsx` with `import 'server-only'`, `data/user.ts`, `data/posts.ts`, imported from `app/page.tsx` as `'../../data/user-dto'` or `'../data/user'` ([How to think about data security in Next.js](https://nextjs.org/docs/app/guides/data-security)). The guide does not say the folder must be called `data`; the `server-only` section uses `lib/data.ts` for the same idea.

Writes are Server Functions. "A Server Function can be defined by using the `use server` directive. You can place the directive at the top of an **asynchronous** function to mark the function as a Server Function, or at the top of a separate file to mark all exports of that file." The inline form sits inside a page: "Server Functions can be inlined in Server Components by adding the `"use server"` directive to the top of the function body" (example in `app/page.tsx`). Client components cannot define them: "It's not possible to define Server Functions in Client Components. However, you can invoke them in Client Components by importing them from a file that has the `"use server"` directive at the top of it", shown as `app/actions.ts` imported by `app/ui/button.tsx`. The file examples alternate between `app/lib/actions.ts` and `app/actions.ts`; the page never prescribes one ([Mutating Data](https://nextjs.org/docs/app/getting-started/mutating-data)). The directive reference uses `app/actions.ts` and an inline `updatePost` inside `app/posts/[id]/page.tsx` ([use server](https://nextjs.org/docs/app/api-reference/directives/use-server)). The security guide extends the DAL to writes: "This keeps authentication, authorization, and database logic in a dedicated `server-only` module, while `"use server"` actions stay thin", with `data/posts.ts` doing the work and `app/actions.ts` calling it then `revalidatePath('/posts')` ([How to think about data security in Next.js](https://nextjs.org/docs/app/guides/data-security)).

The Learn course picks the separate file and says why: "Navigate to your `lib/` directory and create a new file named `actions.ts`. At the top of this file, add the React `use server` directive", and "You can also write Server Actions directly inside Server Components by adding `"use server"` inside the action. But for this course, we'll keep them all organized in a separate file. We recommend having a separate file for your actions." ([Mutating Data, Learn](https://nextjs.org/learn/dashboard-app/mutating-data)). For reads it says: "You can call `sql` anywhere on the server, like a Server Component. But to allow you to navigate the components more easily, we've kept all the data queries in the `data.ts` file, and you can import them into the components." ([Fetching Data, Learn](https://nextjs.org/learn/dashboard-app/fetching-data)). The final example's `app/lib/actions.ts` starts with `'use server'`, creates its own `postgres` client, defines a `zod` `FormSchema`, and exports `createInvoice`, `updateInvoice`, `deleteInvoice` and `authenticate`, each ending in `revalidatePath('/dashboard/invoices')` and `redirect('/dashboard/invoices')` ([final-example/app/lib/actions.ts](https://github.com/vercel/next-learn/blob/main/dashboard/final-example/app/lib/actions.ts)). The form in `app/ui/invoices/create-form.tsx` imports `createInvoice` from `@/app/lib/actions` and binds it with `useActionState` ([final-example/app/ui/invoices/create-form.tsx](https://github.com/vercel/next-learn/blob/main/dashboard/final-example/app/ui/invoices/create-form.tsx)).

vercel/commerce splits differently: the Shopify client, queries and mutations are a library at `lib/shopify/{index.ts,queries/,mutations/,fragments/,types.ts}`, and the server actions sit beside the components that call them, in `components/cart/actions.ts`, which opens with `"use server"`, imports `addToCart`, `getCart`, `removeFromCart` and friends from `lib/shopify`, and exports `addItem`, `removeItem`, `updateItemQuantity`, `redirectToCheckout`, `createCartAndSetCookie`, calling `updateTag(TAGS.cart)` after each change ([commerce components/cart/actions.ts](https://github.com/vercel/commerce/blob/main/components/cart/actions.ts)). The Stripe example has `app/actions/stripe.ts` with `"use server"`, exporting `createCheckoutSession(data: FormData)` and `createPaymentIntent(data: FormData)`, which import the Stripe client from `lib/stripe.ts` (a file that begins `import "server-only"`) and `formatAmountForStripe` from `utils/stripe-helpers` ([with-stripe-typescript app/actions/stripe.ts](https://github.com/vercel/next.js/blob/canary/examples/with-stripe-typescript/app/actions/stripe.ts), [lib/stripe.ts](https://github.com/vercel/next.js/blob/canary/examples/with-stripe-typescript/lib/stripe.ts)); webhooks are a route handler at `app/api/webhooks/route.ts`. The stripe-samples checkout-one-time-payments repository does have a Next.js server at `server/nextjs/`, but it uses route handlers, not server actions: `app/api/create-checkout-session/route.ts` exports `POST`, reads `formData`, creates the session and returns `NextResponse.redirect(session.url!, 303)` ([checkout-one-time-payments server/nextjs](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/nextjs)). The Stripe Checkout quickstart offers a Next.js variant: "Add a Route Handler in your application that creates a Checkout Session", with the order preview "at `app/page.jsx`" and a `lib/stripe.ts` beginning `import 'server-only'` ([Build a Stripe-hosted checkout page](https://docs.stripe.com/checkout/quickstart?client=next)).

### Interactive versus plain

The distinction is a directive, not a folder or a name. "By default, layouts and pages are Server Components", and "You can create a Client Component by adding the `"use client"` directive at the top of the file, above your imports." Client components are for "State and event handlers. E.g. `onClick`, `onChange`", "Lifecycle logic. E.g. `useEffect`", "Browser-only APIs", "Custom hooks" ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). The directive page adds: "You only need to add it to the files whose components you want to render directly within Server Components." ([use client](https://nextjs.org/docs/app/api-reference/directives/use-client)). The placement advice is about tree depth, not file location: "add `'use client'` to specific interactive components instead of marking large parts of your UI as Client Components" ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). The example paths mix both kinds in one place: `app/ui/like-button.tsx`, `app/ui/search.tsx` and `app/ui/modal.tsx` carry `'use client'` while `app/ui/cart` is a server component passed as a child, and `app/components/counter.tsx` sits next to a server `app/header` ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components), [use client](https://nextjs.org/docs/app/api-reference/directives/use-client)). No page fetched proposes a `client/` folder or a naming suffix.

The official examples confirm the single folder. In the Learn final example, `app/ui/` holds six files with `'use client'` (`search.tsx`, `login-form.tsx`, `dashboard/nav-links.tsx`, `invoices/create-form.tsx`, `invoices/edit-form.tsx`, `invoices/pagination.tsx`) beside fourteen without, including `invoices/table.tsx`, which is `async` and calls `fetchFilteredInvoices` ([final-example/app/ui](https://github.com/vercel/next-learn/tree/main/dashboard/final-example/app/ui)). The course glosses the directive in place, saying the file "is a Client Component, which means you can use event listeners and hooks", and contrasts the siblings: "`<Search>` is a Client Component, so you used the `useSearchParams()` hook to access the params from the client. `<Table>` is a Server Component that fetches its own data, so you can pass the `searchParams` prop from the page to the component." ([Adding Search and Pagination, Learn](https://nextjs.org/learn/dashboard-app/adding-search-and-pagination)). In vercel/commerce, `components/cart/` holds `add-to-cart.tsx`, `cart-context.tsx`, `delete-item-button.tsx`, `edit-item-quantity-button.tsx` and `modal.tsx` with `"use client"`, beside `open-cart.tsx` and `actions.ts` without; `components/price.tsx` is a server component while `components/layout/navbar/search.tsx` is client ([commerce components](https://github.com/vercel/commerce/tree/main/components)). The client `cart-context.tsx` (`createContext`, `use`, `useOptimistic`) is imported by the server root layout and wrapped around `children` ([commerce components/cart/cart-context.tsx](https://github.com/vercel/commerce/blob/main/components/cart/cart-context.tsx)). In the Stripe example, `app/components/CheckoutForm.tsx` and `ElementsForm.tsx` are `"use client"` while `CustomDonationInput.tsx`, `PrintObject.tsx` and `StripeTestCards.tsx` have no directive, all in one folder ([with-stripe-typescript app/components](https://github.com/vercel/next.js/tree/canary/examples/with-stripe-typescript/app/components)).

## Remix and React Router framework mode

### The page frame

In framework mode the root layout is a file in a place the framework reads. The reference says: "The "root" route (`app/root.tsx`) is the only _required_ route in your React Router application because it is the parent to all routes and is in charge of rendering the root `<html>` document" ([root.tsx](https://reactrouter.com/api/framework-conventions/root.tsx)). The routing guide repeats that "Every route in `routes.ts` is nested inside the special `app/root.tsx` module" ([Routing](https://reactrouter.com/start/framework/routing)). The only knob on its location is the app directory as a whole: `appDirectory` is "The path to the `app` directory, relative to the root directory. Defaults to `"app"`" ([react-router.config.ts](https://reactrouter.com/api/framework-conventions/react-router.config.ts)). The special files list names `root.tsx` and `routes.ts` as required and `entry.client.tsx`, `entry.server.tsx` and `react-router.config.ts` as optional ([Special Files](https://reactrouter.com/explanation/special-files)).

The document shell is a named export of that file, not a free function: "The root route also supports an additional optional `Layout` export", which exists to "Avoid duplicating your document's "app shell" across your root component, `HydrateFallback`, and `ErrorBoundary`", and "`Layout` takes a single `children` prop, which is the `default` export (e.g. `App`), `HydrateFallback`, or `ErrorBoundary`" ([root.tsx](https://reactrouter.com/api/framework-conventions/root.tsx)). The default template's `app/root.tsx` exports exactly `links`, `Layout` (the `<html>` document with `<Meta />`, `<Links />`, `<ScrollRestoration />`, `<Scripts />`), `App` returning `<Outlet />`, and `ErrorBoundary` ([default/app/root.tsx](https://github.com/remix-run/react-router-templates/blob/main/default/app/root.tsx)). The Remix v2 template's `app/root.tsx` is the same shape with `@remix-run/react` imports ([templates/remix/app/root.tsx](https://github.com/remix-run/remix/blob/v2/templates/remix/app/root.tsx)), and the v2 docs describe the root route in the same words ("the only _required_ route in your Remix application") ([Remix v2 root](https://v2.remix.run/docs/file-conventions/root)).

Layouts below the root are ordinary route modules, and their location is chosen by the application. The `layout()` helper takes a file path: "layout routes create new nesting for their children, but they don't add any segments to the URL. It's like the root route but they can be added at any level" ([Routing](https://reactrouter.com/start/framework/routing)). The address book tutorial says so explicitly when it extracts the sidebar: "You can name and put this layout route wherever you want, but putting it inside of a `layouts` directory will help keep things organized for our simple app", then `mkdir app/layouts` and `touch app/layouts/sidebar.tsx`, registered as `layout("layouts/sidebar.tsx", [...])` ([Address Book](https://reactrouter.com/tutorials/address-book)). With the file system convention instead, a pathless layout is a file named with a leading underscore, so `_auth.login.tsx` nests under `_auth.tsx` ([File Route Conventions](https://reactrouter.com/how-to/file-route-conventions)). In both cases a layout is a module file with a default export, never a bare function passed to the framework.

### Shared page pieces

The documentation reads no `components/` folder. Framework mode reads `app/root.tsx`, `app/routes.ts`, and the files `routes.ts` points at ("Each route has two required parts: a URL pattern to match the URL, and a file path to the route module that defines its behavior") ([Routing](https://reactrouter.com/start/framework/routing)). Anything else under `app/` is plain code. The default template puts its one shared component beside the routes folder, not inside it:

```
default/app/
├── app.css
├── root.tsx
├── routes.ts
├── routes/
│   └── home.tsx
└── welcome/
    ├── logo-dark.svg
    ├── logo-light.svg
    └── welcome.tsx
```

`routes/home.tsx` does `import { Welcome } from "../welcome/welcome"` and renders `<Welcome />` ([default/app/routes/home.tsx](https://github.com/remix-run/react-router-templates/blob/main/default/app/routes/home.tsx)). The folder is named after the feature, not `components/`, and `routes.ts` contains only `[index("routes/home.tsx")]` ([default/app/routes.ts](https://github.com/remix-run/react-router-templates/blob/main/default/app/routes.ts)).

The `.client` and `.server` module pages draw illustrative trees that include a `components/` directory next to `root.tsx`, but say nothing about it; the text is about the suffixes ([.client modules](https://reactrouter.com/api/framework-conventions/client-modules), [.server modules](https://reactrouter.com/api/framework-conventions/server-modules)). The file system convention offers colocation inside the routes folder: "Routes can also be folders with a `route.tsx` file inside defining the route module. The rest of the files in the folder will not become routes. This allows you to organize your code closer to the routes that use them instead of repeating the feature names across other folders", with an example where `_landing/` holds `footer.tsx`, `header.tsx` and `route.tsx` ([File Route Conventions](https://reactrouter.com/how-to/file-route-conventions)). The Remix v2 version of that page adds a "Scaling" recommendation that the React Router page no longer carries: "Our general recommendation for scale is to make every route a folder and put the modules used exclusively by that route in the folder, then put the shared modules outside the `routes` folder elsewhere" ([Remix v2 Route File Naming](https://v2.remix.run/docs/file-conventions/routes)). "Elsewhere" is left to the application.

The official examples are habit, and the habit varies: `_official-jokes/app/components/joke.tsx`, `client-only-components/app/components/`, `leaflet/app/components/map.client.tsx`, `sanity/app/components/`, while `pm-app` names the folder `app/ui/` (`button.tsx`, `dialog.tsx`, `todo-list.tsx`) ([examples tree](https://github.com/remix-run/examples)). The address book tutorial creates no components folder at all; its `Favorite` star button is a plain function defined in `app/routes/contact.tsx` under the route component ([Address Book](https://reactrouter.com/tutorials/address-book)).

### Small formatters

No official starter or tutorial has a money or time formatter. The address book template's only non route module is `app/data.ts`, whose header reads "Nothing in here has anything to do with React Router, it's just a fake database", and it contains no formatting code ([tutorials/address-book/app/data.ts](https://github.com/remix-run/react-router/blob/main/tutorials/address-book/app/data.ts)). The default template has no helper module ([react-router-templates default](https://github.com/remix-run/react-router-templates/tree/main/default)). The closest thing to a money helper is the Stripe example, and it is a server utility rather than a formatter:

```ts
// stripe-integration/app/utils/stripe.server.tsx
export const getStripeSession = async (
  priceId: string,
  domainUrl: string,
): Promise<string> => {
  const stripe = initStripe(process.env.STRIPE_SECRET_KEY);
```

imported by `app/routes/buy.tsx` as `import { getStripeSession, getDomainUrl } from "~/utils/stripe.server"` ([stripe-integration](https://github.com/remix-run/examples/tree/main/stripe-integration)). Nothing in `utils/` or `lib/` is read by the framework; the only thing the build reads is the `.server` or `.client` suffix on a file or folder name: "`.server` modules are a good way to explicitly mark entire modules as server-only. The build will fail if any code in a `.server` file or `.server` directory accidentally ends up in the client module graph" ([.server modules](https://reactrouter.com/api/framework-conventions/server-modules)).

### The logic behind a route

Data access and the form operation are exports of the route module. "Route loaders provide data to route components before they are rendered. They are only called on the server when server rendering or during the build with pre-rendering", and "Route actions allow server-side data mutations with automatic revalidation of all loader data on the page when called from `<Form>`, `useFetcher`, and `useSubmit`" ([Route Module](https://reactrouter.com/start/framework/route-module)). "Note that the `loader` function is removed from client bundles so you can use server only APIs without worrying about them being included in the browser" ([Data Loading](https://reactrouter.com/start/framework/data-loading)), and "Route actions defined with `action` are only called on the server while actions defined with `clientAction` are run in the browser" ([Actions](https://reactrouter.com/start/framework/actions)).

The docs' own examples import the persistence call from a neighbouring module and keep the operation in the route: `import { fakeDb } from "../db"` followed by `const product = await fakeDb.getProduct(params.pid)` in the loader ([Data Loading](https://reactrouter.com/start/framework/data-loading)), and `let project = await fakeDb.updateProject({ title })` in the action ([Actions](https://reactrouter.com/start/framework/actions)). The address book tutorial has the same split: a single data module `app/data.ts` with "Handful of helper functions to be called from route loaders and actions" (`getContacts`, `getContact`, `createEmptyContact`, `updateContact`, `deleteContact`) ([data.ts](https://github.com/remix-run/react-router/blob/main/tutorials/address-book/app/data.ts)), and the operations in route files: `loader` in `app/routes/contact.tsx` calling `getContact(params.contactId)`; `loader` and `action` in `app/routes/edit-contact.tsx`, the action doing `Object.fromEntries(formData)`, `updateContact(...)` and `redirect(...)`; `action` in `app/routes/destroy-contact.tsx` calling `deleteContact`; the "New" button's `action` in `app/root.tsx` calling `createEmptyContact()`; and the list `loader` in `app/layouts/sidebar.tsx` calling `getContacts()` ([Address Book](https://reactrouter.com/tutorials/address-book)).

Remix v2 described this as "Remix's Fullstack Data Flow": "Route loaders provide data to the UI", "Forms post data to route actions that update persistent state", "Loader data on the page is automatically revalidated", with `loader`, the component and `action` in one module calling `getUser` and `updateUser` ([Remix v2 Data Flow](https://v2.remix.run/docs/discussion/data-flow)). Its data loading guide used `import { db } from "~/db.server"` and said "Since Remix runs on your server, you can connect directly to a database in your route modules" ([Remix v2 Data Loading](https://v2.remix.run/docs/guides/data-loading)). On stores, the v2 docs say "most Remix applications forgo them entirely" and warn that when React state holds anything network related (loader data, pending submissions, navigation state) "it's likely that you're managing state that Remix already manages", pointing instead at URL search params, cookies, server sessions and server caches ([Remix v2 State Management](https://v2.remix.run/docs/discussion/state-management)). The examples place the data layer in various spots: the blog tutorial uses `app/db.server.ts` plus `app/models/post.server.ts` (`getPosts`, `getPost`, `createPost` over Prisma), the jokes app uses `app/utils/db.server.ts`, and the Stripe example performs the payment in the `action` of `app/routes/buy.tsx` ([examples](https://github.com/remix-run/examples)).

### Interactive versus plain

In the stable framework mode there is one word, component, and no folder or name split between a stateful component and a rendering one. The route module page calls the default export "the component that will render when the route matches" ([Route Module](https://reactrouter.com/start/framework/route-module)); the tutorial's `Favorite` component, which owns a `useFetcher()` and answers a click, sits in the same file as the data only `Contact` component in `app/routes/contact.tsx` ([Address Book](https://reactrouter.com/tutorials/address-book)); the default template's `Welcome`, which only renders, sits in `app/welcome/welcome.tsx` ([default template](https://github.com/remix-run/react-router-templates/tree/main/default/app)). The only naming convention is the bundle boundary, not interactivity: "You can use `*.client.ts` on file names or nest files within `.client` directories to force them out of server bundles", and such values "will all be `undefined` on the server, so the only places to use them are in `useEffect` and user events like click handlers" ([.client modules](https://reactrouter.com/api/framework-conventions/client-modules)). The examples use it for components that cannot render on the server (`leaflet/app/components/map.client.tsx`, `react-quill/app/components/textEditor.client.tsx`), while an ordinary stateful component such as `client-only-components/app/components/complex-component.tsx` (with `useState` and `useEffect`) has no suffix ([examples](https://github.com/remix-run/examples)).

The split appears only in the experimental RSC mode: "React Server Components support is experimental and subject to breaking changes in minor/patch releases", and "If you need to use client-only features (e.g. Hooks, event handlers) within React elements returned from loaders/actions, you'll need to extract components using these features into a client module" marked `"use client"`; the example is a `counter.tsx` beside the route's `route.tsx`, imported as `./counter` ([React Server Components](https://reactrouter.com/how-to/react-server-components)). The RSC template in react-router-templates mirrors the default tree (`app/root.tsx`, `app/routes.ts`, `app/routes/home.tsx`, `app/welcome/welcome.tsx`) with no separate client folder ([unstable_rsc-framework-mode](https://github.com/remix-run/react-router-templates/tree/main/unstable_rsc-framework-mode)).

### The page frame

The root layout is a file in a place the framework reads: "To create a layout that applies to every page, make a file called `src/routes/+layout.svelte`." If the app does not provide one, SvelteKit uses a default that is just `let { children } = $props();` followed by `{@render children()}`; "The only requirement is that the component includes a `@render` tag for the page content" ([Routing](https://svelte.dev/docs/kit/routing)). The routes directory itself is the one configurable knob: "You can change `src/routes` to a different directory by editing the project config" ([Routing](https://svelte.dev/docs/kit/routing)), through `files.routes`, whose default is `"src/routes"`; the whole `files` block is marked `@deprecated this feature is still supported, but it's generally recommended to use monorepos instead` ([KitConfig in packages/kit/types/index.d.ts](https://github.com/sveltejs/kit/blob/main/packages/kit/types/index.d.ts), rendered at [Configuration](https://svelte.dev/docs/kit/configuration)). Inside the routes directory the name `+layout.svelte` is fixed; the `+` prefix is what marks a route file ([Routing](https://svelte.dev/docs/kit/routing)).

A layout cannot be a plain function. A Svelte component is a file: "Components are the building blocks of Svelte applications. They are written into `.svelte` files, using a superset of HTML" ([.svelte files](https://svelte.dev/docs/svelte/svelte-files)). The layout is therefore a `.svelte` component, discovered by name. The docs do not describe importing a layout component into a page as the layout mechanism; what they do describe is composition inside a layout file: the advanced routing page shows `src/routes/nested/route/+layout@.svelte` importing `ReusableLayout from '#lib/ReusableLayout.svelte'` and says "It's perfectly fine to use other means such as composition (reusable `load` functions or Svelte components) or if-statements to achieve what you want" ([Advanced routing](https://svelte.dev/docs/kit/advanced-routing)). The hierarchy can be reshaped without moving files: directories "wrapped in parentheses" such as `(app)` and `(marketing)` "do not affect the URL pathname of the routes inside them" and each may hold its own `+layout.svelte`; a page can escape with `+page@(app).svelte`, `+page@item.svelte` or `+page@.svelte` (root), and "a `+layout@.svelte` component would reset the hierarchy for all its child routes" ([Advanced routing](https://svelte.dev/docs/kit/advanced-routing)). The tutorial puts the shared nav in `src/routes/+layout.svelte` and states "A `+layout.svelte` file applies to every child route, including the sibling `+page.svelte` (if it exists). You can nest layouts to arbitrary depth" ([Tutorial: Layouts](https://svelte.dev/tutorial/kit/layouts)).

The demo template follows this: `src/routes/+layout.svelte` imports `Header from './Header.svelte'` and `'./layout.css'`, renders `<Header />`, `<main>{@render children()}</main>` and a footer; the minimal template's `+layout.svelte` only sets a favicon in `<svelte:head>` and renders `children` ([demo/src/routes/+layout.svelte](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/%2Blayout.svelte), [minimal/src/routes/+layout.svelte](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/minimal/src/routes/%2Blayout.svelte)).

### Shared page pieces

The docs name two homes and give a rule for choosing. Colocation first: "Any other files inside a route directory are ignored by SvelteKit. This means you can colocate components and utility modules with the routes that need them." Then: "If components and modules are needed by multiple routes, it's a good idea to put them in `#lib`" ([Routing, Other files](https://svelte.dev/docs/kit/routing)). The project structure page says the same from the other side: "`lib` contains your library code (utilities and components), which can be imported via the `#lib` alias, or packaged up for distribution using `svelte-package`", and "`routes` contains the routes of your application. You can also colocate other components that are only used within a single route here" ([Project structure](https://svelte.dev/docs/kit/project-structure)). The tutorial phrases the rule as "A good rule of thumb is 'put code close to where it's used'" and introduces `src/lib` for code "used in multiple places" ([Tutorial: The #lib subpath import](https://svelte.dev/tutorial/kit/lib)). There is no `components/` folder in any of the documentation trees.

Whether the framework reads `src/lib` changed between major versions. In SvelteKit 2, "SvelteKit automatically makes files under `src/lib` available using the `$lib` import alias" ([$lib at @sveltejs/kit@2.70.3](https://github.com/sveltejs/kit/blob/%40sveltejs%2Fkit%402.70.3/documentation/docs/98-reference/26-%24lib.md)) and `files.lib` was a config option ([options.js at @sveltejs/kit@2.70.3](https://github.com/sveltejs/kit/blob/%40sveltejs%2Fkit%402.70.3/packages/kit/src/core/config/options.js)). In SvelteKit 3 the alias is no longer the framework's: "Previously, this alias was `$lib` and was automatically configured by SvelteKit. It is now `#lib` and must be declared in your `package.json` `imports` field" ([#lib](https://svelte.dev/docs/kit/$lib)). The `sv` CLI writes `"imports": { "#lib": "./src/lib/index.js", "#lib/*": "./src/lib/*" }` into `package.json`, "leveraging Node's built-in subpath imports feature" ([#lib](https://svelte.dev/docs/kit/$lib)); `files.lib` is now `removed(e.config_option_removed_files_lib)` in [options.js](https://github.com/sveltejs/kit/blob/main/packages/kit/src/core/config/options.js), with the message "SvelteKit no longer generates a `$lib` alias" ([messages/build-errors/config.md](https://github.com/sveltejs/kit/blob/main/packages/kit/messages/build-errors/config.md)). The `kit.alias` option is "deprecated. Use subpath imports instead" ([Configuration](https://svelte.dev/docs/kit/configuration)). So in Kit 3 `src/lib` is a convention plus a `package.json` entry, with one framework-read exception: "directories named `server`, at any depth, mark any code within as server only. SvelteKit will prevent you from importing these in client code" ([Project structure](https://svelte.dev/docs/kit/project-structure)).

The starters practise colocation inside `src/routes` rather than a components folder. The demo template:

```

├ lib/images/            github.svg, svelte-logo.svg, svelte-welcome.png
└ routes/
  ├ +layout.svelte       imports ./Header.svelte and ./layout.css
  ├ +page.svelte         imports ./Counter.svelte
  ├ +page.ts
  ├ Counter.svelte
  ├ Header.svelte        imports #lib/images/*.svg
  ├ layout.css
  ├ about/+page.svelte, about/+page.ts
  └ sverdle/
    ├ +page.server.ts
    ├ +page.svelte
    ├ game.ts
    ├ words.server.ts
    └ how-to-play/+page.svelte, how-to-play/+page.ts
```

([sveltejs/cli, packages/sv/src/create/templates/demo](https://github.com/sveltejs/cli/tree/main/packages/sv/src/create/templates/demo)). `Header.svelte` is used by the layout alone and sits beside it; `src/lib` holds only images. The minimal template has `src/lib/index.ts` containing the single comment "place files you want to import through the `#lib` alias in this folder." and `src/lib/assets/favicon.svg` ([minimal/src/lib/index.ts](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/minimal/src/lib/index.ts)). The realworld app mixes both: `src/lib/ArticleList/index.svelte`, `src/lib/ArticleList/ArticlePreview.svelte` and `src/lib/ListErrors.svelte` are shared; `src/routes/Nav.svelte`, `Pagination.svelte`, `PreloadingIndicator.svelte` sit at the routes root, and `src/routes/article/[slug]/` holds `ArticleMeta.svelte`, `Comment.svelte`, `CommentContainer.svelte`, `CommentInput.svelte` next to the page that uses them ([sveltejs/realworld tree](https://github.com/sveltejs/realworld/tree/master/src)).

No official starter or example has a money or time formatter module. The demo template contains no `Intl`, `format` or `toLocale` call at all (grep over `packages/sv/src/create/templates`). The realworld app formats a date inline in the component markup, twice, with no helper:

```svelte
<!-- src/lib/ArticleList/ArticlePreview.svelte and src/routes/article/[slug]/ArticleMeta.svelte -->
<span class="date">{new Date(article.createdAt).toDateString()}</span>
```

([ArticlePreview.svelte](https://github.com/sveltejs/realworld/blob/master/src/lib/ArticleList/ArticlePreview.svelte), [ArticleMeta.svelte](https://github.com/sveltejs/realworld/blob/master/src/routes/article/%5Bslug%5D/ArticleMeta.svelte)). The nearest thing to a helpers module in realworld is `src/lib/constants.js` (`export const page_size = 10;` and a placeholder image URL) and `src/lib/api.js` (a `send` wrapper plus `get`, `del`, `post`, `put`) ([constants.js](https://github.com/sveltejs/realworld/blob/master/src/lib/constants.js), [api.js](https://github.com/sveltejs/realworld/blob/master/src/lib/api.js)). Nothing in `lib` is read by the framework except `server` directories, as above. The server-only page's own example of a colocated utility is `src/routes/utils.js` with `export const add = (a, b) => a + b;`, used to show that re-exporting a `#lib/server` secret from it makes the whole chain illegal ([Server-only modules](https://svelte.dev/docs/kit/server-only-modules)).

### The logic behind a route

Data access and mutations both live in the route file, specifically in `+page.server.js`, and the data layer they call is placed under `src/lib/server`. Loading: "A `+page.svelte` file can have a sibling `+page.js` that exports a `load` function, the return value of which is available to the page via the `data` prop." If the function "uses private environment variables, for example, or accesses a database" then "it would go in a `+page.server.js` instead" ([Loading data](https://svelte.dev/docs/kit/load)). Universal `load` runs "both on the server and in the browser"; server `load` runs "only server-side"; "Server `load` functions are convenient when you need to access data directly from a database or filesystem, or need to use private environment variables" ([Loading data](https://svelte.dev/docs/kit/load)). Every database example on that page is `import * as db from '#lib/server/database.js';` in `src/routes/blog/[slug]/+page.server.js`, `src/routes/blog/[slug]/+layout.server.js` or `src/routes/+layout.server.js`, calling `db.getPost`, `db.getPostSummaries`, `db.getUser` ([Loading data](https://svelte.dev/docs/kit/load)).

Mutations: "A `+page.server.js` file can export _actions_, which allow you to `POST` data to the server using the `<form>` element." The simplest form is a `default` action in `src/routes/login/+page.server.js`; named actions such as `login` and `register` are invoked with `action="?/register"`. The anatomy example imports `* as db from '#lib/server/db.js'` and does `const user = await db.getUser(email); cookies.set('sessionid', await db.createSession(user));` inside the action ([Form actions](https://svelte.dev/docs/kit/form-actions)). Progressive enhancement is `import { enhance } from '$app/forms'` plus `use:enhance` on the form ([Form actions](https://svelte.dev/docs/kit/form-actions)). The page also notes that "new development is focused on remote functions, which are intended to become the recommended way to communicate with the server", while "Form actions are feature-complete and will continue to work" ([Form actions](https://svelte.dev/docs/kit/form-actions)).

The tutorial uses exactly this split. "We've already got an in-memory database set up in `src/lib/server/database.js`, and our `load` function in `src/routes/+page.server.js` uses the `cookies` API"; the action is `default: async ({ cookies, request }) => { const data = await request.formData(); db.createTodo(cookies.get('userid'), data.get('description')); }` ([Tutorial: The form element](https://svelte.dev/tutorial/kit/the-form-element)). `database.js` exports `getTodos`, `createTodo`, `deleteTodo` over a `Map` ([database.js source](https://github.com/sveltejs/svelte.dev/blob/main/apps/svelte.dev/content/tutorial/03-sveltekit/06-forms/01-the-form-element/%2Bassets/app-a/src/lib/server/database.js)). The next chapter replaces `default` with `create` and `delete` and warns "Default actions cannot coexist with named actions" ([Tutorial: Named form actions](https://svelte.dev/tutorial/kit/named-form-actions)). The page data chapter instead colocates the data with the route, `import { posts } from './data.js'` in `src/routes/blog/+page.server.js`, with the note "For the sake of the tutorial, we're importing data from `src/routes/blog/data.js`. In a real app, you'd be more likely to load the data from a database or a CMS" ([Tutorial: Page data](https://svelte.dev/tutorial/kit/page-data)).

The demo template keeps the game logic colocated with the route and the secret part server-only: `src/routes/sverdle/+page.server.ts` has `load` building `new Game(cookies.get('sverdle'))` and actions `update`, `enter` (`if (!game.enter(guess)) return fail(400, { badGuess: true });`) and `restart`; `game.ts` is the `Game` class; `words.server.ts` holds the word lists, imported only by `game.ts` ([sverdle/+page.server.ts](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/sverdle/%2Bpage.server.ts), [game.ts](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/sverdle/game.ts)). The realworld app puts the API client in `src/lib/api.js` and each operation in the route: `src/routes/login/+page.server.js` has a `default` action calling `api.post('users/login', ...)` and setting a `jwt` cookie; `src/routes/editor/+page.server.js` posts `articles`; `src/hooks.server.js` decodes the cookie into `event.locals.user`; the one shared loader helper, `get_articles`, is colocated at `src/routes/profile/@[user]/get_articles.js` ([login/+page.server.js](https://github.com/sveltejs/realworld/blob/master/src/routes/login/%2Bpage.server.js), [hooks.server.js](https://github.com/sveltejs/realworld/blob/master/src/hooks.server.js)).

Stores are not where the docs put this logic. The state management page says "it's important not to store data in shared variables" on the server and "Instead, you should _authenticate_ the user using `cookies` and persist the data to a database.", that `load` functions "should be _pure_", that app state on the server uses "Svelte's context API", that URL search parameters are "a good place" for "filters or sorting rules on a table", and that disposable UI state goes in snapshots ([State management](https://svelte.dev/docs/kit/state-management)).

### Interactive versus plain

One folder, one word, one file type. Both a stateful component and a display-only one are `.svelte` files; the docs call all of them components and never split them by folder or name. The demo's `Counter.svelte` holds `const count = new Spring(0)` and a `$derived` value, and sits in `src/routes/` beside `Header.svelte`, which only reads `page.url.pathname` to mark the current link ([Counter.svelte](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/Counter.svelte), [Header.svelte](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/Header.svelte)). In realworld, `ArticlePreview.svelte` carries an optimistic `use:enhance` handler that mutates `article.favorited` and lives in `src/lib/ArticleList/` next to the plain list wrapper `index.svelte` ([ArticlePreview.svelte](https://github.com/sveltejs/realworld/blob/master/src/lib/ArticleList/ArticlePreview.svelte)). The only naming distinctions the framework reads are about where code runs, not about interactivity: the `+` prefix for route files, the `.server.js` suffix or a `server` directory for server-only modules ([Server-only modules](https://svelte.dev/docs/kit/server-only-modules)), and `+server.js` for endpoints, since "All files run on the client except `+server` files" ([Routing](https://svelte.dev/docs/kit/routing)). Whether a page ships JavaScript is a page option (`export const csr = dev;` in the demo's `how-to-play/+page.ts`), not a folder ([how-to-play/+page.ts](https://github.com/sveltejs/cli/blob/main/packages/sv/src/create/templates/demo/src/routes/sverdle/how-to-play/%2Bpage.ts)).

### The page frame

The root of the page is a file in a known place: `app/app.vue`. "The app.vue file is the main component of your Nuxt application" and "Nuxt will treat this file as the **entrypoint** and render its content for every route of the application" ([app.vue](https://nuxt.com/docs/4.x/directory-structure/app/app), [Views](https://nuxt.com/docs/4.x/getting-started/views)). The file is optional once an `app/pages/` directory exists: "Nuxt will automatically include a default `app.vue`, but you can still add your own to customize the structure and content as needed" ([app.vue](https://nuxt.com/docs/4.x/directory-structure/app/app)). Routing is wired by placing `<NuxtPage />` in it, and shared chrome can be written straight into it: the docs show a `<header>`, `<NuxtPage />`, `<footer>` template under the label `app/app.vue` ([app.vue](https://nuxt.com/docs/4.x/directory-structure/app/app)).

Named layouts are a second layer of files, also in a known place. "Layouts are wrappers around pages that contain a common User Interface for several pages, such as header and footer displays", they render the page through `<slot />`, and "`app/layouts/default.vue` file will be used by default" ([Views](https://nuxt.com/docs/4.x/getting-started/views)). They are switched on in the entrypoint: "Layouts are enabled by adding `<NuxtLayout>` to your `app.vue`", then a page picks one with `definePageMeta({ layout: 'custom' })`, or at runtime with `setPageLayout('panel', ...)`, or opts out with `layout: false` and places its own `<NuxtLayout>` ([Layouts](https://nuxt.com/docs/4.x/directory-structure/app/layouts)). The framework reads the folder: "components placed in this directory will be automatically loaded via asynchronous import when used", and layout names are normalized to kebab case ([Layouts](https://nuxt.com/docs/4.x/directory-structure/app/layouts)). The docs steer small apps away from the folder: "If you only have a single layout in your application, we recommend using `app.vue` instead" ([Layouts](https://nuxt.com/docs/4.x/directory-structure/app/layouts), [Views](https://nuxt.com/docs/4.x/getting-started/views)).

A layout is therefore a `.vue` single file component in `app/layouts/`, not a plain function; the layouts page shows no function form, and the one structural rule is that "Your layouts must have a single root element to allow Nuxt to apply transitions between layout changes" ([Layouts](https://nuxt.com/docs/4.x/directory-structure/app/layouts)). The generated starter has no layout at all: the `v4` branch contains only `app/app.vue`, `public/favicon.ico`, `public/robots.txt`, `nuxt.config.ts`, `package.json`, `tsconfig.json`, `.gitignore` and `README.md`, and that `app.vue` renders `<NuxtRouteAnnouncer />` and `<NuxtWelcome />` ([nuxt/starter v4](https://github.com/nuxt/starter/tree/v4)). The official layouts example has `app.vue` wrapping `<NuxtLayout class="layouts"><NuxtPage /></NuxtLayout>`, three files `layouts/default.vue`, `layouts/custom.vue`, `layouts/other.vue`, and `pages/custom.vue` declaring `definePageMeta({ layout: 'custom' })` ([examples/features/layouts](https://github.com/nuxt/examples/tree/main/examples/features/layouts)).

### Shared page pieces

A component used by several routes goes in `app/components/`, a root level sibling of `pages/` and `layouts/` inside `app/`, and the framework reads the folder: "Nuxt automatically imports any components in this directory (along with components that are registered by any modules you may be using)" ([Components](https://nuxt.com/docs/4.x/directory-structure/app/components)). The Views page states the same for the four kinds: components are "reusable pieces of the user interface, like buttons and menus" placed in `app/components/`, "and they will be automatically available across your application without having to explicitly import them" ([Views](https://nuxt.com/docs/4.x/getting-started/views)). Naming is derived from the path: `components/base/foo/Button.vue` becomes `<BaseFooButton />`, duplicate segments are removed, and "For clarity, we recommend that the component's filename matches its name" ([Components](https://nuxt.com/docs/4.x/directory-structure/app/components)). The scan is configurable through the `components` option: entries such as `{ path: '~/user-module/components', pathPrefix: false }` or `{ path: '~/components/special-components', prefix: 'Special' }`, with the plain `'~/components'` entry last; `~` resolves to `/<rootDir>/app` in Nuxt 4 ([Components](https://nuxt.com/docs/4.x/directory-structure/app/components), [Nuxt Configuration, alias](https://nuxt.com/docs/4.x/api/nuxt-config)). The scan can be switched off by "setting `components.dirs` to an empty array" ([Auto-imports](https://nuxt.com/docs/4.x/guide/concepts/auto-imports)). Two extra conventions exist in the same folder: a `components/global/` subfolder or a `.global.vue` suffix registers a component globally, and the `Lazy` prefix (`<LazyMountainsList />`) defers loading ([Components](https://nuxt.com/docs/4.x/directory-structure/app/components)).

Neither the pages page nor the components page describes colocating a component next to its route; the pages page does not say where components used by a page go, and `pages/` is read only for routes ([Pages](https://nuxt.com/docs/4.x/directory-structure/app/pages)). The starter generates no `components/` folder ([nuxt/starter v4](https://github.com/nuxt/starter/tree/v4)). The examples all use the one folder: `components/CustomInput.vue` in the auto imports example, `components/TheQuote.vue` in the data fetching example, `components/TButton.vue` in the Tailwind example, and `app/components/AppHeader.vue`, `ItemListNav.vue`, `LoadSpinner.vue`, `LoadingWrapper.vue`, `PostComment.vue`, `PostItem.vue` in hackernews ([nuxt/examples](https://github.com/nuxt/examples), [nuxt/hackernews](https://github.com/nuxt/hackernews)). The examples' own description reads: "Vue components in the `components/` directory are auto-imported and can be used directly in your templates" ([Auto Imports example](https://nuxt.com/docs/4.x/examples/features/auto-imports)).

### Small formatters

The folder is called `utils/`, and in Nuxt 4 it sits at `app/utils/`. "Use the utils/ directory to auto-import your utility functions throughout your application", and "The main purpose of the `app/utils/` directory is to allow a semantic distinction between your Vue composables and other auto-imported utility functions" ([Utils](https://nuxt.com/docs/4.x/directory-structure/app/utils)). The framework reads it: a named export is available everywhere under its own name, a default export under the camel cased file name ("available as randomEntry()"), and scanning "is identical to the `app/composables/`" directory, which means top level files only unless `imports.dirs` is extended with globs such as `'~/composables/**'` ([Utils](https://nuxt.com/docs/4.x/directory-structure/app/utils), [Composables](https://nuxt.com/docs/4.x/directory-structure/app/composables)). The docs' own example is a number formatter:

```ts
// utils/index.ts (label as printed in the docs)
export const { format: formatNumber } = Intl.NumberFormat('en-GB', {
  notation: 'compact',
  maximumFractionDigits: 1,
})
```

used as `<p>{{ formatNumber(1234) }}</p>` in `app/app.vue` ([Utils](https://nuxt.com/docs/4.x/directory-structure/app/utils)). A formatter needed on both sides goes in `shared/utils/`: "Use the shared/ directory to share functionality between the Vue app and the Nitro server", "Code in the shared/ directory cannot import any Vue or Nitro code", "available in Nuxt v3.14+", and only `shared/utils/` and `shared/types/` are auto imported, with the tree showing `shared/utils/formatters/upper.ts` as "Not auto-imported" because it is nested; the example is `shared/utils/capitalize.ts` consumed by both `app/app.vue` and `server/api/hello.get.ts` ([Shared](https://nuxt.com/docs/4.x/directory-structure/shared)).

No official example has a money or date formatter. The auto imports example has `utils/string.ts` with `export const upperCase = (str: string) => str.toUpperCase()`, called from `composables/hello.ts` ([examples/features/auto-imports](https://github.com/nuxt/examples/tree/main/examples/features/auto-imports)); the layers example has `base/utils/bar.ts` with `export const getBar = () => 'bar'` ([examples/advanced/config-extends](https://github.com/nuxt/examples/tree/main/examples/advanced/config-extends)). The hackernews app is the closest: `app/utils/index.ts` holds `host(url)`, `pluralize(time, label)`, `isAbsolute(url)` and a time formatter:

```ts

export function timeAgo(time: number | Date) {
  const between = Date.now() / 1000 - Number(time)
  if (between < 3600) {
    return pluralize(~~(between / 60), ' minute')
  }
  else if (between < 86400) {
    return pluralize(~~(between / 3600), ' hour')
  }
  else { return pluralize(~~(between / 86400), ' day') }
}
```

and templates call `{{ timeAgo(item.time) }} ago` and `({{ host(item.url) }})` without an import ([nuxt/hackernews app/utils/index.ts](https://github.com/nuxt/hackernews/blob/main/app/utils/index.ts), [PostItem.vue](https://github.com/nuxt/hackernews/blob/main/app/components/PostItem.vue)). The same app keeps a root level `utils/api.ts` commented "Shared between app & server" that is not auto imported (it is outside `shared/`) and is pulled in explicitly with `import { validFeeds } from '~~/utils/api'`, `~~` being `/<rootDir>` ([utils/api.ts](https://github.com/nuxt/hackernews/blob/main/utils/api.ts), [app/middleware/feed.ts](https://github.com/nuxt/hackernews/blob/main/app/middleware/feed.ts), [Nuxt Configuration, alias](https://nuxt.com/docs/4.x/api/nuxt-config)). The starter generates no `utils/` folder.

### The logic behind a route

Data access and mutations belong to the `server/` directory at the project root, outside `app/`, run by Nitro: "Build full-stack applications with Nuxt's server framework. You can fetch data from your database or another server, create APIs, or even generate static server-side content like a sitemap or a RSS feed" ([Server](https://nuxt.com/docs/4.x/getting-started/server)). "The server/ directory is used to register API and server handlers to your application"; files in `server/api/` are prefixed with `/api`, `server/routes/` are not, `server/middleware/` runs before every request, and "Each file should export a default function defined with `defineEventHandler()` or `eventHandler()`" ([Server directory](https://nuxt.com/docs/4.x/directory-structure/server)). The HTTP method is encoded in the file name, and the body of a form post is read in the handler:

```ts
// server/api/submit.post.ts
export default defineEventHandler(async (event) => {
  const body = await readBody(event)
  return { body }
})
```

([Server directory](https://nuxt.com/docs/4.x/directory-structure/server)). Server helpers go in `server/utils/`: "In the `server` directory, Nuxt auto-imports exported functions and variables from `server/utils/`" ([Auto-imports](https://nuxt.com/docs/4.x/guide/concepts/auto-imports)).

On the page side there is no loader or action convention; a page or component fetches in `<script setup>`. "Nuxt comes with two composables and a built-in library to perform data-fetching in browser or server environments: `useFetch`, `useAsyncData` and `$fetch`", and "It is recommended to use `$fetch` for client-side interactions (event-based) or combined with `useAsyncData` when fetching the initial component data" ([Data Fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching)). The form submission example lives in the component itself, labelled `app/app.vue`: `const { data } = await useFetch('/api/data')` for the initial read and `async function handleFormSubmit () { const res = await $fetch('/api/submit', { method: 'POST', body: { ... } }) }` for the event ([Data Fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching)). Shared client state is a composable: `useState` is "an SSR-friendly `ref` replacement" whose value is "shared across all components using a unique key", the recommended shape is `composables/states.ts` with `export const useColor = () => useState<string>('color', () => 'pink')`, and for a store library "Pinia" is named "the official Vue recommendation" with its example at `app/stores/website.ts`; the directory structure index lists no `stores/` directory, so that folder belongs to the Pinia module, not to Nuxt ([State Management](https://nuxt.com/docs/4.x/getting-started/state-management), [Directory Structure](https://nuxt.com/docs/4.x/directory-structure)).

The examples follow this split. The data fetching example has `pages/index.vue` calling `await useFetch('/api/hello')` against `server/api/hello.ts` ([examples/features/data-fetching](https://github.com/nuxt/examples/tree/main/examples/features/data-fetching)). The local auth example puts the operation in a composable, not the page: `pages/login.vue` submits with `@submit="authLogin(loginForm.email, loginForm.password).catch(onError)"`, `auth/composables/auth.ts` defines `authLogin` as a `$fetch('/api/auth/login', { method: 'POST', body: {...} })` followed by `navigateTo`, and `auth/server/api/auth/login.post.ts` does `const { email, password } = await readBody(event)` and calls `findUserByEmail` from `auth/server/utils/db.ts`, which wraps Nitro's `useStorage()` ([examples/auth/local](https://github.com/nuxt/examples/tree/main/examples/auth/local)). Hackernews keeps a client cache and fetch functions in one composable file, `app/composables/store.ts` (`useStore` over `useState`, plus `fetchItem`, `fetchFeed`, `fetchComments`, `fetchUser` calling `$fetch('/api/hn/item', ...)`), the upstream calls in `server/api/hn/item.get.ts` under `defineCachedEventHandler`, and the page `app/pages/item/[id].vue` awaiting `fetchItem(id.value)` in `<script setup>` ([nuxt/hackernews](https://github.com/nuxt/hackernews)).

### Interactive versus plain

One folder, one word. Pages, layouts and components are all Vue single file components ("Pages are Vue components and can have any valid extension that Nuxt supports"), and the components folder has no split between stateful and presentational files ([Pages](https://nuxt.com/docs/4.x/directory-structure/app/pages), [Components](https://nuxt.com/docs/4.x/directory-structure/app/components)). The only naming distinctions the framework reads concern where a component renders, not whether it holds state: "If a component is meant to be rendered only client-side, you can add the `.client` suffix to your component"; "Server components allow server-rendering individual components within your client-side apps", via the `.server` suffix and `<NuxtIsland>`; and when both exist "the component will render Comments.server on the server then Comments.client once mounted in the browser" ([Components](https://nuxt.com/docs/4.x/directory-structure/app/components)). Everything else is a plain SFC with or without a `<script setup>` block.

The examples bear this out. `components/CustomInput.vue` declares `defineProps(['modelValue'])` and `defineEmits(['update:modelValue'])` and emits on input, while `components/TheQuote.vue` fetches a quote and renders it; both sit in the same `components/` folder with the same `.vue` extension ([examples/features/auto-imports](https://github.com/nuxt/examples/tree/main/examples/features/auto-imports), [examples/features/data-fetching](https://github.com/nuxt/examples/tree/main/examples/features/data-fetching)). In hackernews, `app/components/PostItem.vue` only takes an `item` prop and renders it, and `LoadingWrapper.vue`, `ItemListNav.vue` and `PostComment.vue` live beside it with no prefix or subfolder marking which ones react to events ([nuxt/hackernews app/components](https://github.com/nuxt/hackernews/tree/main/app/components)). State that must survive hydration goes to `useState` inside a composable rather than into the component ("Never define `const state = ref()` outside of `<script setup>` or `setup()` function"), which moves the shared state out of the component file but does not rename or relocate the component ([State Management](https://nuxt.com/docs/4.x/getting-started/state-management)).

## The Redux style guide

Versions verified: the Redux documentation at redux.js.org carries no version number of its own; the pages below were read on 2026-10-02 and cross checked against the Markdown sources in the `master` branch of [reduxjs/redux](https://github.com/reduxjs/redux/blob/master/docs/style-guide/style-guide.md) (latest commit `56abca4` on 2026-09-30). Library releases: Redux Toolkit [v2.13.0](https://github.com/reduxjs/redux-toolkit/releases/tag/v2.13.0) (2026-09-29), Redux core [v5.0.1](https://github.com/reduxjs/redux/releases/tag/v5.0.1) (2023-12-23), React Redux [v9.3.0](https://github.com/reduxjs/react-redux/releases/tag/v9.3.0) (2026-05-15). Companion repositories: [reduxjs/redux-essentials-example-app](https://github.com/reduxjs/redux-essentials-example-app), branch `master` (commit `0d6135a`, 2026-09-19, the empty starting project), branch `tutorial-steps-ts` (commit `2fc16b0`, 2026-09-19, the finished app) and tags `ts-checkpoint-0-setup` through `ts-checkpoint-6-rtkqConversion`; [reduxjs/redux-templates](https://github.com/reduxjs/redux-templates), branch `master` (commit `37f05cf`, 2026-09-28), packages `vite-template-redux` and `expo-template-redux-typescript`, example `examples/rtk-app-structure-example`. The older `cra-template-redux` no longer exists on `master`: the repository README says "The older Create-React-App and React Native CLI templates were removed. Their last version is preserved at the `archive/cra-and-rn-cli` tag" ([Redux Project Templates README](https://github.com/reduxjs/redux-templates/blob/master/README.md)).

Redux is a state container, not a router or a page framework. It reads no folder and no file name. The style guide says so in the first sentence of its structure rule: "Redux itself does not care about how your application's folders and files are structured" ([Redux Style Guide](https://redux.js.org/style-guide/)), and the FAQ repeats it: "Since Redux is just a data store library, it has no direct opinion on how your project should be structured" ([Redux FAQ: Code Structure](https://redux.js.org/faq/code-structure)). Everything below is convention, graded by the style guide's three levels: Priority A, Essential ("These rules help prevent errors, so learn and abide by them at all costs"), Priority B, Strongly Recommended ("Your code will still run if you violate them, but violations should be rare and well-justified"), and Priority C, Recommended ("Where multiple, equally good options exist, an arbitrary choice can be made to ensure consistency") ([Redux Style Guide](https://redux.js.org/style-guide/)).

### The page frame

The question of a root layout does not apply to Redux as a framework: nothing in Redux is located by path. What the docs do say is where the store, the `Provider` and `App` sit. The Essentials tutorial's counter app lists its key files as follows ([Redux Essentials, Part 2: Redux Toolkit App Structure](https://redux.js.org/tutorials/essentials/part-2-app-structure)):

```
/src
  main.tsx: the starting point for the app
  App.tsx: the top-level React component
  /app
    store.ts: creates the Redux store instance
    hooks.ts: exports pre-typed React-Redux hooks
  /features
    /counter
      Counter.tsx: a React component that shows the UI for the counter feature
      counterSlice.ts: the Redux logic for the counter feature
```

The `Provider` is placed in the entry file, around the whole tree: "We already created our store in `app/store.ts`, so we can import it here. Then, we put our `<Provider>` component around the whole `<App>`, and pass in the store" ([Part 2](https://redux.js.org/tutorials/essentials/part-2-app-structure)). The Vite template's `main.tsx` does the same ([vite-template-redux/src/main.tsx](https://github.com/reduxjs/redux-templates/blob/master/packages/vite-template-redux/src/main.tsx)). The style guide's own example tree puts `App.tsx` inside `/app` instead, glossed "`/app` contains app-wide setup and layout that depends on all the other folders" ([Redux Style Guide](https://redux.js.org/style-guide/)); the tutorial and both templates keep it at `src/App.tsx`. In the social media example `App.tsx` is "the main application component. Renders the top navbar and handles client-side routing for the other content" ([Redux Essentials, Part 3: Basic Redux Data Flow](https://redux.js.org/tutorials/essentials/part-3-data-flow)); the finished file wraps a React Router `<Router>`, renders `<Navbar />` once above the `<Routes>`, and defines a local `ProtectedRoute` in the same file ([src/App.tsx, tutorial-steps-ts](https://github.com/reduxjs/redux-essentials-example-app/blob/tutorial-steps-ts/src/App.tsx)). The "layout" is a plain function, `App`, chosen by the application and wired by hand in `main.tsx`; only the bundler's entry reads its location, never Redux.

### Shared page pieces

The style guide's example tree reserves a folder for them: "`/common`: hooks, generic components, utils, etc", described as "truly generic and reusable utilities and components" ([Redux Style Guide](https://redux.js.org/style-guide/)). The tutorial and the companion repo use the name `components/` instead. The starting project on `master` and at `ts-checkpoint-0-setup` holds `src/components/Navbar.tsx`, `src/components/Spinner.tsx` and `src/components/UserIcon.tsx`, with no `app/` folder at all ([tree at ts-checkpoint-0-setup](https://github.com/reduxjs/redux-essentials-example-app/tree/ts-checkpoint-0-setup/src)). The finished branch adds `src/components/TimeAgo.tsx` and keeps the same four files there ([tree at tutorial-steps-ts](https://github.com/reduxjs/redux-essentials-example-app/tree/tutorial-steps-ts/src)). The prose of Part 3 is inconsistent with the repo on one file: its project listing places `Navbar.tsx` under `/app` ("`/app`: `Navbar.tsx`: renders the top header and nav content"), and several code block titles in Parts 4 and 6 say `app/Navbar.tsx`, while other code blocks in the same pages say `components/Navbar.tsx` and the repo has only `components/Navbar.tsx` ([Part 3](https://redux.js.org/tutorials/essentials/part-3-data-flow), [Part 4](https://redux.js.org/tutorials/essentials/part-4-using-data), [Part 6](https://redux.js.org/tutorials/essentials/part-6-performance-normalization)).

Components used by several routes but tied to one feature stay in the feature folder: `PostAuthor` is introduced because "we want to show this same kind of info in more than one place", is written to `features/posts/PostAuthor.tsx` and then imported "into both `PostsList.tsx` and `SinglePostPage.tsx`" ([Part 4](https://redux.js.org/tutorials/essentials/part-4-using-data)). The Vite template has no `components/` folder at all: `Counter.tsx` and `Quotes.tsx` sit in `features/counter/` and `features/quotes/` ([vite-template-redux tree](https://github.com/reduxjs/redux-templates/tree/master/packages/vite-template-redux/src)); the Expo template has `src/components/` (`AsyncButton`, `Header`, `Section`, and so on) and `src/constants/Colors.ts` ([expo-template-redux-typescript tree](https://github.com/reduxjs/redux-templates/tree/master/packages/expo-template-redux-typescript/src)). None of these folders is read by Redux; the FAQ lists the Rails style of "separate folders for 'actions', 'constants', 'reducers', 'containers', and 'components'" only as one of three common patterns ([Redux FAQ: Code Structure](https://redux.js.org/faq/code-structure)).

### Small formatters

No official Redux example has a money formatter. The one formatter in the Essentials app is the relative time display, and it is written as a React component, not a function in `utils/`. Part 4 introduces it: "We'll add a `<TimeAgo>` component to handle formatting a timestamp string as a relative description. Libraries like `date-fns` have some useful utility functions for parsing and formatting dates, which we can use here", and the code block is titled `components/TimeAgo.tsx` ([Part 4](https://redux.js.org/tutorials/essentials/part-4-using-data)). The file in the companion repo is identical ([src/components/TimeAgo.tsx, tutorial-steps-ts](https://github.com/reduxjs/redux-essentials-example-app/blob/tutorial-steps-ts/src/components/TimeAgo.tsx)):

```tsx
import { parseISO, formatDistanceToNow } from 'date-fns'

interface TimeAgoProps {
  timestamp: string
}

export const TimeAgo = ({ timestamp }: TimeAgoProps) => {
  let timeAgo = ''
  if (timestamp) {
    const date = parseISO(timestamp)
    const timePeriod = formatDistanceToNow(date)
    timeAgo = `${timePeriod} ago`
  }

  return (
    <time dateTime={timestamp} title={timestamp}>
      &nbsp; <i>{timeAgo}</i>
    </time>
  )
}
```

`PostsList.tsx` imports it with `import { TimeAgo } from '@/components/TimeAgo'`, next to `Spinner` from the same folder ([src/features/posts/PostsList.tsx](https://github.com/reduxjs/redux-essentials-example-app/blob/tutorial-steps-ts/src/features/posts/PostsList.tsx)). The companion repo has no `utils/`, `lib/` or `helpers/` folder on any branch read. The templates have `src/utils/`, but it holds only `test-utils.tsx`, a `renderWithProviders` wrapper around React Testing Library ([vite-template-redux/src/utils/test-utils.tsx](https://github.com/reduxjs/redux-templates/blob/master/packages/vite-template-redux/src/utils/test-utils.tsx)). The style guide's generic name for such things is `/common`, "hooks, generic components, utils, etc" ([Redux Style Guide](https://redux.js.org/style-guide/)). Nothing in any of these folders is read by Redux.

### The logic behind a route

This is the question the style guide answers most directly. The structure rule, Priority B, reads: "we recommend that most applications should structure files using a 'feature folder' approach (all files for a feature in the same folder). Within a given feature folder, the Redux logic for that feature should be written as a single 'slice' file, preferably using the Redux Toolkit `createSlice` API. (This is also known as the 'ducks' pattern). While older Redux codebases often used a 'folder-by-type' approach with separate folders for 'actions' and 'reducers', keeping related logic together makes it easier to find and update that code" ([Redux Style Guide](https://redux.js.org/style-guide/)). Its example tree has `/features/todos/todosSlice.ts`, glossed as "a 'duck'-style file that contains a call to RTK's `createSlice()` function, and exports the slice reducer and action creators", next to `Todos.tsx`, "a React component". The FAQ lists the three structures, "Rails-style", "'Feature folders' / 'Domain'-style" and "'Ducks/Slices': similar to domain style, but explicitly tying together actions and reducers, often by defining them in the same file", then states "We specifically recommend organizing your logic into 'feature folders', with all the Redux logic for a given feature in a single 'slice/ducks' file" ([Redux FAQ: Code Structure](https://redux.js.org/faq/code-structure)). The tutorial defines the unit: "A 'slice' is a collection of Redux reducer logic and actions for a single feature in your app, typically defined together in a single file" ([Part 2](https://redux.js.org/tutorials/essentials/part-2-app-structure)).

Where business logic goes inside that file is graded too. "Put as Much Logic as Possible in Reducers" is Priority B: "try to put as much of the logic for calculating a new state into the appropriate reducer, rather than in the code that prepares and dispatches the action (like a click handler)". "Reducers Should Own the State Shape" is Priority B: "each 'slice reducer' being responsible for providing an initial value and calculating the updates to that slice of the state". "Model Actions as Events, Not Setters" is Priority B: "we recommend trying to treat actions more as 'describing events that occurred', rather than 'setters'". "Write Action Types as `domain/eventName`" is Priority C: "we suggest using the 'domain/action' convention for readability". "Use Redux Toolkit for Writing Redux Logic" is Priority B. Side effects are Priority C: "Use RTK Query for Data Fetching" ("we recommend using RTK Query as the default approach for data fetching and caching in a Redux app ... We recommend against writing data fetching logic by hand in almost all cases") and "Use Thunks and Listeners for Other Async Logic" ("We recommend using the Redux thunk middleware for imperative logic, such as complex sync logic that needs access to `dispatch` or `getState`, and moderately complex async logic. This includes use cases like moving logic out of components"). The companion rule "Move Complex Logic Outside Components", also Priority C, adds: "We still encourage moving complex synchronous or async logic outside components, usually into thunks ... However, the use of React hooks does make it somewhat easier to manage logic like data fetching directly inside a component" ([Redux Style Guide](https://redux.js.org/style-guide/)). The FAQ frames it as a spectrum between "'fat' action creators, with 'thin' reducers" and the reverse, and concludes "We recommend putting as much logic as possible into reducers ... but reducers should do most of the work" ([Redux FAQ: Code Structure](https://redux.js.org/faq/code-structure)). The thunks page: "Thunks are a standard approach for writing async logic in Redux apps", and "It's preferable to put as much logic as possible in reducers, but it's fine for thunks to also have additional logic inside as well" ([Writing Logic with Thunks](https://redux.js.org/usage/writing-logic-thunks)). Selectors follow the reducer: "it's a good idea to define reusable selectors alongside their corresponding reducers", exporting `selectTodos` from `src/features/todos/todosSlice.ts` ([Deriving Data with Selectors](https://redux.js.org/usage/deriving-data-selectors)).

The tutorial's file paths bear this out. Data access splits in two. The transport lives outside the features: "a small HTTP API client object that exposes `client.get()` and `client.post()` methods ... defined in `src/api/client.ts`", and the fake REST API "defined in `src/api/server.ts`" ([Redux Essentials, Part 5: Async Logic and Data Fetching](https://redux.js.org/tutorials/essentials/part-5-async-logic)). The operations live in the slice: "Thunks are typically written in 'slice' files, since the thunk data fetching is usually conceptually related to a particular slice's update logic", and `fetchPosts = createAppAsyncThunk('posts/fetchPosts', async () => { const response = await client.get<Post[]>('/fakeApi/posts') ...` is in `features/posts/postsSlice.ts`, with the typed thunk factory in `src/app/withTypes.ts` ([Part 5](https://redux.js.org/tutorials/essentials/part-5-async-logic)). The form submission is a `handleSubmit` in the component `features/posts/AddPostForm.tsx`: in Part 3 it dispatches the `postAdded` action created by `postsSlice`; in Part 5 it becomes `await dispatch(addNewPost({ title, content, user: userId })).unwrap()` with a local `useState` for the request status; in Part 7 it calls `useAddNewPostMutation()` from `features/api/apiSlice.ts`, a folder added because "this isn't specific to any of the other 'features' we've already written" and because "Your application is expected to have only one `createApi` call in it" ([Part 3](https://redux.js.org/tutorials/essentials/part-3-data-flow), [Part 5](https://redux.js.org/tutorials/essentials/part-5-async-logic), [Redux Essentials, Part 7: RTK Query Basics](https://redux.js.org/tutorials/essentials/part-7-rtk-query-basics)). The Vite template puts its fake fetch in the feature folder rather than in `api/`: `features/counter/counterAPI.ts` holds `fetchCount`, "A mock function to mimic making an async request for data", which `counterSlice.ts` wraps in `createAsyncThunk("counter/fetchCount", ...)` ([counterAPI.ts](https://github.com/reduxjs/redux-templates/blob/master/packages/vite-template-redux/src/features/counter/counterAPI.ts), [counterSlice.ts](https://github.com/reduxjs/redux-templates/blob/master/packages/vite-template-redux/src/features/counter/counterSlice.ts)). The RTK usage guide says nothing about file placement ([Redux Toolkit Usage Guide](https://redux.js.org/toolkit/usage/usage-guide)).

### Interactive versus plain

Redux separates them neither by folder nor by name. `features/posts/` holds `PostsList.tsx` (reads the store), `AddPostForm.tsx` and `EditPostForm.tsx` (form state plus dispatch), `ReactionButtons.tsx` (dispatches), `PostAuthor.tsx` (reads one user, renders a name) and `SinglePostPage.tsx`, all called "component" ([tree at tutorial-steps-ts](https://github.com/reduxjs/redux-essentials-example-app/tree/tutorial-steps-ts/src/features/posts)). `TimeAgo` goes to `components/` because it is generic, not because it is stateless ([Part 4](https://redux.js.org/tutorials/essentials/part-4-using-data)). The style guide names the older vocabulary and retires it: `connect` "allows you to write 'presentational'-style components that receive all their values as props", but "While the 'container/presentational' concept is still valid, hooks push you to write components that are responsible for requesting their own data internally by calling an appropriate hook" ([Redux Style Guide](https://redux.js.org/style-guide/)); the thunks page says "The community has switched away from the 'container/presentational' pattern in general" ([Writing Logic with Thunks](https://redux.js.org/usage/writing-logic-thunks)). The replacement rule is about granularity, not kind: "Connect More Components to Read Data from the Store", Priority B, wants `<UserListItem>` to "call `useSelector` to extract its own user entry from the store" rather than receive it as a prop. Local interactivity stays local: "Avoid Putting Form State In Redux", Priority C, says "Most form state shouldn't go in Redux" ([Redux Style Guide](https://redux.js.org/style-guide/)); the tutorial's `Counter` keeps `useState('2')` for its input because "The only place that text string is used is here, in the `<Counter>` component" ([Part 2](https://redux.js.org/tutorials/essentials/part-2-app-structure)), and Part 3 summarises "Temporary data like form input values should be kept as React component state or plain HTML input fields. Dispatch a Redux action to update the store when the user is done with the form" ([Part 3](https://redux.js.org/tutorials/essentials/part-3-data-flow)).

## The React documentation

Versions verified: react.dev as served on 2026-10-02, documenting React 19.3 (released September 9, 2026, per [Versions](https://react.dev/versions) and the [facebook/react releases page](https://github.com/facebook/react/releases), where 19.3.0 is the latest stable tag). The docs source was also read from the [reactjs/react.dev](https://github.com/reactjs/react.dev) repository, default branch, latest commit `8c68ae8d2410abe59f351195780c6f8ea9f50904` dated 2026-10-01; file names quoted below come from the Sandpack blocks in `src/content/learn/*.md` and `src/content/reference/rsc/*.md`. The legacy FAQ was read from [legacy.reactjs.org](https://legacy.reactjs.org/docs/faq-structure.html), which carries the banner "This site is no longer updated. Go to react.dev" and documents React 18 era practice.

React is a library with no router, no file convention and no build tool, and react.dev says so: the build tools it names "start off with a client-only, single-page app (SPA), but don't include any further solutions for common functionality like routing, data fetching, or styling" ([Build a React app from Scratch](https://react.dev/learn/build-a-react-app-from-scratch)). Most answers below therefore come from what react.dev does in its examples and from its silence, which is consistent and is the main finding.

### The page frame

React has no layout concept and react.dev never uses the word layout for an application shell. The nearest thing is the root component: "Your React application begins at a "root" component. Usually, it is created automatically when you start a new project. For example, if you use CodeSandbox or if you use the framework Next.js, the root component is defined in `pages/index.js`." ([Your First Component](https://react.dev/learn/your-first-component)). The next page names the file: "These currently live in a root component file, named `App.js` in this example. Depending on your setup, your root component could be in another file, though. If you use a framework with file-based routing, such as Next.js, your root component will be different for every page." ([Importing and Exporting Components](https://react.dev/learn/importing-and-exporting-components)). react.dev's own sandbox calls the root `App.js` and puts every file at the project root, with no `src/` or `pages/`; the `pages/index.js` path is attributed to Next.js.

Whether a location is read is answered by delegation. "If you want to build a new app or website with React, we recommend starting with a framework." ([Creating a React App](https://react.dev/learn/creating-a-react-app)); under "Full-stack frameworks" it lists Next.js (App Router), React Router (v7) and Expo (for native apps), under "Other frameworks" TanStack Start (Beta) and RedwoodSDK, and under "Start From Scratch" Vite, Parcel and Rsbuild. On the from-scratch path: "Routers can be configured within your code, or defined based on your component folder and file structures." ([Build a React app from Scratch](https://react.dev/learn/build-a-react-app-from-scratch)). That is the only sentence on react.dev connecting a folder to behaviour, and it hands the choice to a router library. In React itself a layout is a plain function taking `children`, as in `Card({ children })` ([Passing Props to a Component](https://react.dev/learn/passing-props-to-a-component)) and `TasksProvider({ children })` ([Scaling Up with Reducer and Context](https://react.dev/learn/scaling-up-with-reducer-and-context)). Nothing reads its location.

### Shared page pieces

React has one word for everything on screen: "React applications are built from isolated pieces of UI called components." ([Describing the UI](https://react.dev/learn/describing-the-ui)). "Most React apps use components all the way down. This means that you won't only use components for reusable pieces like buttons, but also for larger pieces like sidebars, lists, and ultimately, complete pages! Components are a handy way to organize UI code and markup, even if some of them are only used once." ([Your First Component](https://react.dev/learn/your-first-component)). React's built-in ones are `<Fragment>`, `<Profiler>`, `<Suspense>`, `<StrictMode>`, `<Activity>` and `<ViewTransition>`, followed by "You can also define your own components as JavaScript functions." ([Built-in React Components](https://react.dev/reference/react/components)).

Where a shared component goes is answered at the level of files, never folders, and the motive is file size, not role: "You can declare many components in one file, but large files can get difficult to navigate. To solve this, you can export a component into its own file, and then import that component from another file." ([Describing the UI](https://react.dev/learn/describing-the-ui)). The example moves `Gallery` and `Profile` out of `App.js` into `Gallery.js` ("Make a new JS file to put the components in", export, import). The export rule is JavaScript's: "A file can have no more than one default export, but it can have as many named exports as you like." and the habit is called a habit: "People often use default exports if the file exports only one component, and use named exports if it exports multiple components and values. Regardless of which coding style you prefer, always give meaningful names to your component functions and the files that contain them." ([Importing and Exporting Components](https://react.dev/learn/importing-and-exporting-components)). A grep of the Learn and RSC source for `components/`, `lib/`, `helpers/`, `utils/`, `hooks/`, `pages/` and `features/` as folders finds only URL paths such as `/reference/react-dom/components/common`. react.dev names no `components/` folder anywhere, and React reads no files.

[Thinking in React](https://react.dev/learn/thinking-in-react) decomposes an application entirely without folders. The split criterion: "One such technique is the separation of concerns, that is, a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents." The five components, `FilterableProductTable`, `SearchBar`, `ProductTable`, `ProductCategoryRow` and `ProductRow`, are all defined in the single `App.js` of each of the page's three sandboxes (verified in the source). The page names no folder and no file per component.

The only file structure guidance the React team ever wrote is legacy, React 18 era, on a site that says "This site is no longer updated". The [File Structure FAQ](https://legacy.reactjs.org/docs/faq-structure.html) opens: "React doesn't have opinions on how you put files into folders. That said there are a few common approaches popular in the ecosystem you may want to consider." It shows "Grouping by features or routes" (`common/`, `feed/`, `profile/`, each holding its JS, CSS and tests) and "Grouping by file type" (`api/`, `components/`), then "Avoid too much nesting" ("consider limiting yourself to a maximum of three or four nested folders within a single project") and "Don't overthink it" ("don't spend more than five minutes on choosing a file structure", "If you feel completely stuck, start by keeping all files in a single folder.", and "it is a good idea to keep files that often change together close to each other. This principle is called "colocation"."). react.dev has no equivalent: none of the fifty pages in the `/learn` index is about structure, the sitemap has no URL matching struct, folder, organi or project, and a `site:react.dev` search for "file structure" and "project structure" returned only third-party blogs.

### Small formatters

react.dev has exactly one formatter in the Learn section (found by grepping the source for `Intl.`). It sits in the same file as the component that calls it and exists only to show that a call is an expression: "Any JavaScript expression will work between curly braces, including function calls like `formatDate()`" ([JavaScript in JSX with Curly Braces](https://react.dev/learn/javascript-in-jsx-with-curly-braces)).

```js
// App.js, from "JavaScript in JSX with Curly Braces"
const today = new Date();

function formatDate(date) {
  return new Intl.DateTimeFormat(
    'en-US',
    { weekday: 'long' }
  ).format(date);
}

export default function TodoList() {
  return (
    <h1>To Do List for {formatDate(today)}</h1>
  );
}
```

There is no money formatter on react.dev; prices in Thinking in React are string literals such as `"$1"` in the data. Other formatting is inline: `time.toLocaleTimeString()` passed as a prop in [Passing Props to a Component](https://react.dev/learn/passing-props-to-a-component) and in the `Clock` of [Keeping Components Pure](https://react.dev/learn/keeping-components-pure).

The one helper file react.dev uses is `utils.js`, a flat file beside `App.js`, never a folder, imported as `import { getImageUrl } from './utils.js';` and left unexplained ([Passing Props to a Component](https://react.dev/learn/passing-props-to-a-component), [Rendering Lists](https://react.dev/learn/rendering-lists)):

```js
// utils.js
export function getImageUrl(person, size = 's') {
  return (
    'https://react.dev/images/docs/scientists/' +
    person.imageId +
    size +
    '.jpg'
  );
}
```

Static data goes into flat siblings `data.js` and `places.js` ([Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)). None of this is read by React. The only naming rule for a plain function is negative: "If your function doesn't call any Hooks, avoid the `use` prefix. Instead, write it as a regular function without the `use` prefix. For example, `useSorted` below doesn't call Hooks, so call it `getSorted` instead" ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

### The logic behind a route

React has no routes, so it has no logic behind one. What it has is a position on where state logic and side effects go, plus module conventions for Server Components.

For a client application, logic leaves the component in two named steps. The reducer: "you can move that state logic into a single function outside your component, called a "reducer"." and "If you want, you can even move the reducer to a different file:", with the sandbox showing `tasksReducer.js` beside `App.js`, `AddTask.js` and `TaskList.js` ([Extracting State Logic into a Reducer](https://react.dev/learn/extracting-state-logic-into-a-reducer)). The wiring: "You don't have to do this, but you could further declutter the components by moving both reducer and context into a single file." `TasksContext.js` then holds the contexts, the reducer, `TasksProvider` and the hooks `useTasks()` and `useTasksDispatch()`: "Now all of the context and reducer wiring is in `TasksContext.js`. This keeps the components clean and uncluttered, focused on what they display rather than where they get the data" ([Scaling Up with Reducer and Context](https://react.dev/learn/scaling-up-with-reducer-and-context)). Custom hooks get one file each, `useOnlineStatus.js`, `useFormInput.js`, `useChatRoom.js`, and "Custom Hooks let you share stateful logic but not state itself." ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Where a submission's effect runs is a principle, not a place: "In React, side effects usually belong inside event handlers." and `useEffect` "should be your last resort" ([Keeping Components Pure](https://react.dev/learn/keeping-components-pure)). Data fetching is delegated: "we recommend prefetching data in router loaders or on the server as much as possible!" ([Build a React app from Scratch](https://react.dev/learn/build-a-react-app-from-scratch)).

For Server Components the unit is still the module. "Server Components are a new type of Component that renders ahead of time, before bundling, in an environment separate from your client app or SSR server." They have no marker: "A common misunderstanding is that Server Components are denoted by `"use server"`, but there is no directive for Server Components. The `"use server"` directive is used for Server Functions." Data access is written in the component, `const notes = await db.notes.getAll();` inside `async function Notes()` ([Server Components](https://react.dev/reference/rsc/server-components)). The operation a form triggers is a Server Function, shown in two placements with no preference: inline, `async function createNoteAction() { 'use server'; await db.notes.create(); }` inside the `EmptyNote` component; or in a file, "Client Components can import Server Functions from files that use the `"use server"` directive", imported as `import {createNote} from './actions';` ([Server Functions](https://react.dev/reference/rsc/server-functions)). The file form marks "all exports within that file as Server Functions", and "To import a Server Functions from client code, the directive must be used on a module level." ([use server](https://react.dev/reference/rsc/use-server)). `actions.js` is a flat sibling of `App.js`; no page says where it must live.

### Interactive versus plain

React does not separate an interactive component from a rendering one by folder or name. Both are components, both are functions, and interactivity is added by giving the same component props and state, not by renaming or moving it. Thinking in React is built on this: "It's often easier to build the static version first and add interactivity later. Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing." and "don't use state at all to build this static version. State is reserved only for interactivity, that is, data that changes over time." The source confirms the static and final sandboxes hold the same five functions in the same file; only signatures change, `SearchBar()` becoming `SearchBar({ filterText, inStockOnly, onFilterTextChange, onInStockOnlyChange })` and `FilterableProductTable` gaining `useState`. Who owns state is positional: "Find their closest common parent component", or "create a new component solely for holding the state and add it somewhere in the hierarchy above the common parent component." ([Thinking in React](https://react.dev/learn/thinking-in-react)). The only vocabulary for the two kinds is a Deep Dive: "uncontrolled" is "a component with some local state", "controlled" is "when the important information in it is driven by props rather than its own local state"; no folder or naming convention follows ([Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)).

The one hard line React draws is in the Server Components model, and it is a file, not a folder. "Add `'use client'` at the top of a file to mark the module and its transitive dependencies as client code." It must be "at the very beginning of a file, above any imports or other code", and "`'use client'` defines the boundary between server and client code on the module dependency tree, not the render tree." The example keeps `src/App.js`, `src/FancyText.js`, `src/InspirationGenerator.js` (the only file with the directive), `src/Copyright.js` and `src/inspirations.js` in one place; `FancyText` is rendered from both sides and stays one file. When to mark is about capability: "As Server Components are default, here is a brief overview of the advantages and limitations to Server Components to determine when you need to mark something as client rendered.", with "Server Components cannot support interaction as event handlers must be registered and triggered by a client." and "Server Components cannot use most Hooks." ([use client](https://react.dev/reference/rsc/use-client)). The page says nothing about a folder for client components.

The single naming rule React enforces is for Hooks, not components: "Hook names must start with `use` followed by a capital letter, like `useState` (built-in) or `useOnlineStatus` (custom, like earlier on the page)." and "If your linter is configured for React, it will enforce this naming convention." ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

Where the JavaScript frameworks agree with the eight server frameworks:

- The page frame has a framework given home in every router framework, as it did in six of the eight server frameworks. Next.js reads `app/layout.js` ("must include a root layout"), React Router reads `app/root.tsx` ("the only required route"), SvelteKit reads `src/routes/+layout.svelte`, Nuxt reads `app/app.vue` and `app/layouts/default.vue`. Rails' `layouts/application`, Phoenix's `Layouts.app`, ASP.NET Core's `Shared/_Layout` and Play's `main.scala.html` are the same move. In both groups the frame is a file found by name, and the application's freedom is to omit it (SvelteKit and Nuxt supply a default), to nest it, or to move the whole tree (`src/`, `appDirectory`, `files.routes`).
- Small formatters are never a folder the framework reads. In the first survey every formatter was a registration or an import (Rails helpers, Django `templatetags/`, Flask filters). Here they are plain modules imported by path: `app/lib/utils.ts` in the Learn course, `utils/stripe-helpers.ts` in the Stripe example, `app/utils/` in the React Router examples, `src/lib` in SvelteKit. Nuxt is the one exception on either side, since `app/utils/` and `shared/utils/` are scanned and auto imported, and even there the scan is a convenience over ordinary exports. Nothing in either group generates the file where a formatter goes except Rails, Django, Phoenix and, by its `formatNumber` example, the Nuxt docs.
- The HTTP side sequences the write. In the server frameworks the handler did the write and the redirect (Rails `create`, Django `vote`, Razor `OnPostAsync`). Here the route module does it: Next.js Server Functions in `app/lib/actions.ts` end with `revalidatePath` and `redirect`, React Router `action` exports call `updateContact` then `redirect`, SvelteKit `actions` in `+page.server.js` call `db.createTodo`, Nuxt `server/api/*.post.ts` handlers read the body and reply. The data call itself is pulled from a neighbouring module in every official example (`app/lib/data.ts`, `app/data.ts`, `#lib/server/database.js`, `server/utils/db.ts`), as Phoenix pulled it from a context and Play from an injected repository.
- A separate business or service layer is never generated and almost never named. The first survey found no framework that generates a service folder. Here create-next-app generates `app/layout.tsx`, `app/page.tsx` and nothing else; the React Router template generates `root.tsx`, `routes.ts`, one route and one `welcome/` component; `sv create` minimal generates an empty `src/lib/index.ts`; `nuxi init` generates `app/app.vue` alone; the Redux Vite template generates `app/store.ts` and `features/counter/`. The one document in either group that names such a layer as a recommendation is the Next.js data security guide ("Data Access Layer: for new projects"), and it names no folder, using `data/` in one example and `lib/data.ts` in another.
- Package by layer versus package by feature splits both groups the same way. The Redux style guide puts feature folders at Priority B and calls folders by type "older"; the Learn course splits `app/ui/` by route name (`dashboard/`, `invoices/`); Next.js offers "Split project files by feature or route" as one of three; React Router's fs convention colocates by route folder; SvelteKit's rule is "put code close to where it's used". Spring's `customer/` package, Play's `app/v1/post` and Phoenix's contexts were the feature camp before; Rails, Django and Laravel the layer camp. The JavaScript group leans harder to feature folders, and only Nuxt and the legacy React FAQ's "grouping by file type" show the by type layout as a first class option.

Where the JavaScript frameworks differ from the eight:

- The layout is a function in every JavaScript framework, and a template in most server frameworks. Rails, Django, Laravel's `@extends`, ASP.NET Core and Flask use a template that other templates extend; only Phoenix 1.8, Laravel's `<x-layout>` and Play's `main.scala.html` made the frame a component called with content. Here every layout is a component that receives `children` (Next.js and React Router), renders `children()` (SvelteKit) or a `<slot />` (Nuxt), and React's docs show the bare form as `Card({ children })`. But the function still lives in a file the framework finds by name; none of the four routers lets the application register a layout from code, and SvelteKit and Nuxt cannot express a layout as anything but a single file component.
- Shared pieces move from the template tree into code, and the frameworks stop reading the folder. The server frameworks read `app/views`, `templates/`, `Views/Shared/`, `resources/views/components` and discovered partials, fragments and view components by location. Of the four routers only Nuxt reads a components folder (`app/components/`, auto imported, names from the path). Next.js says it is "unopinionated" and that `components` and `lib` have "no special framework significance"; React Router reads nothing but `root.tsx`, `routes.ts` and the files they name; SvelteKit ignores every file in a route directory that does not start with `+`. What the frameworks offer instead is colocation: Next.js private folders `_components` and route groups, React Router's `folder/route.tsx`, SvelteKit's "Any other files inside a route directory are ignored", none of which the server frameworks had.
- The data layer has a sanctioned side. No server framework distinguished code that may run in the browser; here three of four do, by name: Next.js `server-only` and `'use server'`, React Router `.server` and `.client` suffixes whose misuse fails the build, SvelteKit `server` directories and `.server.js` that "will error" when imported from the browser, Nuxt `.client` and `.server` suffixes and the `server/` root. This is the one place where a folder or suffix name carries a rule in the JavaScript group, and it is about where code runs, not what it does.
- Reads sit in the view. Server frameworks fetched in the controller and passed data to a template; here a Server Component, a `load` function beside the page, a `loader` export or a `useFetch` in `<script setup>` fetches for the component that renders it, and the Next.js docs call the inline form "Component-Level Data Access". Only Nuxt keeps the server side in a separate `server/` tree the way a controller folder did.
- Stores exist as a question and are answered the same way by the routers and by Redux itself. The server frameworks had no equivalent. SvelteKit's state management page forbids shared server variables and tells the reader to persist to a database; Remix v2 said "most Remix applications forgo them entirely"; Nuxt names `useState` and Pinia for client state only; the Redux style guide keeps form state out of the store and puts the operation in a reducer or a thunk inside a feature's slice file, with transport in `src/api/`. Even Redux, the one tool whose purpose is a store, keeps the money and the time formatting out of it.
- Interactive versus plain is a boundary the server frameworks never needed. Rails, Django and the rest render once; the question did not arise. Here it does, and every framework answers it the same way: one word, one folder, a per file marker. Next.js and React mark client code with `'use client'` at the top of the file and place client and server components side by side in `app/ui/`; React Router and Nuxt use `.client` suffixes that mark where a file may load, not whether it holds state; SvelteKit has no marker at all. No official source in either group proposes a `client/` folder, a `containers/` folder or a naming suffix for stateful components; Redux names the container and presentational split only to say the community "switched away" from it.

What the pieces are called:

- The frame: `layout` (Next.js, `layout.js`; SvelteKit, `+layout.svelte`; Nuxt, `layouts/`), `root` with a `Layout` export (React Router), `app.vue` (Nuxt's entrypoint), `App` or the "root component" (React and Redux). The server frameworks said layout too (Rails, Laravel, ASP.NET Core), with `base.html` (Django, Flask) and `main` (Play) as the others.
- Shared pieces: `components/` by habit in Nuxt (read), vercel/commerce, the Redux tutorial and half the React Router examples; `ui/` in the Learn course and the other half; `lib` in SvelteKit for anything "needed by multiple routes"; `common/` in the Redux style guide; `welcome/` (a feature folder) in the React Router template. The server frameworks said partials, components, fragments, tags and view components, and read the folder.
- Formatters: `lib/` (Learn course `app/lib/utils.ts`, SvelteKit `src/lib`), `utils/` (Next.js Stripe example, React Router examples, Nuxt `app/utils/` and `shared/utils/`, Redux templates' `src/utils/`), a flat `utils.js` (React docs). No official source in the JavaScript group uses `helpers/`, where Rails said helpers and Flask said filters.
- The logic behind a route: Server Functions or Server Actions in `actions.ts` (Next.js), `loader` and `action` (React Router), `load` and `actions` (SvelteKit), event handlers under `server/api` (Nuxt), reducers and thunks in a slice (Redux). The data module beneath them is `data.ts` (Next.js Learn, React Router tutorial), `database.js` or `db.server.ts` (SvelteKit, Remix), `server/utils/db.ts` (Nuxt), `api/client.ts` (Redux); the Next.js security guide's name for the layer is Data Access Layer. The server frameworks called the same thing a model, a context, a repository or a service.
- Interactive versus plain: Client Component and Server Component (Next.js, React), with no name for a stateful component as such in any framework; SvelteKit, Nuxt, React Router and Redux use the single word component for both.
