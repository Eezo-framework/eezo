# Skeleton one landed the http surface its later tickets had already decided

**Status:** accepted

Issue #107 is the walking skeleton ticket for `modules/http`, and its text is narrow: one route, one response, no database, no derivation, no Store. The diff that closed it is wider than that text. Six pieces of scope that belong to tickets #107 never named landed inside it anyway, because each piece was a design #103, #105, #106 or #109 had already settled, and building #107 without it would have meant building a smaller version of the same code and throwing it away when the owning ticket arrived. This ADR names each piece, names the ticket that actually decided it, and records that the decision is to keep all six rather than revert any of them. It also records one thing #107 pulled back out after landing it, because a decided design that got deleted belongs in this record as much as a decided design that got kept.

## What landed early

**WebSocket routing end to end.** `#107` asked only that `WebSocketUpgradeHandler.from(server)` be configured. What shipped is the routing behind it: `Route.Ws`, `WsListener`, `WsConn`, the Jetty listener (`JettyListener` in `Eezo.scala`), `WebSocketSuite`, and the `jetty-websocket-jetty-client` test dependency that exercises it. The design is #106's, not #107's. It paid for itself immediately: building it is what surfaced the finding, now a comment on `JettyListener` itself, that Scala's mixin forwarders defeat Jetty's reflective event binding, so a listener must extend `Session.Listener.Abstract`, the class, rather than implement `Session.Listener`, the interface. `modules/live` would have hit that hazard head on with no comment warning it off, had this module shipped the bare configuration #107 asked for and left the routing for #106 to write from a standing start.

**Path matching beyond one static route.** `PathPattern`'s `:name` and `*rest` segments, `Request.param[A]`, its memoised multi valued form, and `FromPath` are #103's and #106's decisions, unreachable from the one static `GET` #107 describes. `*rest` in particular is not a convenience left in for later: the code generator translates a `__path` filename segment into it, so the catch all segment is a prerequisite for work #103 already commits to, not scope invented ahead of need.

**The request body's cap and the response body's `Bytes` case.** #107's one route needs neither: a static page reads no body and returns HTML, not encoded bytes. What shipped is #103's answer in full. `Eezo.run`'s `maxBodySize` parameter, defaulted to 1 MiB through `Config.DefaultMaxBodySize`, bounds the array `Request.body` holds; `readRequest` in `Eezo.scala` enforces it by reading one byte past the cap and throwing `PayloadTooLarge`, mapped to a 413, the moment `body.length` exceeds it, so a `Content-Length` the client controls is never mistaken for a limit. `Body.Bytes(value: Array[Byte])`, the case in `Response.scala`'s `Body` enum for output that is already encoded, sits beside `Html` and `Empty` for the same reason: #103 settled `Response`'s body as that sealed three case set, with a fourth case, `Stream`, reserved and unimplemented, before #107 had any body to return that was not HTML. Both are exercised now, the cap in `EezoServerSuite`, `Body.Bytes` there too, and neither is separable from #107's own `Request` and `Response`: the field and the case belong to the same case class and the same enum #107 constructs on every request, so keeping them is keeping the type #103 defined, and deleting either would mean re adding the same field and the same case under #103's own ticket after #107 had already shipped a narrower version of both.

**The problems hook.** `Eezo.run`'s `problems: PartialFunction[Throwable, Problem]` parameter is not creep at all. [ADR 0001](0001-http-errors-live-in-http-and-carry-no-status.md) documents this hook by name as the extension point for exceptions outside eezo's own sealed set, tried after eezo's own set and before the fallback to 500. That ADR is its authority. This entry exists only to point at it, so that a reader who finds the hook while auditing #107's diff does not mistake a decision already recorded for a fourth piece of scope creep.

**The generator's filename table and ordering.** #107 asked only that the sbt plugin turn one handwritten file into one generated route. What shipped is the whole convention #109 designed: the seven verb table, `Index`, `New`, `Show`, `Edit`, `Create`, `Update`, `Destroy`, mapping a filename to a method, a `def` name and a path suffix, with a custom filename falling back to a `def` of its own name; the `_id` to `:id` and `__path` to `*rest` directory translation that produces the segments `PathPattern` above parses; emit ordering that ranks a literal segment before `:name` before `*rest`, so `/widgets/new` stays reachable ahead of `/widgets/:id`, breaking ties by path and then by method so two runs of the generator emit the same file; and the missing def warning, a text scan that catches a filename with no matching `def` before the compiler ever sees it. All of it lives in `RouteGenerator.scala` and `EezoPlugin.scala` and is exercised by `RouteGeneratorSuite`. None of it is reachable from #107's single static route, one handwritten file never exercises seven verbs, a catch all directory, or an ordering tie, so a generator built for #107 alone would have been rewritten in full the day #109 arrived.

**The core HTML DSL.** #107 needed only enough HTML to render one response body. What shipped is #105's full design: the `Html` enum and its four cases, `Text`, `Raw`, `Element`, `Fragment`; escaping performed at construction behind a package private constructor so unescaped text cannot enter the tree from outside `eezo.core.html`; the `key` field that reaches `data-eezo-key` for `modules/live`'s future differ; fragment splicing, which keeps tree child index equal to DOM child index; the `Tag` and `Mod` union call site that the DSL is built on; and the `Tags` and `Attrs` objects, covering document, structure, text, lists, forms, media and tables. All of it lives under `modules/core/src/main/scala/eezo/core/html`, tested by `EscapingSuite`, `RenderingSuite` and `DslSuite`. #107's one route needed a handful of tags and no escaping discipline worth naming; the rest is #105's design, landed whole because a DSL sized to #107 alone would not have been the DSL `modules/live`'s diff already depends on.

One further departure is worth naming here because it was checked against the same research the skeleton otherwise follows: `research/http-server.md` section 12 configures `addMapping("/eezo/live", ...)`; `Eezo.start`, inside the `WebSocketUpgradeHandler.from` configuration closure in `Eezo.scala`, configures `container.addMapping("/*", ...)` instead. The comment beside that call already gives the reason, Jetty's path spec grammar cannot express a pattern mixing `:name` and a catch all, and PathPattern above is exactly that grammar, so a single catch all mapping handing every WebSocket path to eezo's own matcher is required by the second item on this list, not an unexplained drift from the research.

## What #107 pulled back out

`RouteGenerator.modelCandidates`, the `derived` half of `RouteGenerator.render`'s output, and the `PackageDeclaration`, `CaseClass` and `DerivesClause` regexes that fed it, landed early alongside the rest of this list and were removed again before #107 closed, along with the three tests in `RouteGeneratorSuite` that exercised them. Commit 8e6d524 is where the removal happened. It is correct on its own terms: the deleted code emitted `eezo.derives.Resource.routesOf[...]` against a `modules/derives` that carries no source, only a `.gitkeep`, and #107's own text is explicit, no database, no derivation, no Store. Shipping a call to a typeclass that cannot exist yet is not a walking skeleton, it is a compile error waiting on a module nobody has written.

But #109 decided that scan. Its ticket settles exactly this shape, one `Resource.routesOf[X]` line per candidate case class, letting the compiler rather than the generator decide whether a `Resource[X]` exists, and #102's decision log records it as settled, not as provisional. Deleting it without a note leaves no record that the deletion is a deferral rather than a reversal, and a reader of `RouteGeneratorSuite` today has no way to tell the two apart. The record this ADR keeps for an early addition applies the same way to this deletion: #109's model scan is not abandoned, it is correct and undeliverable until `modules/derives` holds a `Resource` typeclass for it to call, and that is #113's work. #113 is where the scan returns, built against a real `Resource[A]` rather than a name the compiler cannot yet resolve.

## Considered options

**Strip the diff back to the literal text of #107 and re add each piece under its own ticket.** Rejected. The routing, the path grammar, the listener hazard, the generator's conventions, and the HTML DSL are not separable from the walking skeleton without either deleting working, tested code or building a second, smaller version of it now and a full version later under #103, #105, #106 and #109. Both cost more than keeping what already compiles and passes its tests, and re adding the WebSocket listener later would mean rediscovering the mixin forwarder hazard a second time, without this ADR's comment to warn against it.

**Leave the scope undocumented and let #103, #105, #106 and #109 discover on arrival that their work is already done.** Rejected. A ticket that opens to find its surface already built has no record of what decided that surface or why, and review of the already landed code would happen nowhere, since #107's review is already closed. Recording it here gives each ticket a named starting point instead of a surprise.

## Consequences

`#103`, `#105`, `#106` and `#109` are all closed. Each closed by folding its design into #102's decision log, `Handler`, `Request`, `Response`, `PathPattern`, `Route.Ws`, `WsListener`, `WsConn`, the `Html` tree, and the generator's filename table and ordering are all recorded there as settled, not by commissioning anyone to review the code that shipped early against them. So the review this ADR originally meant to hand off has, as of this correction, no ticket carrying it. That is a real gap, not a formality: nothing open today is scoped to check `PathPattern`, `Route.Ws`, `WsListener`, `WsConn`, the `Html` tree, or `RouteGenerator` to the depth #107's own review, scoped to a walking skeleton, did not reach. `#113` and `#118` will touch parts of this surface as they build `:id` parsing and boot time shadowing on top of `PathPattern` and `RouteTable`, and that contact is the closest thing to a review this code will get without a ticket that names the task directly. Until one exists, treat this paragraph as the debt itself: the code is shipped, tested, and unassigned to any ticket now open to look at it again.

The cost is honest, not hidden: this code went through #107's review, which was scoped to a walking skeleton, not to a WebSocket protocol, a path grammar, a route generator's conventions, or an HTML DSL. Anyone auditing #107 in isolation will find scope its own text does not mention; this ADR is the pointer from that diff to the tickets that actually decided it, and, since this correction, to the fact that those tickets are now closed with the deeper review they were meant to carry out not picked up anywhere else.
