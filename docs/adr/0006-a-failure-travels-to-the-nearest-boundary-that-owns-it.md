# A failure travels to the nearest boundary that owns it

**Status:** accepted

A failure travels to the nearest boundary that owns it, and a boundary owns the failures it names. This extends [ADR 0001](0001-http-errors-live-in-http-and-carry-no-status.md) and does not supersede it: the sealed set, its home in `modules/http` and the missing status field stay exactly as 0001 fixed them. What 0001 left unsaid is which failures belong in that set, what everything else travels as, and where each kind stops.

There are two channels. A **refusal** is a failure the caller is expected to handle: the request cannot be honoured and the client or the caller is at fault, as with a missing row, a stale CSRF token, a foreign owner or a body too large. It is one of the sealed `EezoException` set in `http` (`BadRequest`, `NotFound`, `MethodNotAllowed`, `Forbidden`, `PayloadTooLarge`, `NotImplemented`), thrown where it is detected, and it carries no status. `InternalServerError` is in the set too, but it is the request boundary's own wrapper for everything that is not a refusal, not something a handler throws. A **defect** is a failure that means the application is built wrong: a guard asked on an unguarded route, a session too large for a cookie. It is a plain `IllegalStateException`, or a `require`, whose message names the mistake and the fix, because nobody can handle it where it is raised: the fix is a code change. A defect found while the application starts, such as a resource mounted twice or an `Owned` model on a store that cannot narrow, is thrown while the route table is built and stops the boot instead of reaching a boundary. An environment failure, a database or a socket gone, travels the same way as a defect.

There are three boundaries, each answering in its own vocabulary.

* **The request boundary** is `Boundary.resolve`, reached from `EezoHandler.handle`, where the parse, the route and the frame each answer a failure through `answer`, and from the WebSocket creator for a refused upgrade. It is last and names everything. A refusal gets the status its exhaustive match gives it. Anything else is offered to the application's `problems` hook, and what the hook does not cover becomes a 500 through `InternalServerError`, logged at ERROR with its stack trace, its message shown to the client only when `dev` is true.
* **The savepoint boundary** is `attempt[E]` in `io.eezo.db.Scopes`, and it owns only the failure its caller names. On a non fatal failure it rolls the savepoint back, hands an `E` back as a `Left`, and lets everything else travel on to the enclosing `transact`, which rolls the whole transaction back. If the savepoint rollback itself fails, it owns nothing and the body's failure travels on. `attempt` with no type, `attempt[Throwable]` and `attempt[Nothing]` do not compile, because none of them is a choice the caller made.
* **The socket boundary** answers a mounted live page once the request is gone. In `Live.scala`, a refusal found after the socket opens is answered in one of two ways. `onOpen` refuses the socket itself by closing it with a 44xx code: 4403 for an origin not allowed or a user who is not the page's, 4404 for an unknown page, 4409 for a page already connected. `onText` answers a malformed frame with an error frame carrying the problem and a WARNING line. `onText` answers an event that throws an `Exception`, a defect, with a generic error frame (`event '<name>' failed`) and an ERROR line carrying the stack trace. A dead connection is closed or detached: `onError` detaches it and starts its grace window, and a send that fails closes it. The mount runs before the socket exists and uses the request boundary, and so do the refusals raised while the upgrade is built: a guard's `Forbidden`, or an upgrade matching no `Route.Ws`, which the WebSocket creator answers as a 404.

## Considered options

The research behind this choice is on [issue #216](https://github.com/Eezo-framework/eezo/issues/216) and in [`docs/research/error-conventions-in-scala-3.md`](../research/error-conventions-in-scala-3.md). It found that no surveyed Scala 3 library or framework uses `Either` at every seam, and that every one of them keeps exceptions for defects.

**Sealed exceptions, kept.** The set 0001 fixed carries refusals already, and the derived handlers already throw `NotFound` and `Forbidden` from it. Kept because it is the smaller change: no handler signature moves, no derived code is rewritten, and the one exhaustive match stays the only place a status is decided. The direct style libraries the research read (Ox, Yaes, Kyo) short circuit a logical error with a thrown, stack trace free exception caught at an enclosing block, so a thrown refusal is not a departure from them, only an untyped one.

**`Either` at the handler edge.** A handler returning `Either[EezoException, Response]`, or a derived one returning it on eezo's behalf. Rejected because every handler, derived and handwritten, would change its signature for a failure only some of them can have, while a defect would still need the thrown channel: all six web frameworks surveyed answer an uncaught exception as a logged 500, including the two with a typed error channel. eezo would then run two refusal channels side by side, a `Left` and a thrown `EezoException` from code a handler calls.

**A `Refuse` capability over `boundary/break`.** The shape of Ox's `either:`, Yaes's `Raise[E]` and Kyo's `Abort[E]`: a handler that may refuse asks for a capability, a refusal breaks out to a boundary around the handler, and the type says which handlers can refuse. It was the recommended alternative, on the condition of a compiled spike. Deferred rather than rejected: its short circuit is a thrown `RuntimeException` like the sealed set's, so it changes what a signature says, not how a failure travels, and it can be laid over the same sealed set later without moving a boundary. The smaller change was chosen first.

## Consequences

`attempt[E]` is the only failure a persistence or boundary seam hands back as an `Either`. The `Store[A]` seam answers a missing row with `None` or `false`, `db`'s writes answer with a count, and a handler answers with a `Response` or a thrown refusal. `Form`'s `Either[FormErrors, A]`, returned by `Form.parse` and `request.as[A]`, and `Field.read`'s `Either[String, X]` are not a failure channel: they are decoded input that the handler answers itself, by rendering the form again with its errors, and nothing in them travels to a boundary. A second `Either` that carries a failure towards a boundary would be a second refusal channel and needs its own record.

`NoSuchRow` is gone, removed on [issue #217](https://github.com/Eezo-framework/eezo/issues/217). `Crud.updateById` and `delete` return the matched count like `deleteWhere` and `deleteAll`, and `JdbcStore` compares it to one. A write that matched no row is an answer, not a failure; the only persistence layer in the survey that threw on one was eezo's. `attempt` was narrowed on [issue #218](https://github.com/Eezo-framework/eezo/issues/218) from `Either[Throwable, A]`, which swallowed defects and guard refusals, to the `attempt[E]` described above.

Live produces no `EezoException`, on purpose: a socket has no status to give, so its refusals are close codes (4403, 4404, 4409) when the socket opens and error frames once it is attached. An `EezoException` thrown from a live event handler is answered like any other throw there, with the generic error frame and a log line.

The `require` on the session cookie size, in `SessionCookie.encode`, is a defect. It runs inside the request boundary's `try`, so it reaches the browser as a 500, writes no cookie, and its message, which says to store a key in the session and the data elsewhere, reaches the log and the dev page. The bare `IllegalStateException` sites and `db`'s named subclasses of it, `EscapedScope`, `OffThread` and `ReentrantScope`, are the defect shape and stay as they are.

The `problems` hook stays for an application's own exceptions, tried after eezo's set and before the 500 fallback, as 0001 said. It is where an application answers a 409 or a 422 that eezo does not model.
