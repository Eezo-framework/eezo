# Error conventions in Scala 3 libraries: what carries a logical error

Research for ticket [#216](https://github.com/Eezo-framework/eezo/issues/216), an input to [#197](https://github.com/Eezo-framework/eezo/issues/197), part of map [#193](https://github.com/Eezo-framework/eezo/issues/193). Checked on 2026-09-22. Primary sources only: every claim links to the repository, reference page or first party documentation that owns it. Quotes are verbatim from the page cited. This document takes no decision.

## The question

How do Scala 3 libraries and web frameworks carry a logical error, and does any of them do it with `Either` at every seam?

Three words are used throughout, in the sense the ticket gave them. A **logical error** is a refusal the domain anticipates: not found, forbidden, validation failed. A **defect** is a programmer mistake: a broken invariant, a route table that forgot a guard. An **environment failure** is the world going away: a socket closed, a database down, a timeout.

## Short answer

1. **No surveyed library or framework uses `Either` at every seam.** The ones that use `Either` at all use it for the logical error only, and every one of them keeps exceptions for defects. Ox states this as a rule; Kyo encodes it as `Failure` versus `Panic`; Yaes and Arrow let exceptions pass through untouched unless the user wraps them; the Scala 3 reference page on `CanThrow` says the erased capability exists to avoid an error monad.
2. **The direct style libraries hide the `Either` behind a capability or a boundary.** Ox's `either:` and `.ok()`, Yaes's `Raise[E]`, Kyo's `Abort[E]` and the standard library's `boundary`/`break` all short circuit by throwing a stack trace free exception and catching it at the enclosing block. The `Either` appears only at the edge where the block is run.
3. **Every web framework says 404 or 403 with a plain response value.** Five of six also offer a second channel: a thrown exception mapped by a partial function (Sharaf, http4s, Play, Cask) or a typed error channel (tapir's `Left(e)`, ZIO HTTP's `ZIO[R, Response, Response]`). Decoder failures are a value in http4s, tapir, Play and Cask and an exception in Sharaf and ZIO HTTP. An uncaught exception is a logged 500 in all six.
4. **Every persistence layer reports a zero row update as a count, not a failure.** `Int` in Magnum's fragments, Doobie, Slick, Anorm and ScalikeJDBC; `Completion.Update(0)` in Skunk; `Unit` with the count discarded in Magnum's derived `Repo`. Selecting one row that is not there is an `Option` in all six, and `unique`/`head`/`single` throws in the four that offer it. Driver failures are the raw `SQLException` in five of six.
5. **Derivation libraries split evenly.** circe, tapir codecs and Chimney's partial transformers return a value; Magnum's macro generated `Repo` and upickle's derived readers throw. The one place a framework converted user code from throwing to returning is tapir's `serverLogicRecoverErrors`, which exists so that a user may throw an `E <: Throwable` and still get the typed error output.
6. **Rust and Kotlin name the same two buckets and refuse to merge them.** Rust: `Result` for "anticipated runtime failure" and `panic!` for "a bug that has been detected in your program". Kotlin's `Result` KEEP says a throw based typed result was abandoned because "there would be no way to distinguish" a domain error from "the logic error in the code (a crash)". Arrow's `Raise` is a thrown `CancellationException` subclass unwrapped only by the scope that owns it.

The last section states what these facts imply for a framework whose handlers are derived, and cites. It recommends nothing.

## eezo's side of the seam

Read from the repository at `4156da4`, Scala 3.8.4 (`project/Toolchain.scala`).

* `modules/http/src/main/scala/io/eezo/http/Errors.scala`: `sealed abstract class EezoException(message: String) extends RuntimeException(message)` with seven cases, `BadRequest`, `NotFound`, `MethodNotAllowed`, `Forbidden`, `PayloadTooLarge`, `NotImplemented`, `InternalServerError`. None carries a status. ADR 0001 records why the set is sealed, lives in `http` rather than `core`, and is mapped once by an exhaustive match at the boundary, with `Eezo.run(..., problems: PartialFunction[Throwable, Problem])` as the user's hook, tried after eezo's set and before the fallback to 500 (`docs/adr/0001-http-errors-live-in-http-and-carry-no-status.md`).
* `modules/core/src/main/scala/io/eezo/core/Store.scala`: the seam the derivation speaks. `find` returns `Option[A]`, `update` and `delete` return `Boolean`, `insert` returns `Unit`. The trait's comment: "Nothing here throws. A missing row is a `false` or a `None`, which `Resource` turns into a 404; an implementation that raised would be deciding an HTTP status one layer below the layer that knows what HTTP is."
* `modules/http/src/main/scala/io/eezo/http/Resource.scala`: the derived handlers are where a `None` or a `false` becomes a thrown `NotFound(request.path)` (line 367) and a foreign row a thrown `Forbidden` (line 366). Programmer mistakes in the same file throw `IllegalStateException` (lines 247, 262, 293, 329).
* `modules/db/src/main/scala/io/eezo/db/Crud.scala`: `final case class NoSuchRow(msg: String) extends RuntimeException(msg)`, "An `update` or `delete` that matched no row." `JdbcStore.scala` lines 99 to 109 catch it and return `false`, with the comment "`NoSuchRow` becomes `false` here, and nowhere else."
* `modules/db/src/main/scala/io/eezo/db/Scopes.scala` line 48: `def attempt[A](body: Tx ?-> A)(using tx: Tx): Either[Throwable, A]`, a savepoint sub unit that catches `NonFatal` and returns `Left`. Issue [#197](https://github.com/Eezo-framework/eezo/issues/197) notes it is the only `Either` signature in the framework.
* `modules/db/src/main/scala/io/eezo/db/capability/Capability.scala`: `EscapedScope` and `OffThread` extend `IllegalStateException`; `SchemaError` is a plain case class.
* `modules/auth/src/main/scala/io/eezo/auth/Guard.scala` line 86: `Guard.current` outside a guarded route throws `IllegalStateException`; the comment says it is "not one of eezo's HTTP failures, because the mistake" is the programmer's.

So today eezo already runs three shapes side by side: exceptions for refusals that reach HTTP (`EezoException`), `Option` and `Boolean` at the `Store[A]` seam, and `IllegalStateException` for defects. What [#197](https://github.com/Eezo-framework/eezo/issues/197) asks is which of those is the rule and which the outlier. The rest of this document is what the ecosystem does with the same three cases.

## 1. Direct style libraries

### Ox (softwaremill/ox)

Ox is the one library in the survey that writes the rule down. From its [Error handling](https://ox.softwaremill.com/latest/basics/error-handling.html) page, verbatim:

> In Ox, we propose distinguishing two kinds of errors:
>
> unrecoverable errors: bugs, catastrophic failures (e.g. out of memory) and conditions which require the current "processing unit" to be terminated. This might be handling of the current HTTP request (and returning a 500), handling of an incoming MQ message, or simply exiting a CLI. These are untyped **on purpose**, and signalled using exceptions. That way, implementing control flow based on the specific error type is discouraged.
>
> recoverable/"expected" errors: anticipated failures, where the code can take specific corrective action based on the error's details. These are fully typed, represented as values

and the sentence ends by naming the values: `Either`s, "or as part of a custom data type."

* **Logical error:** a value, "e.g. the left side of an `Either[MyError, MyResult]`. They are not thrown, but returned from the computations which are orchestrated by Ox." Ox's own combinators recognise such values only through an `ErrorMode`: "Provided implementations include `EitherMode[E]` (where left sides of `Either`s are used to represent errors), and `UnionMode[E]`, where a union type of `E` and a successful value is used. Arbitrary user-provided implementations are possible as well." ([Error handling](https://ox.softwaremill.com/latest/basics/error-handling.html); [ErrorMode.scala](https://raw.githubusercontent.com/softwaremill/ox/master/core/src/main/scala/ox/ErrorMode.scala), whose scaladoc reads "An application error is a value which is returned as a successful completion of a fork. However, unlike regular values, such error values are reported and cause the enclosing scope to end.")
* **Defect:** an exception, untyped on purpose (quote above). "The general rule for computation combinators is that using them should throw exactly the same exceptions, as if the provided code was executed without them. That is, no additional exceptions might be thrown, and no exceptions are swallowed." A failing supervised fork ends the scope, interrupts its siblings and rethrows ([Error handling in scopes](https://ox.softwaremill.com/latest/structured-concurrency/error-handling-scopes.html)).
* **Environment failure:** an exception at the source, converted to a value only where recovery is meaningful. The page is explicit about the cost: "Representing recoverable errors as values might incur a syntax overhead, and might be less convenient in some cases. Moreover, all I/O libraries typically throw exceptions", so to use them as values "one would need to provide a wrapper which converts such exceptions to values, at the boundary where recovery becomes meaningful." And: "An error which is unrecoverable at one level might become recoverable when caught at a higher level", but "only with the context that is accessible at the catch point."
* **`either:` blocks:** "To streamline working with `Either` values, Ox provides a specialised version of the boundary/break mechanism. Within a code block passed to `either`, it allows "unwrapping" `Either`s using `.ok()`. ... In case a failure is encountered (a left side of an `Either`), the computation is short-circuited, and the failure becomes the result." The source imports `scala.util.boundary`; `apply` is `boundary(Right(body))` and `.ok()` does `case Left(e) => break(Left(e))` ([either.scala](https://raw.githubusercontent.com/softwaremill/ox/master/core/src/main/scala/ox/either.scala)). Nesting is refused: "Either blocks cannot be nested in the same scope to prevent surprising failures after refactors."
* **Bridging:** `.catching[E]` converts a throwing expression to an `Either` and "catches only non-fatal exceptions!"; `.orThrow` goes the other way. Ox's own streams and channels throw: "any exceptions that occur when evaluating the flow's logic will be thrown when running the flow" ([flows.md](https://raw.githubusercontent.com/softwaremill/ox/master/doc/streaming/flows.md)); `Sink.send` and `Source.receive` "will throw a `ChannelClosedException`" with `sendSafe`/`receiveSafe` returning a union type instead ([channels.md](https://raw.githubusercontent.com/softwaremill/ox/master/doc/streaming/channels.md)).
* **Keeps exceptions for defects:** yes, as the stated rule.

### Gears (lampepfl/gears)

* "An Experimental Asynchronous Programming Library for Scala 3" ([README](https://github.com/lampepfl/gears)).
* `trait Future[+T] extends Async.OriginalSource[Try[T]], Cancellable`; `Future.apply` "wraps its execution in a [[scala.util.Try]]"; `await` on a `Try` source is `awaitResult.get`, so a `Failure` rethrows. The scaladoc states the style: "Idiomatic Gears code should ''never'' return active futures. Should a function be async (i.e. takes an [[Async]] context parameter), they should return values or throw exceptions directly." ([futures.scala](https://raw.githubusercontent.com/lampepfl/gears/main/shared/src/main/scala/async/futures.scala))
* **Logical error:** nothing dedicated; the user returns a value. The one typed helper is an `await` on a `Source[Either[E, T]]` that calls `.right.get`.
* **Defect and environment failure:** the same shape, an exception stored as `Failure` and rethrown by `.await`; cancellation is `CancellationException`.
* **Keeps exceptions for defects:** yes; there is no other channel.

### Yaes (rcardin/yaes)

* "The `Raise[E]` type describes the possibility that a function can raise an error of type `E`. `E` can be a logic typed error or an exception." Signature form: `def divide(a: Int, b: Int)(using Raise[DivisionByZero]): Int`, or with the infix alias `def divide(a: Int, b: Int): Int raises DivisionByZero`. The README's stance: "λÆS embraces direct style: no monads, no for-comprehensions, just plain Scala" ([README](https://raw.githubusercontent.com/rcardin/yaes/main/README.md)).
* **Implementation:** `type Raise[E] = Raise.Unsafe[E]`; `infix type raises[A, Error] = Raise[Error] ?=> A`. The single handler is `fold`, which is a `boundary` whose given `Raise[E]` does `def raise(error: => E): Nothing = break(onError(error))`. Every other handler is `fold`: `run` gives `A | E`, `either` gives `Either[E, A]`, `option`, `nullable`, `recover`, `withDefault` ([Raise.scala](https://raw.githubusercontent.com/rcardin/yaes/main/yaes-core/src/main/scala/io/yaes/Raise.scala)).
* **Logical error:** `Raise.raise(e)` for any `E`, converted to a value only at the handler.
* **Defect:** a thrown exception passes through untouched. Both `Raise.catching` overloads catch `NonFatal` only and rethrow everything else; the scaladoc reads "Catches an exception and raises an error of type `E`. For other exceptions, the exception is rethrown."
* **Environment failure:** the library's own I/O effects declare the exception type as the error, `Input.readLn()` requires `Raise[IOException]` and `System.env[Int]` requires `Raise[NumberFormatException]`; foreign code is bridged with `catching`. `Raise.rethrowError: Raise[Throwable]` exists "when integrating with exception-based effect systems, such as Cats Effect."
* **Keeps exceptions for defects:** yes by default; nothing is caught unless asked.

### Kyo (getkyo/kyo)

* The `Abort` scaladoc names three outcomes: "`Success[A]`: The computation completes successfully with a value of type A"; "`Failure[E]`: An expected business/domain failure with a meaningful error value of type E"; "`Panic(ex: Throwable)`: An unexpected exception, similar to unchecked exceptions". And: "Abort is designed for modeling domain-specific errors as values rather than exceptions" ([Abort.scala](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-prelude/shared/src/main/scala/kyo/Abort.scala)).
* `Result` "combines the features of `Either` (for expected errors) and `Try` (for unexpected exceptions) into a single type"; `opaque type Result[+E, +A] >: Success[A] | Error[E]` with `Failure[+E]` and `Panic(exception: Throwable)` both under `Error[E]` ([Result.scala](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-data/shared/src/main/scala/kyo/Result.scala)). The kyo-data README: "Like `Either`, `Result` carries an error type parameter; unlike `Either`, it distinguishes expected failures (`Failure[E]`) from unexpected exceptions (`Panic`). Both are subtypes of `Error[E]`, so handlers can target either layer." ([kyo-data README](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-data/README.md))
* **Logical error:** `Abort.fail(e)`, `E` any type including unions and literal singletons. "The error type `E` can be anything (a sealed `enum`, a `String`, a `Throwable`)." ([kyo-prelude README](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-prelude/README.md))
* **Defect:** `Panic`. Any non fatal throw under `Abort.run[E]` becomes `Result.Panic` unless `E` is itself a matching `Throwable` type (`Abort.runWith` on `ArrowEffect.handleCatching`, Abort.scala lines 190 to 227). "The three handlers differ in how they treat `Panic`: `run` returns it as part of `Result`, `recover` leaves it unhandled in `Abort[Nothing]`, and the `OrThrow` variants rethrow it."
* **Environment failure:** typed for Kyo's own primitives, "Three error types appear in `Abort` rows across the module: `Closed` ... `Interrupted` ... `Timeout`" ([kyo-core README](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-core/README.md)); foreign exceptions are `Panic` unless `Abort.catching[E]` names them.
* **Style note:** "The recommended way to write Kyo code is the monadic style ... Direct style is an alternative, not the default." ([README](https://raw.githubusercontent.com/getkyo/kyo/main/README.md)). In the `direct` macro "the block's return type stays `A` and the effect row `S` is inferred from the `.now` sites inside" ([kyo-direct README](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-direct/README.md)).
* **Keeps exceptions for defects:** yes, as `Panic` values, rethrown only at an `OrThrow` handler or the application boundary.

### `scala.util.boundary` and `break` (Scala 3.3.0)

The primitive under Ox's `either:` and Yaes's `Raise`. From the library source ([boundary.scala](https://raw.githubusercontent.com/scala/scala3/main/library/src/scala/util/boundary.scala)):

* "Integration with exceptions. `break`s are logically non-fatal exceptions. The `Break` exception class extends `RuntimeException` and is optimized so that stack trace generation is suppressed." The class is constructed with `enableSuppression = false, writableStackTrace = false`.
* "Better performance: breaks to enclosing scopes in the same method can be rewritten to jumps." The PR that shipped it says "there is a new MiniPhase `DropBreaks` that rewrites local breaks to labeled returns, i.e. jumps" and "The abstractions are not experimental." ([scala/scala3#16612](https://github.com/scala/scala3/pull/16612)); the 3.3.0 release lists "Introduce boundary/break control abstraction. #16612" ([3.3.0 release](https://github.com/scala/scala3/releases/tag/3.3.0)).
* `def break[T](value: T)(using label: Label[T]): Nothing = throw Break(label, value)`; `boundary.apply` catches `Break` and returns its value only `if ex.isSameLabelAs(local)`, otherwise rethrows.
* Because `Break` is a `RuntimeException`, a `catch case NonFatal(e)` between a `break` and its `boundary` intercepts it. The scaladoc does not warn about this; it follows from the class hierarchy.
* Odersky's own words on `Either`, in the strawman PR that preceded `boundary`: "`Result` will hopefully replace `Either`, which is in my opinion an abomination for error handling." and "Exceptions should only be used if the failure case is very unlikely (rule of thumb: in less than 0.1% of cases)." ([scala/scala3#16550](https://github.com/scala/scala3/pull/16550))

### Experimental `CanThrow` and `saferExceptions`

From the [Scala 3 reference](https://docs.scala-lang.org/scala3/reference/experimental/canthrow.html):

* Status: "This page describes experimental support for exception checking in Scala 3. It is enabled by the language import `import language.experimental.saferExceptions`" and "The reason for publishing this extension now is to get feedback on its usability." It is still under `object experimental` in `language.scala` at 3.9.0 and 3.10.0-RC2 ([language.scala at 3.9.0](https://raw.githubusercontent.com/scala/scala3/3.9.0/library/src/scala/runtime/stdLibPatches/language.scala)).
* Why not an error monad, verbatim: "So the dilemma is that exceptions are easy to use only as long as we forget static type checking. This has caused many people working with Scala to abandon exceptions altogether and to use an error monad like `Either` instead. This can work in many situations but is not without its downsides either. It makes code a lot more complicated and harder to refactor. It means one is quickly confronted with the problem how to work with several monads." The page does not contain the phrase "Either is not the answer".
* The capability: `erased class CanThrow[-E <: Exception]`, "compile-time only artifacts; they do not have a runtime footprint." `infix type $throws[R, +E <: Exception] = CanThrow[E] ?=> R`, so `def m(x: T): U throws E` is `def m(x: T)(using CanThrow[E]): U`. A `try` generates "an accumulated capability of type `CanThrow[Ex1 | ... | Ex2]` that is available as a given in the scope of `body`".
* Signatures untouched: "The signature of `map` does not have to account for effects. It takes a closure as always, but that closure may refer to capabilities in its free variables. This means that `map` is already effect polymorphic even though we did not change its signature at all."
* Scope: "The `saferExceptions` feature is designed to work only with checked exceptions", where "An exception type is _checked_ if it is a subtype of `Exception` but not of `RuntimeException`." So a `RuntimeException`, which is what `EezoException` extends, is outside the feature.
* Caveat, which is about escape not `Try` or `Future` (neither word appears on the page): "What's missing is that `try` should enforce that the capabilities it generates do not escape as free variables in the result of its body." and "a `try` always has to be placed in the same computation stage as the throws that it enables."
* The same argument in the paper: "This has caused many Scala developers to abandon exceptions altogether and to use monads [Wadler 1998] instead, specifically an error monad like Try or Either. This approach can often work but is not without its downsides either. It makes code more complicated and harder to refactor." ([Safer Exceptions for Scala, SCALA '21](https://infoscience.epfl.ch/server/api/core/bitstreams/38409509-638b-489b-af7c-869c70cf7e5a/content))

## 2. Web frameworks

### http4s

* `type HttpRoutes[F[_]] = Http[OptionT[F, *], F]` where `type Http[F[_], G[_]] = Kleisli[F, Request[G], Response[G]]` ([package.scala](https://raw.githubusercontent.com/http4s/http4s/main/core/shared/src/main/scala/org/http4s/package.scala)).
* **404 or 403:** a plain value. `NotFound()` and `Forbidden()` are `EntityResponseGenerator`s returning `F[Response[G]]` ([Responses.scala](https://raw.githubusercontent.com/http4s/http4s/main/dsl/src/main/scala/org/http4s/dsl/impl/Responses.scala)). "Route did not match" is a separate channel, `OptionT` `None`, collapsed by `orNotFound` to `Response.notFound` ([KleisliSyntax.scala](https://raw.githubusercontent.com/http4s/http4s/main/core/shared/src/main/scala/org/http4s/syntax/KleisliSyntax.scala)).
* **Uncaught exception:** `type ServiceErrorHandler[F[_]] = Request[F] => PartialFunction[Throwable, F[Response[F]]]`; the default logs a `MessageFailure` at debug and renders it, and logs any other `Throwable` at error and returns a 500 ([server/package.scala](https://raw.githubusercontent.com/http4s/http4s/main/server/shared/src/main/scala/org/http4s/server/package.scala)). The docs: on an exception "it returns a `500` response code", and the section on customising error handling is marked "TODO" ([Error handling](https://http4s.org/v0.23/docs/error-handling.html)).
* **Decoder failure:** `type DecodeResult[F[_], A] = EitherT[F, DecodeFailure, A]`; `attemptAs` keeps the `EitherT`, `as[A]` does `F.rethrow(attemptAs.value)`, so the value becomes an exception in `F` ([Media.scala](https://raw.githubusercontent.com/http4s/http4s/main/core/shared/src/main/scala/org/http4s/Media.scala)). `MessageFailure` carries its own rendering: `ParseFailure` is 400, `InvalidMessageBodyFailure` is 422, `MediaTypeMismatch` is 415 ([MessageFailure.scala](https://raw.githubusercontent.com/http4s/http4s/main/core/shared/src/main/scala/org/http4s/MessageFailure.scala)).
* **Extensible:** yes, through the `ServiceErrorHandler`, `ErrorHandling` middleware, `MessageFailure` subclasses and `AuthMiddleware` `onFailure` routes ([Authentication](https://http4s.org/v0.23/docs/auth.html)).

### tapir

* "You can think of an endpoint as a function which takes input parameters of type A and I and returns a result of type Either[E, O]." ([Basics](https://tapir.softwaremill.com/en/latest/endpoint/basics.html))
* **404 or 403:** `Left(e)` where `E` is the endpoint's `errorOut`. `def serverLogic[F[_]](f: I => F[Either[E, O]])` ([Endpoint.scala](https://raw.githubusercontent.com/softwaremill/tapir/master/core/src/main/scala/sttp/tapir/Endpoint.scala)). Statuses come from `oneOf` variants: "All possible outputs must have a common supertype. Typically, the supertype is a sealed trait, and the variants are implementing case classes." and "Error outputs can be extended with new variants" ([oneOf](https://tapir.softwaremill.com/en/latest/endpoint/oneof.html)). Default: "successful responses are returned with the `200 OK` status code, and errors with `400 Bad Request`" ([Server logic](https://tapir.softwaremill.com/en/latest/server/logic.html)).
* **The escape hatch from `Either`:** `serverLogicRecoverErrors(f: I => F[O])`: "If your `E` error type is an exception (extends `Throwable`), and if errors that occur in the server logic are represented as failed effects, you can use a variant of the methods above, which extract the error from the failed effect, and respond with the error output appropriately." Its signature requires `E <:< Throwable` and a `ClassTag[E]`. Also `serverLogicSuccess`, `serverLogicError`, `serverLogicOption` ("if the error type is a `Unit`, a `None` results is treated as an error") and `serverLogicPure` ([Server logic](https://tapir.softwaremill.com/en/latest/server/logic.html)).
* **Uncaught exception:** "By default, an `ERROR` will be logged, and an `500 InternalServerError` returned." ([Error handling](https://tapir.softwaremill.com/en/latest/server/errors.html)); `DefaultExceptionHandler` maps two of its own exceptions to 413 and 400 and everything else to 500 ([ExceptionHandler.scala](https://raw.githubusercontent.com/softwaremill/tapir/master/server/core/src/main/scala/sttp/tapir/server/interceptor/exception/ExceptionHandler.scala)).
* **Decoder failure:** a value, `DecodeResult` with `Value`, `Missing`, `Multiple`, `Error(original, error: Throwable)`, `Mismatch`, `InvalidValue` ([DecodeResult.scala](https://raw.githubusercontent.com/softwaremill/tapir/master/core/src/main/scala/sttp/tapir/DecodeResult.scala)); `DefaultDecodeFailureHandler` answers 400 for query, header, body and path capture, 401 for an auth input, and "no match" for a method or path mismatch so the next endpoint is tried ([DecodeFailureHandler.scala](https://raw.githubusercontent.com/softwaremill/tapir/master/server/core/src/main/scala/sttp/tapir/server/interceptor/decodefailure/DecodeFailureHandler.scala)).
* **Extensible:** yes, three layers: typed `errorOut` per endpoint, swappable `DecodeFailureHandler`, `ExceptionHandler` and `RejectHandler`, and `serverLogicRecoverErrors`.

### Play Framework

* An action is "a `(play.api.mvc.Request => play.api.mvc.Result)` function"; `val pageNotFound = NotFound(<h1>Page not found</h1>)`, `val anyStatus = Status(488)("Strange response type")` ([ScalaActions](https://www.playframework.com/documentation/3.0.x/ScalaActions)). `val NotFound = new Status(NOT_FOUND)`, `val Forbidden = new Status(FORBIDDEN)` ([Results.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/api/mvc/Results.scala)).
* **404 or 403:** a plain `Result`. In composition, `Either` appears: `trait ActionRefiner[-R[_], +P[_]] extends ActionFunction[R, P] { protected def refine[A](request: R[A]): Future[Either[Result, P[A]]] }` and `trait ActionFilter[R[_]] ... { protected def filter[A](request: R[A]): Future[Option[Result]] }` ([Action.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/api/mvc/Action.scala)); the docs return `Left(NotFound)` from a refiner and `Some(Forbidden)` from a filter ([ScalaActionsComposition](https://www.playframework.com/documentation/3.0.x/ScalaActionsComposition)). The `Left` is a `Result`, the response itself, not a domain error.
* **Uncaught exception:** `HttpErrorHandler.onServerError(request, exception): Future[Result]`, logged and rendered as a 500 with a dev or prod page; `onClientError(request, statusCode, message)` for the 4xx series ([HttpErrorHandler.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/api/http/HttpErrorHandler.scala); [ScalaErrorHandling](https://www.playframework.com/documentation/3.0.x/ScalaErrorHandling)).
* **Decoder failure:** binders return `Either[String, A]` ([ScalaRequestBinders](https://www.playframework.com/documentation/3.0.x/ScalaRequestBinders)); the generated router folds a `Left` into `errorHandler.onClientError(request, BAD_REQUEST, error)` ([GeneratedRouter.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/core/routing/GeneratedRouter.scala)); forms use `bindFromRequest().fold(formWithErrors => BadRequest(...), userData => ...)` ([ScalaForms](https://www.playframework.com/documentation/3.0.x/ScalaForms)).
* **Extensible:** yes, a custom `HttpErrorHandler`, refiners and filters, bindables, and `Status(n)`.

### Cask

* `case class Response[+T](data: T, statusCode: Int, headers: Seq[(String, String)], cookies: Seq[Cookie])`; `object Abort { def apply(code: Int) = Response("", code, Nil, Nil) }` ([Response.scala](https://raw.githubusercontent.com/com-lihaoyi/cask/master/cask/src/cask/model/Response.scala)). Docs: `cask.Response("content here", statusCode = 404)` and `cask.Abort(401)` ([Cask docs](https://com-lihaoyi.github.io/cask/)).

Returning a `Left` lets you bail out early with a fixed `cask.Response`" ([Cask docs](https://com-lihaoyi.github.io/cask/)), plus overridable `handleEndpointError`, `handleNotFound`, `handleMethodNotAllowed`.

### Sharaf

The ticket describes Sharaf as Ox based. ## 4. The cost of `Either` in derived code

The ticket asked for documented experience of typed errors in code the user does not write, and whether libraries hide the `Either` behind a capability to keep signatures untouched.

**What the language designers wrote.** The `CanThrow` reference page is the primary statement, quoted in full in section 1: an error monad "makes code a lot more complicated and harder to refactor" and confronts the writer with "the problem how to work with several monads". The same page explains the choice of a capability precisely by the signatures it leaves alone: "capabilities can be expressed as parameters whereas traditionally effects are expressed as some addition to result values. It turns out that this can make a big difference!" and "we'd have to parameterize _every method_ that takes a function argument that way, so the added overhead of declaring all these exception types looks just like a sort of ceremony we would like to avoid." ([CanThrow](https://docs.scala-lang.org/scala3/reference/experimental/canthrow.html)). The strawman PR that became `boundary`/`break` puts the same point in operational terms: "Exceptions propagate silently until they are handled in a `catch`. All other failure modes require either ad-hoc code or monadic lifting into for comprehensions to propagate." ([scala/scala3#16550](https://github.com/scala/scala3/pull/16550)).

**What the libraries did with it.** Every direct style library in section 1 that offers typed errors implements them over `boundary`/`break`, that is, over a stack trace free `RuntimeException`, and exposes the `Either` only at the handler: Ox's `either:` is `boundary(Right(body))` ([either.scala](https://raw.githubusercontent.com/softwaremill/ox/master/core/src/main/scala/ox/either.scala)); Yaes's `fold` is a `boundary` whose `raise` is `break(onError(error))`, and `Raise.either`, `Raise.run` and `Raise.option` are folds ([Raise.scala](https://raw.githubusercontent.com/rcardin/yaes/main/yaes-core/src/main/scala/io/yaes/Raise.scala)); Arrow's `either { }` is `fold(block, { Either.Left(it) }, { Either.Right(it) })` over a thrown `RaiseCancellationException` ([Builders.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/commonMain/kotlin/arrow/core/raise/Builders.kt); [Fold.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/commonMain/kotlin/arrow/core/raise/Fold.kt)). Ox's page states why the block exists, "To streamline working with `Either` values", and Arrow's migration page states what it removes: "you don't need to use any function to compose computations, you use regular Kotlin idioms" and it "avoids wrapping and unwrapping `Right` and `Left` values." ([From Either to Raise](https://arrow-kt.io/learn/typed-errors/from-either-to-raise/)). Kyo keeps the error in the type, `A < Abort[E]`, but its `direct` macro infers the row: "the block's return type stays `A` and the effect row `S` is inferred from the `.now` sites inside" ([kyo-direct README](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-direct/README.md)).

**What a framework did when users would not return `Left`.** tapir's `serverLogic` takes `I => F[Either[E, O]]`, and tapir ships four alternatives that take something else: `serverLogicSuccess(f: I => F[O])`, `serverLogicError(f: I => F[E])`, `serverLogicOption(f: I => F[Option[O]])`, and `serverLogicRecoverErrors(f: I => F[O])`, which "extract the error from the failed effect" when `E <:< Throwable`, with the docs' example comments "note: no Right() wrapper" and "no Left() wrapper, a failed future" ([Server logic](https://tapir.softwaremill.com/en/latest/server/logic.html)). Play's composition `Either[Result, P[A]]` carries the response itself on the left, never a domain error ([Action.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/api/mvc/Action.scala)).

**What derived code returns, library by library.**

## 5. Rust and Kotlin as references

**Rust.** The book opens the error chapter with the split: "Rust groups errors into two major categories: recoverable and unrecoverable errors. For a recoverable error, such as a file not found error, we most likely just want to report the problem to the user and retry the operation. Unrecoverable errors are always symptoms of bugs, such as trying to access a location beyond the end of an array, and so we want to immediately stop the program." and "Rust doesn't have exceptions. Instead, it has the type `Result<T, E>` for recoverable errors and the `panic!` macro that stops execution when the program encounters an unrecoverable error." ([ch09-00](https://doc.rust-lang.org/book/ch09-00-error-handling.html)). The guidance for which is which: "It's advisable to have your code panic when it's possible that your code could end up in a bad state. In this context, a bad state is when some assumption, guarantee, contract, or invariant has been broken", whereas "When expected failure occurs (like a parser being given malformed data or an HTTP request returning a rate limit status), it's more appropriate to return a `Result` than to make a `panic!` call." and "A contract violation always indicates a caller-side bug. Panicking when the contract is violated makes sense because it's not a kind of error you want the calling code to have to explicitly handle; the calling programmers need to fix the code." ([ch09-03](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)). The standard library says the same in its own voice: "The `panic!` macro is used to construct errors that represent a bug that has been detected in your program." while `Result` wraps "error types that represent an anticipated runtime failure mode of that computation" ([panic!](https://doc.rust-lang.org/std/macro.panic.html)); "The Rust language provides two complementary systems" and "The components of the first system, the panic runtime and interfaces, are most commonly used to represent bugs that have been detected in your program. The components of the second system, `Result`, the error traits, and user defined types, are used to represent anticipated runtime failure modes of your program." ([std::error](https://doc.rust-lang.org/std/error/index.html)). Catching the defect channel is discouraged in the API itself: `catch_unwind` "is not recommended to use this function for a general try/catch mechanism. The `Result` type is more appropriate to use for functions that can fail on a regular basis." ([catch_unwind](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html)). Propagation is `?`, which returns `Result::Err(From::from(e))` ([reference](https://doc.rust-lang.org/reference/expressions/operator-expr.html)), and the ecosystem splits error types by audience: "Use thiserror if you care about designing your own dedicated error type(s) so that the caller receives exactly the information that you choose in the event of failure. This most often applies to library-like code. Use Anyhow if you don't care what error type your functions return, you just want it to be easy. This is common in application-like code." ([thiserror README](https://github.com/dtolnay/thiserror)). Environment failures live in the `Result` bucket with an open kind: `std::io::ErrorKind` "is intended to grow over time and it is not recommended to exhaustively match against it" ([ErrorKind](https://doc.rust-lang.org/std/io/enum.ErrorKind.html)).

**Kotlin and Arrow.** "Kotlin treats all exceptions as _unchecked_ by default. Unchecked exceptions simplify the exception handling process: you can catch exceptions, but you don't need to explicitly handle or declare them." ([Exceptions](https://kotlinlang.org/docs/exceptions.html)); an older revision of the page gave the reason, "Kotlin does not have checked exceptions", with the `Appendable.append` example and Bruce Eckel's observation that "experience with large software projects suggests a different result", namely "decreased productivity and little or no increase in code quality" ([exceptions.md at aebf4e2](https://github.com/JetBrains/kotlin-web-site/blob/aebf4e24d5d70396bf9fee57a3fa8ea3f2eda861/docs/topics/exceptions.md)). The standard library's `Result` is deliberately not a domain error carrier: "The `Result` class is designed to capture generic failures of Kotlin functions for their latter processing and should be used in general-purpose API like futures, etc ... The `Result` class is not designed to represent domain-specific error conditions." The KEEP names the two buckets: "Exceptions in Kotlin are designed for the failures that usually do not require local handling at each call site. This includes several broad areas: logic and programming errors like index bounds problems and various checks for internal invariants and preconditions, environment problems, out of memory conditions, etc." while "if some API requires its callers to handle failures locally ... then it should use nullable types, when these failures do not carry additional business meaning, or domain-specific data types to represent its successful results and failures". I/O is called out as "a corner case" where "it is idiomatic in Kotlin to use exceptions (like `IOException`)". It rejected an `Either` in the standard library ("It increases verboseness without providing improvement for any of the outlined Use cases") and records why a throw based typed result was abandoned: "there would be no way to distinguish a domain-specific error that needs to be represented in the `Result` type for handling it by the caller from the logic error in the code (a crash) that shall still be represented as exception to be handled in a centralized place of the application" ([KEEP result.md](https://github.com/Kotlin/KEEP/blob/master/proposals/stdlib/result.md)). Arrow fills the gap the KEEP left to libraries. Its definition: "We use the term logical failure to describe a situation not deemed as successful in your domain, but that is still within the realms of that domain. For example, if you are implementing a repository for users, not finding a user for a certain query is a logical failure. In contrast to logical failures we have real exceptions, which are problems, usually technical, which are truly exceptional and are thus not part of our domain." Its rule: "Logical failures indicate problems within the domain, and those should be handled as part of the usual domain logic." and "Exceptions indicate problems which affect the system's ability to continue working. For example, if the database connection breaks this is something outside your domain logic." and "Unless you explicitly wrap your code to catch exceptions as part of `Either` or `Raise`, exceptions bubble up in the usual way." The shape is a receiver, `fun Raise<UserNotFound>.findUser(id: UserId): User`, or in the future a context parameter ([Working with typed errors](https://arrow-kt.io/learn/typed-errors/working-with-typed-errors/)); the Kotlin context parameters KEEP uses `Raise` as its worked example and files it under "As scopes" beside `CoroutineScope` and `Transaction` ([KEEP context-parameters.md](https://github.com/Kotlin/KEEP/blob/master/proposals/context-parameters.md)). Under the hood `raise` throws a `RaiseCancellationException`, a `CancellationException` subclass with `fillInStackTrace` overridden to an empty array and the comment "We don't need stacktrace on shift, it hurts performance", and `fold` unwraps it only when `this.raise === raise`, the scope that created it; any other throwable is rethrown or handed to an explicit `catch` that "automatically avoids capturing fatal exceptions" ([Fold.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/commonMain/kotlin/arrow/core/raise/Fold.kt); [CancellationExceptionNoTrace.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/androidAndJvmMain/kotlin/arrow/core/raise/CancellationExceptionNoTrace.kt)).

## What this means for a direct style framework with derived handlers

Facts only, each with its source. The decision is [#197](https://github.com/Eezo-framework/eezo/issues/197)'s.

1. **The convention the direct style ecosystem states is two channels, not one.** Ox writes it as a rule, exceptions for "bugs, catastrophic failures" and conditions that terminate the "processing unit", values for "anticipated failures, where the code can take specific corrective action" ([Ox error handling](https://ox.softwaremill.com/latest/basics/error-handling.html)). Kyo encodes it as `Failure[E]` beside `Panic(Throwable)` in one `Result` ([Result.scala](https://raw.githubusercontent.com/getkyo/kyo/main/kyo-data/shared/src/main/scala/kyo/Result.scala)). Yaes and Arrow leave exceptions alone unless the user wraps them, and both wrap `NonFatal` only ([Raise.scala](https://raw.githubusercontent.com/rcardin/yaes/main/yaes-core/src/main/scala/io/yaes/Raise.scala); [Working with typed errors](https://arrow-kt.io/learn/typed-errors/working-with-typed-errors/)). Rust and the Kotlin `Result` KEEP name the same two buckets, and the KEEP records that collapsing them into one throw based carrier was abandoned because it could not tell a domain error from a crash ([KEEP result.md](https://github.com/Kotlin/KEEP/blob/master/proposals/stdlib/result.md)). Ox names "handling of the current HTTP request (and returning a 500)" as the unit an unrecoverable error terminates; nothing in the survey names a 404 or a 403 as unrecoverable.

2. **"`Either` everywhere" is a shape no surveyed library has.** Where `Either` is used for a logical error it is a value at one edge: tapir's `serverLogic` ([Server logic](https://tapir.softwaremill.com/en/latest/server/logic.html)), Ox's `either:` result ([either.scala](https://raw.githubusercontent.com/softwaremill/ox/master/core/src/main/scala/ox/either.scala)), Yaes's `Raise.either` ([Raise.scala](https://raw.githubusercontent.com/rcardin/yaes/main/yaes-core/src/main/scala/io/yaes/Raise.scala)). Inside the block the signature carries a capability or nothing, and propagation is a thrown `Break` or `RaiseCancellationException` with the stack trace suppressed ([boundary.scala](https://raw.githubusercontent.com/scala/scala3/main/library/src/scala/util/boundary.scala); [CancellationExceptionNoTrace.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/androidAndJvmMain/kotlin/arrow/core/raise/CancellationExceptionNoTrace.kt)). The persistence layers do not return `Either` for a zero row update at all; they return a count, and Magnum's derived `Repo` discards even that ([PostgresDbType.scala](https://raw.githubusercontent.com/AugustNagro/magnum/master/magnum/src/main/scala/com/augustnagro/magnum/PostgresDbType.scala)).

3. **The language designers' stated reason for a capability is the signature it leaves alone, which is the derived handler's situation.** `CanThrow` is a context parameter rather than a result wrapper because "capabilities can be expressed as parameters whereas traditionally effects are expressed as some addition to result values", and a higher order function such as `map` "is already effect polymorphic even though we did not change its signature at all" ([CanThrow](https://docs.scala-lang.org/scala3/reference/experimental/canthrow.html)). A derived handler is code whose signature the user does not write; today `Resource` turns `Store[A]`'s `None` into a thrown `NotFound` at one line (`Resource.scala` line 367), so the derivation's signature is `Response` with no error type. With an `Either` at that seam the derived signature would carry the error type; with a `Raise[E]`, `CanThrow[E]` or `Abort[E]` it would carry a context parameter; with the current exception it carries neither. The ecosystem has all three shapes in production libraries; `CanThrow` itself is still experimental at 3.9.0 ([language.scala at 3.9.0](https://raw.githubusercontent.com/scala/scala3/3.9.0/library/src/scala/runtime/stdLibPatches/language.scala)) and covers only checked exceptions, which `EezoException extends RuntimeException` is not.

4. **Every capability implementation in the survey shares one mechanical fact with eezo's current exceptions: the short circuit is a `RuntimeException`.** `Break` "extends `RuntimeException`" with the stack trace suppressed ([boundary.scala](https://raw.githubusercontent.com/scala/scala3/main/library/src/scala/util/boundary.scala)); Ox and Yaes are built on it; Arrow throws a `CancellationException` and unwraps only its own scope's ([Fold.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-core/src/commonMain/kotlin/arrow/core/raise/Fold.kt)). What the capability adds over a bare throw is the type in the signature and the compile error when no handler is in scope ("A Label is generated from an enclosing `scala.util.boundary` call. Maybe that boundary is missing?"). What it does not remove is the exposure to an intervening `catch case NonFatal(e)`, which eezo's own `Scopes.attempt` is (`Scopes.scala` line 48). The same fact holds for `EezoException`, a `RuntimeException` that `attempt` would swallow into `Left` if thrown inside it.

5. **Every web framework surveyed says 404 with a value, and the frameworks closest to eezo's shape also accept a throw.** Sharaf, synchronous on a virtual thread, maps `NotFoundException` and `RejectedException` through a partial function that a user extends with `orElse` ([Exception handler](https://sake92.github.io/sharaf/howtos/exception-handler.html)); http4s's `ServiceErrorHandler` and Play's `HttpErrorHandler` are the same shape ([server/package.scala](https://raw.githubusercontent.com/http4s/http4s/main/server/shared/src/main/scala/org/http4s/server/package.scala); [HttpErrorHandler.scala](https://raw.githubusercontent.com/playframework/playframework/main/core/play/src/main/scala/play/api/http/HttpErrorHandler.scala)). eezo's `problems: PartialFunction[Throwable, Problem]` hook (ADR 0001) is that shape. tapir is the one framework with a typed error output at the handler, and it added `serverLogicRecoverErrors` so that a thrown `E <: Throwable` reaches that output without a `Left` ([Server logic](https://tapir.softwaremill.com/en/latest/server/logic.html)).

6. **The persistence convention is that a missing row is not an error at all.** `Option` from every `findById`, a count from every update, and a throw only from the `unique`/`head`/`single` variants the caller opted into (section 3). eezo's `Store[A]` matches this convention exactly, `Option` and `Boolean`, and its comment gives the same reason Ox gives for the level at which an error becomes recoverable: the layer that knows what HTTP is decides the status ([Store.scala](https://github.com/Eezo-framework/eezo/blob/4156da4/modules/core/src/main/scala/io/eezo/core/Store.scala); [Ox error handling](https://ox.softwaremill.com/latest/basics/error-handling.html)). The one place eezo's `db` deviates, `NoSuchRow` thrown by `updateById` and caught back into `false` by `JdbcStore`, has no counterpart in the six libraries surveyed: none of them throws on a zero row update.

7. **Defects are a bare `RuntimeException` in every library that names them.** Ox says so; Kyo's `Panic` is "similar to unchecked exceptions" and is rethrown at the boundary; Rust panics; Kotlin's KEEP puts "logic and programming errors" and "internal invariants and preconditions" in the exception bucket; Arrow's `catch` refuses fatal ones ([NonFatal.kt](https://github.com/arrow-kt/arrow/blob/main/arrow-libs/core/arrow-exception-utils/src/androidAndJvmMain/kotlin/arrow/core/NonFatal.kt)). eezo's `IllegalStateException` in `Guard.current` and `Resource` is that convention. No surveyed library carries a defect in a typed channel; Kyo carries it beside one.

8. **What no primary source in this survey answers.** None documents a measured cost of `Either` in macro generated code; the evidence is the choices made (section 4's table) and the two directions of bridging. None of the direct style libraries has a derived HTTP handler, so none has faced the exact question of which shape the derivation's signature should show. Those two gaps are where [#197](https://github.com/Eezo-framework/eezo/issues/197) has to rely on eezo's own spike rather than on precedent.
