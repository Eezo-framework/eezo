# Cookies, HMAC signing and bcrypt on Jetty 12.1 and JDK 25

This document records, as of 2026-09-12, what the platform eezo stands on gives a session ticket for free and what it has to add: how the Jetty 12.1 core API reads a `Cookie` header and writes a `Set-Cookie` one, what JDK 25 ships for HMAC signing, constant time comparison and random secrets, which bcrypt library to take since the JDK ships none, and which attributes the frameworks surveyed in `auth-in-other-frameworks.md` put on their session cookie by default. eezo pins Jetty 12.1.11 ([Dependencies.scala](../../project/Dependencies.scala)) and uses the core `org.eclipse.jetty.server.Request` and `Response` API, not the servlet one ([Eezo.scala](../../modules/http/src/main/scala/io/eezo/http/Eezo.scala)); it compiles with `-release 25` and CI runs JDK 25 ([ci.yml](../../.github/workflows/ci.yml)). Jetty facts come from the `jetty-12.1.x` branch source and the published 12.1 javadoc, generated from 12.1.9 at the time of reading; JDK facts from the Java SE 25 javadoc and security guides; library facts from their repositories and Maven Central. Every claim links to a primary source, and a closing section lists what could not be verified.

## Cookies on the Jetty 12.1 core API

### Reading the Cookie header

`Request.getCookies(Request)` is a static method on the core `Request` interface returning `List<HttpCookie>` ([javadoc](https://javadoc.jetty.org/jetty-12.1/org/eclipse/jetty/server/Request.html), [source](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-server/src/main/java/org/eclipse/jetty/server/Request.java)). It delegates to `CookieCache.getCookies(request)`, an "Optimized stateful cookie parser" that reads every `HttpHeader.COOKIE` field from `request.getHeaders()`, parses it under `getHttpConfiguration().getRequestCookieCompliance()`, caches the list under the request attribute `org.eclipse.jetty.server.Request.Cookies`, and returns an empty list, never null, when there is no `Cookie` header ([CookieCache](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-server/src/main/java/org/eclipse/jetty/server/CookieCache.java)). The default compliance is `CookieCompliance.RFC6265` for both parsing and generation ([HttpConfiguration](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-server/src/main/java/org/eclipse/jetty/server/HttpConfiguration.java)), which tolerates `INVALID_COOKIES`, `OPTIONAL_WHITE_SPACE`, `SPACE_IN_VALUES` and `STRIPPED_QUOTES`, so a malformed pair is dropped rather than failing the request and a quoted value comes back unquoted ([CookieCompliance](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-http/src/main/java/org/eclipse/jetty/http/CookieCompliance.java), [RFC6265CookieParser](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-http/src/main/java/org/eclipse/jetty/http/RFC6265CookieParser.java)).

`HttpCookie` is an interface in `jetty-http`, "Implementation of RFC6265 HTTP Cookies (with fallback support for RFC2965)", with `getName`, `getValue`, `getPath`, `getDomain`, `getMaxAge` (`-1` when absent), `isHttpOnly`, `isSecure`, `isPartitioned` and `getSameSite`; `SameSite` has `NONE("None")`, `STRICT("Strict")` and `LAX("Lax")`; `HttpCookie.from(name, value)` and `HttpCookie.build(name, value)` construct the immutable implementation through a `Builder` with `path`, `domain`, `maxAge`, `httpOnly`, `secure`, `sameSite` and `partitioned` ([javadoc](https://javadoc.jetty.org/jetty-12.1/org/eclipse/jetty/http/HttpCookie.html), [source](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-http/src/main/java/org/eclipse/jetty/http/HttpCookie.java)). Neither the builder nor `Immutable` validates the name or value; that happens when the `Set-Cookie` string is rendered.

eezo's adapter already copies every header into `Request.headers: Map[String, Seq[String]]` through `headersOf` ([Eezo.scala](../../modules/http/src/main/scala/io/eezo/http/Eezo.scala)), so the raw `Cookie` header reaches user code today. What is missing is the split into pairs, and the adapter is the one place that holds a `JettyRequest`, so `Request.getCookies(jettyRequest)` can fill a `cookies: Map[String, String]` on `io.eezo.http.Request` at construction, one line next to `headersOf`, with the quoting and compliance handling Jetty already tests.

### Writing Set-Cookie

The response side is `Response.addCookie(Response, HttpCookie)`, "Adds an HTTP SET_COOKIE header to the response", and `Response.putCookie`, which replaces an existing `Set-Cookie` with matching name, domain and path ([javadoc](https://javadoc.jetty.org/jetty-12.1/org/eclipse/jetty/server/Response.html)). Both throw `IllegalArgumentException` on a blank name, both wrap the cookie in `HttpCookieUtils.SetCookieHttpField`, both pass it through `HttpCookieUtils.checkSameSite(cookie, request.getContext())`, which fills in a context wide default from the attribute `org.eclipse.jetty.cookie.sameSiteDefault` when the cookie carries none, and both have a side effect worth knowing: "Expire responses with set-cookie headers, so they do not get cached", implemented by adding `Expires: Thu, 01 Jan 1970 00:00:00 GMT` when the response has no `Expires` yet ([Response.java](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-server/src/main/java/org/eclipse/jetty/server/Response.java)).

The string is assembled by `HttpCookieUtils.getRFC6265SetCookie`, which lives in `jetty-server`, not `jetty-http` ([HttpCookieUtils](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-server/src/main/java/org/eclipse/jetty/server/HttpCookieUtils.java)). It checks the name with `Syntax.requireValidRFC2616Token` and the value with `Syntax.requireValidRFC6265CookieValue`, then appends `name=value` followed, in this order and only when set, by `; Path=`, `; Domain=`, `; Expires=`, `; Max-Age=`, `; Secure`, `; HttpOnly`, `; Partitioned`, `; SameSite=` and any custom attributes. Two details matter for a session cookie. When `maxAge >= 0` Jetty always writes `Expires`, computed as `Instant.now().plusSeconds(maxAge)`, under the comment "This is required as some browser (M$ this means you!) don't handle max-age even with v1 cookies", and adds `Max-Age` only when `maxAge > 0`; a `maxAge` of `0` yields the epoch `Expires` and no `Max-Age`, which is how a cookie is deleted. And `requireValidRFC6265CookieValue` rejects control characters, space, double quote, comma, semicolon, backslash and any byte at or above 0x80 with a `ComplianceViolationException`, allowing only a balanced pair of double quotes around an otherwise valid value ([Syntax](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-core/jetty-http/src/main/java/org/eclipse/jetty/http/Syntax.java)).

That is the RFC 6265 grammar verbatim: `cookie-value = *cookie-octet / ( DQUOTE *cookie-octet DQUOTE )` where `cookie-octet = %x21 / %x23-2B / %x2D-3A / %x3C-5B / %x5D-7E`, "US-ASCII characters excluding CTLs, whitespace DQUOTE, comma, semicolon, and backslash", and servers "that wish to store arbitrary data in a cookie-value SHOULD encode that data, for example, using Base64" ([RFC 6265 section 4.1.1](https://www.rfc-editor.org/rfc/rfc6265#section-4.1.1)). `-`, `_`, `.` and `=` are all cookie octets, so a base64url payload with a `.` between payload and signature needs no quoting; standard base64's `+` and `/` are cookie octets too but collide with form and URL encoding, which is why every surveyed framework uses the URL safe alphabet.

### Jetty's cookie or a hand built header

`io.eezo.http.Response` is a plain value whose `headers: Seq[(String, Url | String)]` is an ordered sequence permitting duplicates precisely because `Set-Cookie` needs both ([Response.scala](../../modules/http/src/main/scala/io/eezo/http/Response.scala)), and the adapter's `write` does nothing but `response.getHeaders.add(name, Response.renderUrl(headerValue))` per pair ([Eezo.scala](../../modules/http/src/main/scala/io/eezo/http/Eezo.scala)). A `("Set-Cookie", "eezo_session=...; Path=/; HttpOnly; SameSite=Lax")` pair therefore reaches the wire today with no adapter change and no Jetty type in user code. Going through `Response.addCookie` would make the adapter recognise cookies as a third kind of thing in the value, would put `org.eclipse.jetty.http.HttpCookie` in eezo's public API, and would stamp `Expires: 1970` on every response that sets a cookie. The rendering rules that matter are the appends quoted above, and eezo can apply the same `cookie-octet` check at construction so a bad value fails where it is written rather than at the socket. `HttpCookieUtils.getSetCookie(cookie, CookieCompliance.RFC6265)` is public and static, so it stays available if the session ticket prefers Jetty to render the string, at the price of an `Expires` computed on every write.

## HMAC and constant time comparison on JDK 25

### Signing primitives

`javax.crypto.Mac` lists `HmacSHA256` among the algorithms "Every implementation of the Java platform is required to support", so `Mac.getInstance("HmacSHA256")` cannot fail on a conforming JDK ([Mac javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/Mac.html), [standard names](https://docs.oracle.com/en/java/javase/25/docs/specs/security/standard-names.html)). The documented sequence is `init(Key)` with a `SecretKeySpec` over the key bytes, then `doFinal(byte[])`, which "Processes the given array of bytes and finishes the MAC operation" and resets the object "to the state it was in when previously initialized". The javadoc says nothing about thread safety, and the OpenJDK source keeps `initialized` and the `MacSpi` in unsynchronized instance fields with no locking around `update` and `doFinal` ([Mac.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/javax/crypto/Mac.java)), whereas `SecureRandom` and `Base64.Encoder` carry an explicit "safe for use by multiple concurrent threads" sentence. A `Mac` per sign or verify call is the safe shape.

`MessageDigest.isEqual(byte[] digesta, byte[] digestb)` is the comparison. Its JDK 25 implementation note reads: "All bytes in `digesta` are examined to determine equality, unless `digestb` is `null` or has a length of zero bytes. If `digestb` is not `null` and does not have a length of zero bytes, then the calculation time depends only on the length of `digesta`. It does not depend on the length of `digestb` or the contents of `digesta` and `digestb`." ([MessageDigest javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/security/MessageDigest.html)). The source accumulates `result |= digesta[i] ^ digestb[indexB]` over every index of `digesta` with no early return ([MessageDigest.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/security/MessageDigest.java)). The guarantee is an `@implNote` rather than specification text, but it is the JDK's own comparison and what Spring Security's `BCrypt.checkpw` uses. The verifier should pass the freshly computed MAC as `digesta` and the cookie's bytes as `digestb`, so timing depends only on the server's own MAC length.

For the throwaway development secret, `new SecureRandom().nextBytes(new byte[32])` is the documented path: `SecureRandom` objects "are safe for use by multiple concurrent threads", and on Linux and macOS the default is `NativePRNG`, whose `nextBytes()` reads `/dev/urandom` ([SecureRandom javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/security/SecureRandom.html), [JDK providers](https://docs.oracle.com/en/java/javase/25/security/oracle-providers.html)). `getInstanceStrong()` resolves through `securerandom.strongAlgorithms=NativePRNGBlocking:SUN,DRBG:SUN` in the shipped `java.security` ([java.security](https://github.com/openjdk/jdk/blob/master/src/java.base/share/conf/security/java.security)), and `NativePRNGBlocking` reads `/dev/random`, so it is the wrong choice for a per boot secret.

`Base64.getUrlEncoder().withoutPadding()` encodes with "the URL and Filename safe Base64 Alphabet as specified in Table 2 of RFC 4648" and omits the trailing `=`; `getUrlDecoder()` accepts unpadded input, since padding "is accepted and interpreted as the end of the encoded byte data, but is not required", and throws `IllegalArgumentException` on characters outside the alphabet, which a verifier must catch and treat as no session ([Base64 javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Base64.html), [RFC 4648 section 5](https://www.rfc-editor.org/rfc/rfc4648.html#section-5)).

### Sign or encrypt

Only Rails encrypts its session cookie: `CookieStore` says "Sessions typically contain at most a user ID and flash message; both fit within the 4096 bytes cookie size limit" and "Your cookies will be encrypted using your application's `secret_key_base`. This goes a step further than signed cookies in that encrypted cookies cannot be altered or read by users", with `aes-256-gcm` as the cipher ([cookie_store.rb](https://github.com/rails/rails/blob/8-1-stable/actionpack/lib/action_dispatch/middleware/session/cookie_store.rb), [message_encryptor.rb](https://github.com/rails/rails/blob/8-1-stable/activesupport/lib/active_support/message_encryptor.rb)). Play signs: since 2.6 the session is a JWT with `play.http.session.jwt.signatureAlgorithm = "HS256"` over a `SecretKeySpec` built from `play.http.secret.key` ([reference.conf](https://github.com/playframework/playframework/blob/main/core/play/src/main/resources/reference.conf), [Cookie.scala](https://github.com/playframework/playframework/blob/main/core/play/src/main/scala/play/api/mvc/Cookie.scala), [2.6 migration](https://www.playframework.com/documentation/2.6.x/Migration26)), and its docs warn that "Information in a cookie is visible to the browser" ([ScalaSessionFlash](https://www.playframework.com/documentation/3.0.x/ScalaSessionFlash)). Flask signs with itsdangerous' `URLSafeTimedSerializer`, `salt = "cookie-session"`, SHA1 digest, `key_derivation = "hmac"` ([sessions.py](https://github.com/pallets/flask/blob/main/src/flask/sessions.py)); itsdangerous verifies with `hmac.compare_digest` and says "The receiver can see the data, but they can not modify it unless they also have your key" ([signer.py](https://github.com/pallets/itsdangerous/blob/main/src/itsdangerous/signer.py), [itsdangerous](https://itsdangerous.palletsprojects.com/en/stable/)). Django stores only an id by default, and its cookie backend is "signed but not encrypted", with `sha256`, `base64.urlsafe_b64encode(s).strip(b"=")` and `constant_time_compare` ([sessions](https://docs.djangoproject.com/en/5.2/topics/http/sessions/), [signing.py](https://github.com/django/django/blob/main/django/core/signing.py)). Plug's `COOKIE` store signs with `MessageVerifier.sign` unless an `encryption_salt` is configured, and the Phoenix generator sets only `signing_salt` ([cookie.ex](https://github.com/elixir-plug/plug/blob/main/lib/plug/session/cookie.ex)).

Encryption costs something signing does not. `AES/GCM/NoPadding` is a required `Cipher` transformation on JDK 25, but "GCM mode has a uniqueness requirement on IVs used in encryption with a given key. When IVs are repeated for GCM encryption, such usages are subject to forgery attacks", so every write needs a fresh random IV carried in the cookie, and tampering surfaces as an `AEADBadTagException` ([Cipher javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/Cipher.html)). What it buys, for a user id and a flash message, is that the browser cannot read the id or the flash text. Both are the user's own data: the id is not a secret by construction, and the flash is text the server is about to render to that same user. Four of five surveyed frameworks judged that not worth a cipher, and eezo's session holds nothing more. HMAC-SHA256 over `base64url(payload)` with the tag appended after a `.` is the shape Play, Flask and Django share, and it needs one `Mac`, one `isEqual` and one `Base64` codec, all in `java.base`.

## bcrypt on the JVM

The JDK ships no bcrypt, scrypt or argon2: the JDK 25 standard names page lists under `SecretKeyFactory` only `AES`, `ARCFOUR`, `ChaCha20`, `DES`, `DESede`, `Generic`, the `PBEWith` families and `PBKDF2With<prf>` ([standard names](https://docs.oracle.com/en/java/javase/25/docs/specs/security/standard-names.html)). `PBKDF2WithHmacSHA256` is not in the list `SecretKeyFactory` requires every platform to support, which names `DESede` alone, but SunJCE ships the `PBKDF2WithHmacSHA1` through `SHA512` family ([SecretKeyFactory javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/SecretKeyFactory.html), [JDK providers](https://docs.oracle.com/en/java/javase/25/security/oracle-providers.html)), driven by `PBEKeySpec(char[] password, byte[] salt, int iterationCount, int keyLength)` ([PBEKeySpec javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/spec/PBEKeySpec.html)). That is the no dependency fallback, and it is what Django and ASP.NET Core run in production, but it produces raw bytes and leaves the salt, iteration count and string format to eezo. A self describing `$2b$12$...` string is what the other frameworks store, and it is why bcrypt is worth one dependency.

`at.favre.lib:bcrypt` 0.10.2 was released on 2023-02-12 ([release](https://github.com/patrickfav/bcrypt/releases/tag/v0.10.2), [Maven Central](https://repo1.maven.org/maven2/at/favre/lib/bcrypt/)) and depends on `at.favre.lib:bytes:1.5.0` ([POM](https://repo1.maven.org/maven2/at/favre/lib/bcrypt/0.10.2/bcrypt-0.10.2.pom)). Every `hash` overload takes the cost first, between `MIN_COST = 4` and `MAX_COST = 31`; `BCrypt.withDefaults()` is `VERSION_2A` with `LongPasswordStrategies.strict`, which throws over 72 bytes, and `verifyer()` accepts any supported version and compares with `equalsConstantTime` ([BCrypt.java](https://github.com/patrickfav/bcrypt/blob/main/modules/bcrypt/src/main/java/at/favre/lib/crypto/bcrypt/BCrypt.java), [LongPasswordStrategy](https://github.com/patrickfav/bcrypt/blob/main/modules/bcrypt/src/main/java/at/favre/lib/crypto/bcrypt/LongPasswordStrategy.java)). It is the most complete bcrypt API on the JVM, but the README still reads "Java 7 Source, JDK 11 required to build (not yet JDK17 compatible)", the last commit on `main` is a README badge from 2025-03-30, and the jar has no `Automatic-Module-Name` ([README](https://github.com/patrickfav/bcrypt#readme)).

`org.mindrot:jbcrypt` 0.4 dates from 2017-02-13 ([Maven Central](https://repo1.maven.org/maven2/org/mindrot/jbcrypt/), [POM](https://repo1.maven.org/maven2/org/mindrot/jbcrypt/0.4/jbcrypt-0.4.pom)). `gensalt()` defaults to `GENSALT_DEFAULT_LOG2_ROUNDS = 10`, output is always `$2a$`, parsing rejects any other minor with "Invalid salt revision", and the key schedule reads bytes cyclically with no length check, so anything past 72 bytes is silently ignored ([BCrypt.java](https://github.com/jeremyh/jBCrypt/blob/master/src/main/java/org/mindrot/BCrypt.java)). It is the reference port the others descend from, with no commit since 2015.

Spring Security's `BCryptPasswordEncoder` ships in `spring-security-crypto` 7.1.1, released 2026-08-20 ([Maven Central](https://repo1.maven.org/maven2/org/springframework/security/spring-security-crypto/), [release](https://github.com/spring-projects/spring-security/releases/tag/7.1.1)). The published POM carries no mandatory dependency; `spring-core`, `bcpkix-jdk18on` and `password4j` are optional, for argon2 and scrypt ([POM](https://repo1.maven.org/maven2/org/springframework/security/spring-security-crypto/7.1.1/spring-security-crypto-7.1.1.pom), [gradle](https://github.com/spring-projects/spring-security/blob/7.1.1/crypto/spring-security-crypto.gradle)), so it does not pull the rest of Spring. The jar is 119 KB of Java 17 bytecode with `Automatic-Module-Name: spring.security.crypto`. Default strength is 10, `BCryptVersion` offers `$2a`, `$2y` and `$2b` with `$2a` the default, and `matches` checks `\A\$2(a|y|b)?\$(\d\d)\$[./0-9A-Za-z]{53}` before `BCrypt.checkpw`, which compares with `MessageDigest.isEqual` ([BCryptPasswordEncoder.java](https://github.com/spring-projects/spring-security/blob/7.1.1/crypto/src/main/java/org/springframework/security/crypto/bcrypt/BCryptPasswordEncoder.java), [BCrypt.java](https://github.com/spring-projects/spring-security/blob/7.1.1/crypto/src/main/java/org/springframework/security/crypto/bcrypt/BCrypt.java)). Since the commits "Enforce BCrypt password length" (2025-03-17) and "Enforce BCrypt password length for new passwords only" (2025-04-17, gh-16802), `hashpw` throws `IllegalArgumentException("password cannot be more than 72 bytes")` while `checkpw` still verifies an older long password. This is the encoder the survey found behind Spring's `DelegatingPasswordEncoder`.

Bouncy Castle's `OpenBSDBCrypt` in `bcprov-jdk18on` 1.86, released 2026-09-11 with thirteen CVE fixes in the notes ([release notes](https://github.com/bcgit/bc-java/blob/r1rv86/docs/releasenotes.md), [Maven Central](https://repo1.maven.org/maven2/org/bouncycastle/bcprov-jdk18on/)), takes an explicit cost and a caller supplied salt, defaults the version to `2y`, truncates silently ("Encoded passwords longer than 72 bytes are truncated and all remaining bytes are ignored"), and checks with `Strings.constantTimeAreEqual` ([OpenBSDBCrypt.java](https://github.com/bcgit/bc-java/blob/r1rv86/core/src/main/java/org/bouncycastle/crypto/generators/OpenBSDBCrypt.java)). The cost is a 7.2 MB provider jar for one hash function. `com.password4j:password4j` 1.8.4 (2025-06-30, Apache 2.0) covers bcrypt, scrypt, argon2 and PBKDF2 with a `$2b$` default at 10 rounds, but drags `slf4j-api` and truncates silently ([POM](https://repo1.maven.org/maven2/com/password4j/password4j/1.8.4/password4j-1.8.4.pom), [AlgorithmFinder.java](https://github.com/Password4j/password4j/blob/master/src/main/java/com/password4j/AlgorithmFinder.java)).

OWASP asks for a work factor "as large as verification server performance will allow, with a minimum of 10", and says "bcrypt has a maximum length input length of 72 bytes [for most implementations], so you should enforce a maximum password length of 72 bytes" rather than pre hashing, which "can be dangerous because of null bytes in the hash output value and because of password shucking" ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Spring ships 10 and Laravel 12 ([survey](auth-in-other-frameworks.md)).

Rails takes `httponly: true`, `path: '/'`, `secure: false` and `expire_after: nil` from rack-session's `DEFAULT_OPTIONS` ([id.rb](https://github.com/rack/rack-session/blob/main/lib/rack/session/abstract/id.rb)); `CookieStore` sets `same_site` from `cookies_same_site_protection`, which `load_defaults "6.1"` makes `:lax` ([cookie_store.rb](https://github.com/rails/rails/blob/8-1-stable/actionpack/lib/action_dispatch/middleware/session/cookie_store.rb), [configuration.rb](https://github.com/rails/rails/blob/8-1-stable/railties/lib/rails/application/configuration.rb)); the name is `"_#{app_name}_session"` ([finisher.rb](https://github.com/rails/rails/blob/8-1-stable/railties/lib/rails/application/finisher.rb)); `secure` is forced only under `config.force_ssl` ([default_middleware_stack.rb](https://github.com/rails/rails/blob/8-1-stable/railties/lib/rails/application/default_middleware_stack.rb)). Flask's config page gives `SESSION_COOKIE_NAME` `'session'`, `SESSION_COOKIE_HTTPONLY` `True`, `SESSION_COOKIE_SECURE` `False`, `SESSION_COOKIE_SAMESITE` `None` with "'Lax' (recommended)", and an expiry only when `session.permanent` ([config](https://flask.palletsprojects.com/en/stable/config/), [sessions.py](https://github.com/pallets/flask/blob/main/src/flask/sessions.py)). Django's `global_settings.py` reads `SESSION_COOKIE_NAME = "sessionid"`, `SESSION_COOKIE_AGE = 60 * 60 * 24 * 7 * 2`, `SESSION_COOKIE_SECURE = False`, `SESSION_COOKIE_PATH = "/"`, `SESSION_COOKIE_HTTPONLY = True`, `SESSION_COOKIE_SAMESITE = "Lax"` ([global_settings.py](https://github.com/django/django/blob/main/django/conf/global_settings.py)). Phoenix's generated endpoint declares `store: :cookie, key: "_<app>_key", signing_salt: ..., same_site: "Lax"` ([endpoint.ex.eex](https://github.com/phoenixframework/phoenix/blob/v1.8.13/installer/templates/phx_web/endpoint.ex.eex)); Plug's `put_resp_cookie` documents `:http_only` "Defaults to true", `:secure` "Defaults to true when the connection is HTTPS" and `:max_age` "Unset by default, which means the browser will default to a session cookie" ([Plug.Conn](https://plug.hexdocs.pm/Plug.Conn.html#put_resp_cookie/4)); `phx.gen.auth` adds `@session_validity_in_days 14` and a signed remember me cookie of 14 days reissued after 7 ([schema_token.ex.eex](https://github.com/phoenixframework/phoenix/blob/v1.8.13/priv/templates/phx.gen.auth/schema_token.ex.eex), [auth.ex.eex](https://github.com/phoenixframework/phoenix/blob/v1.8.13/priv/templates/phx.gen.auth/auth.ex.eex)). Play's `reference.conf` sets `cookieName = "PLAY_SESSION"`, `secure = false`, `maxAge = null` ("the cookie expires when the user closes their browser"), `httpOnly = true`, `sameSite = "lax"`, `path = ${play.http.context}`, and the same for `PLAY_FLASH` ([reference.conf](https://github.com/playframework/playframework/blob/3.0.x/core/play/src/main/resources/reference.conf)). Laravel's `config/session.php` has `lifetime` 120, `expire_on_close` false, `path` `/`, `secure` from `SESSION_SECURE_COOKIE` with no default, `http_only` true, `same_site` `'lax'`, and `StartSession` resets the expiry on every response ([session.php](https://github.com/laravel/laravel/blob/12.x/config/session.php), [StartSession.php](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Session/Middleware/StartSession.php)). ASP.NET Core's `CookieAuthenticationOptions` builds `SameSite = Lax, HttpOnly = true, SecurePolicy = SameAsRequest, IsEssential = true` with `ExpireTimeSpan` 14 days and `SlidingExpiration = true` ([CookieAuthenticationOptions.cs](https://github.com/dotnet/aspnetcore/blob/main/src/Security/Authentication/Cookies/src/CookieAuthenticationOptions.cs)), where `SameAsRequest` means Secure exactly when `Request.IsHttps` ([CookieBuilder.cs](https://github.com/dotnet/aspnetcore/blob/main/src/Http/Http.Abstractions/src/CookieBuilder.cs)). Spring Boot leaves every `server.servlet.session.cookie.*` property unset ([properties](https://docs.spring.io/spring-boot/appendix/application-properties/index.html)), so the container decides: `JSESSIONID`, context path, no `Max-Age`, HttpOnly from Tomcat's `useHttpOnly` default ([SessionCookieConfig](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/sessioncookieconfig), [Tomcat context](https://tomcat.apache.org/tomcat-11.0-doc/config/context.html)).

The pattern is unanimous on `HttpOnly` and `Path=/`, and Lax is the SameSite default in six of eight, with Flask and the servlet container leaving it unset. Lax "sends same-site cookies along with cross-site requests if and only if they are top-level navigations which use a 'safe' (in the [HTTP] sense) HTTP method", so a link from an email still lands logged in while a cross site POST arrives without the cookie, which the draft calls "reasonable defense in depth against CSRF attacks that rely on unsafe HTTP methods (like POST), but does not offer a robust defense against CSRF as a general category"; setting it explicitly also opts out of the two minute "Lax-allowing-unsafe" exemption browsers apply to cookies with no `SameSite` at all ([rfc6265bis section 5.6.7](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis)). No framework sets `Secure` unconditionally; the two that set it at all, Phoenix and ASP.NET Core, mirror the request scheme, which is what keeps plain `http://localhost` working in development. The `__Host-` prefix would be stricter but requires `Secure` ([rfc6265bis section 4.1.3.2](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis)), so it fails the same dev server. Expiry splits between browser session cookies (Rails, Flask, Phoenix, Play, Spring) and a window of two weeks (Django, ASP.NET Core, Phoenix's token).

## Recommendations

- Cookie API: read with Jetty, write by hand. In the adapter, `Request.getCookies(jettyRequest)` fills a `cookies: Map[String, String]` on `io.eezo.http.Request`; on the way out, a small `Cookie` value in `io.eezo.http` renders its own `Set-Cookie` string, validated against the `cookie-octet` rule at construction, and travels as one more `("Set-Cookie", ...)` pair in `Response.headers`. That keeps `HttpCookie` out of eezo's API, leaves the adapter's `write` untouched, and avoids the `Expires: 1970` header `Response.addCookie` stamps on every response.
- Signing scheme: HMAC-SHA256 from `javax.crypto.Mac`, a fresh `Mac` per call, over `base64url(payload)` with the tag appended after a `.`; verify with `MessageDigest.isEqual(computed, received)`; decode with `Base64.getUrlDecoder()` and treat `IllegalArgumentException` as no session. No encryption: the payload is a user id and a flash, and four of five surveyed frameworks sign only.
- Dev secret: `new SecureRandom().nextBytes(new byte[32])` at boot when none is configured, never `getInstanceStrong()`.
- bcrypt: `org.springframework.security:spring-security-crypto` 7.1.1, `BCryptPasswordEncoder` at strength 12 with the `$2b$` version. It is the only candidate with a 2026 release and no runtime dependency, it rejects a password over 72 bytes at hash time while still verifying old ones, it compares with `MessageDigest.isEqual`, and its strings interoperate with every framework surveyed. `at.favre.lib:bcrypt` has the nicer API but no release since 2023; Bouncy Castle is 7.2 MB for one function; jBCrypt is a decade old and truncates silently.
- No dependency fallback: `SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256")` with `PBEKeySpec`, recorded so a user who refuses the dependency knows where the JDK stops.
- Session cookie default: name `eezo_session`, `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` when the request arrived over HTTPS, no `Max-Age` so it is a browser session cookie, matching Rails, Play and Phoenix. A remember me lifetime, if wanted later, follows the two week window Django, ASP.NET Core and `phx.gen.auth` share.

## Facets not verified from primary sources

- The published 12.1 javadoc reports 12.1.9, two patch releases behind the 12.1.11 eezo pins; the source was read at the `jetty-12.1.x` branch head, not the 12.1.11 tag.
- `Mac` thread safety: the JDK 25 javadoc is silent; the claim rests on the unsynchronized fields in the OpenJDK source and the contrast with classes that carry the concurrency sentence.
- `MessageDigest.isEqual`: "constant time" appears only in a source comment, and the timing guarantee is an `@implNote`, not specification text.
- `getInstanceStrong()` blocking is derived from `securerandom.strongAlgorithms` resolving to `NativePRNGBlocking` and the providers guide saying its `nextBytes()` uses `/dev/random`; no javadoc sentence says "may block".
- Which Spring Security release first shipped the 72 byte rejection; the commits are dated but the first tag containing them was not confirmed.
- The 0.3 to 0.4 change in jBCrypt is described upstream as an integer overflow fix for large round counts, not the sign extension bug sometimes attributed to it.
- Chromium's treatment of `Secure` cookies on `http://localhost` is browser behaviour outside the rfc6265bis draft and was not checked against a Chromium source.
- Spring Security itself was not consulted for cookie attributes; the `JSESSIONID` defaults come from Spring Boot, the Servlet javadoc and Tomcat, and Jetty's and Undertow's servlet defaults were not checked.
- Phoenix's remember me cookie is 14 days in the v1.8.13 template, not the 60 days the ticket's framing assumed.
