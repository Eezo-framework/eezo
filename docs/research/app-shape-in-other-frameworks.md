# The shape of an application in the frameworks eezo is modeled on

This document surveys where eight web frameworks put the three things a small shop needs beyond routes and templates: the business layer (where an operation such as "start an order" lives), a vendor integration (who sequences "write the order, call the payment provider, redirect the browser", and where the provider client lives), and shared page code (the page frame, layouts and small formatters such as money and time). For each of Rails, Phoenix, Django, Laravel, Play, Spring Boot, ASP.NET Core and Flask it answers the same four questions: the business layer, the vendor integration, shared page code, and what the framework names as a rule versus what is only habit. A closing comparison collects where the eight converge, where they split, and which conventions the framework enforces rather than shows. Every claim links to a primary source: official guides, the frameworks' generator source on GitHub, or the framework's own or Stripe's own documented Checkout sample for that platform; where a claim could not be verified it is flagged in place. The survey was done on 2026-10-02 against the versions current on that date. It makes no recommendation for eezo.

### The business layer

The guides assign the model layer responsibility for data and business logic, and the controller the job of moving between request, model and view; they do not name a separate place for an operation such as "start an order". Active Record Basics opens by placing Active Record in the model, "the layer of the system responsible for representing data and business logic", and defines the pattern through Fowler as "an object that wraps a row in a database table, encapsulates the database access, and adds domain logic to that data" ([Active Record Basics](https://guides.rubyonrails.org/active_record_basics.html)). Action Controller Overview says "You can imagine that a controller sits between models and views. The controller makes model data available to the view, so that the view can display that data to the user. The controller also receives user input from the view and saves or updates model data accordingly", and "For most conventional RESTful applications, the controller will receive the request, fetch or save data from a model, and use a view to create HTML output" ([Action Controller Overview](https://guides.rubyonrails.org/action_controller_overview.html)). Neither guide discusses service objects, operations that span several models, or where to put them; the Action Controller Overview does not address concerns either ([Active Record Basics](https://guides.rubyonrails.org/active_record_basics.html), [Action Controller Overview](https://guides.rubyonrails.org/action_controller_overview.html)).

What the generators write is a model, a controller, views, a helper and tests, and nothing else. The Command Line guide introduces scaffolding with "A Rails scaffold generates a full set of files for a resource, including a model, controller, views (HTML and JSON), routes, migration, tests, and helper files", and its `bin/rails generate scaffold post title:string body:text` output lists `db/migrate/..._create_posts.rb`, `app/models/post.rb`, `route resources :posts`, `app/controllers/posts_controller.rb`, `app/views/posts/{index,edit,show,new}.html.erb`, `app/views/posts/_form.html.erb`, `app/views/posts/_post.html.erb`, `test/controllers/posts_controller_test.rb`, `test/system/posts_test.rb`, `app/helpers/posts_helper.rb` and the jbuilder views ([Command Line](https://guides.rubyonrails.org/command_line.html)). `bin/rails generate model post title:string body:text` creates only `db/migrate/..._create_posts.rb`, `app/models/post.rb`, `test/models/post_test.rb` and `test/fixtures/posts.yml` ([Command Line](https://guides.rubyonrails.org/command_line.html)). In the source, `Rails::Generators::ScaffoldGenerator` is a `ResourceGenerator` that does `remove_hook_for :resource_controller` and `hook_for :scaffold_controller, required: true` ([scaffold_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/scaffold/scaffold_generator.rb)); the scaffold controller generator in turn hooks `:template_engine`, `:resource_route`, `:test_framework` and `:helper` ([scaffold_controller_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/scaffold_controller/scaffold_controller_generator.rb)), and the ERB scaffold generator's `available_views` is `%w(index edit show new _form)` plus a `_#{singular_name}.html.erb` partial ([erb scaffold_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/erb/scaffold/scaffold_generator.rb)). The generated `create` action is the whole of the operation: it builds the record from `params.expect(...)`, calls `save`, and either redirects with a notice or renders `:new` with an unprocessable status ([controller.rb.tt](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/scaffold_controller/templates/controller.rb.tt)). The Getting Started guide shows the same shape by hand:

```ruby
def create
  @product = Product.new(product_params)
  if @product.save
    redirect_to @product
  else
    render :new, status: :unprocessable_entity
  end
end
```

([Getting Started](https://guides.rubyonrails.org/getting_started.html)). In that guide the rules live on the model (`validates :name, presence: true`, `validates :inventory_count, numericality: { greater_than_or_equal_to: 0 }`, and a callback `after_update_commit :notify_subscribers, if: :back_in_stock?`), while the controller instantiates, saves and redirects ([Getting Started](https://guides.rubyonrails.org/getting_started.html)).

`rails new` does create both concerns folders: `AppBuilder#app` runs `directory "app"`, `empty_directory_with_keep_file "app/assets/images"`, `keep_file "app/controllers/concerns"` and `keep_file "app/models/concerns"` ([app_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/app_generator.rb)). The Getting Started guide's own example of splitting a model does not use `app/models/concerns`: it creates `app/models/product/notifications.rb` and explains "Concerns are a great way to organize features of your Rails application. As you add more features to the Product, the class will become messy", then extracts each feature into a module of its own such as `Product::Notifications`, which the guide says holds all the functionality for handling subscribers and sending notifications, after which the model reads `include Notifications` ([Getting Started](https://guides.rubyonrails.org/getting_started.html)). The authentication generator is the one built in generator that writes a controller concern: it does `template "app/controllers/concerns/authentication.rb"` alongside `app/models/session.rb`, `app/models/user.rb`, `app/models/current.rb` and `app/controllers/sessions_controller.rb` ([authentication_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/authentication/authentication_generator.rb), [templates/app/controllers/concerns](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/authentication/templates/app/controllers/concerns)); the Getting Started guide describes it as "It creates User and Session models and the controllers and views necessary to login to our application" ([Getting Started](https://guides.rubyonrails.org/getting_started.html)). The `ActiveSupport::Concern` API page documents the module mechanics with abstract `Foo`, `Bar` and `Host` examples and never mentions `app/models/concerns` ([ActiveSupport::Concern](https://api.rubyonrails.org/classes/ActiveSupport/Concern.html)).

No `app/services` folder is generated or documented. The `rails new` app templates contain `assets/stylesheets/`, `controllers/`, `helpers/`, `jobs/`, `mailers/`, `models/` and `views/` ([templates/app](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app)); the Getting Started guide never uses the word "service" ([Getting Started](https://guides.rubyonrails.org/getting_started.html)); no guide title on the index mentions services, concerns or business logic ([Rails Guides](https://guides.rubyonrails.org/)). On the "fat model, skinny controller" question, no official page addresses it: a site restricted search for "skinny controller", "fat model" and "service object" on guides.rubyonrails.org and rubyonrails.org returned only community forum threads and blogs, none from the guides ([search](https://www.google.com/search?q=site%3Aguides.rubyonrails.org+%22skinny+controller%22+OR+%22fat+model%22+OR+%22service+object%22)). The Rails Doctrine, the nearest official statement of philosophy, says only that the model in the MVC layer cake is treated as "the prime bastion" of object oriented goodness, and does not mention fat models, skinny controllers or service objects ([The Rails Doctrine](https://rubyonrails.org/doctrine)).

### The vendor integration

Stripe's documented Ruby Checkout integration is a Sinatra application, not a Rails one, and it has no model and no database. The sample's `server/ruby` folder holds `Gemfile`, `server.rb` and a `README.md` that calls it "A Sinatra implementation" run with `bundle install` then `ruby server.rb` ([server/ruby](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/ruby)). Everything lives in the single file `server.rb`: it requires `stripe`, `sinatra` and `dotenv`, loads `.env`, and sets the provider client globally at file top with `Stripe.api_key = ENV['STRIPE_SECRET_KEY']`, preceded by the comment "Don't put any keys in code. Use an environment variable (as shown here) or secrets vault to supply keys to your integration" ([server.rb](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/ruby/server.rb)). The route handler itself sequences the provider call and the redirect; there is no order write because the sample stores nothing:

```ruby
post '/create-checkout-session' do
  # Create new Checkout Session for the order
  session = Stripe::Checkout::Session.create(
    success_url: ENV['DOMAIN'] + '/success.html?session_id={CHECKOUT_SESSION_ID}',
    mode: 'payment',
    # automatic_tax: { enabled: true },
    line_items: [{
      quantity: params['quantity'],
      price: ENV['PRICE'],
    }]
  )

  redirect session.url, 303
end
```

([server.rb](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/ruby/server.rb)). The same file has a `get '/checkout-session'` route that calls `Stripe::Checkout::Session.retrieve`, a `get '/config'` route calling `Stripe::Price.retrieve`, and a `post '/webhook'` route that verifies with `Stripe::Webhook.construct_event` and prints a message when `event_type == 'checkout.session.completed'` ([server.rb](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/ruby/server.rb)). The repository README frames the flow as "Once your customer is ready to pay, use Stripe.js to redirect them to the URL of your Stripe hosted payment page" and lists `server/java`, `server/node`, `server/php`, `server/php-slim`, `server/python`, `server/ruby`, `server/.net` and `server/go` ([README](https://github.com/stripe-samples/checkout-one-time-payments)).

The docs.stripe.com quickstart for Ruby has the same shape with the newer client object: `client = Stripe::StripeClient.new('<<YOUR_SECRET_KEY>>')` at top level, then inside the route `session = client.v1.checkout.sessions.create({ ... line_items: [{ price: '{{PRICE_ID}}', quantity: 1 }], mode: ..., success_url: YOUR_DOMAIN + '/success.html', ... })` followed by `redirect session.url, 303`, run with `ruby server.rb -o 0.0.0.0` ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=ruby)). Its prose says "Add an endpoint on your server that creates a Checkout Session", "After creating the session, redirect your customer to the URL for the Checkout page returned in the response", and, on fulfilment, "Wait to fulfill orders (for example, shipping or sending email receipts) until the payment succeeds" with a pointer to the fulfilment guide ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=ruby)). The quickstart mentions no database and no ORM; the only data the server holds is the price id ("Always keep sensitive information about your product inventory, such as price and availability, on your server") ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=ruby)). So in Stripe's own material the answer to "who sequences write, call, redirect" is the HTTP handler, the provider client is configured at the top of the same file, and a model never imports the provider because there is no model.

On the Rails side, the framework documents a place for configuration but not for an API client as such. The Getting Started table describes `config/` as "Contains configuration for your application's routes, database, and more" and `lib/` as "Extended modules for your application" ([Getting Started](https://guides.rubyonrails.org/getting_started.html)). `rails new` creates `config/initializers` (`AppBuilder#config` does `directory "initializers"` inside `config`) and `lib` with `lib/tasks` (`AppBuilder#lib`) ([app_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/app_generator.rb)); the shipped initializers are `assets.rb`, `content_security_policy.rb`, `cors.rb`, `filter_parameter_logging.rb`, `inflections.rb` and a `new_framework_defaults` file ([config/initializers templates](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/config/initializers)). The Configuring guide lists "four standard spots to place initialization code", namely `config/application.rb`, the environment specific configuration files, initializers, and after initializers, and, under `config.after_initialize`, speaks of "all the application's initializers in `config/initializers`" ([Configuring](https://guides.rubyonrails.org/configuring.html)); the `Rails::Application` booting process reads, at step 7, "Run `Railtie#initializer` defined by railties, engines, and application. One by one, each engine sets up its load paths and routes, and runs its `config/initializers/*` files" ([Rails::Application](https://api.rubyonrails.org/classes/Rails/Application.html)). For the secret itself, the credentials command describes "encrypted credentials, so you can safely store access tokens, database passwords, and the like safely inside the app without relying on a mess of ENVs" ([credentials USAGE](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/credentials/USAGE)), read through `Rails.application.credentials`, which "Returns an `ActiveSupport::EncryptedConfiguration` instance for the credentials file specified by `config.credentials.content_path`" defaulting to `config/credentials.yml.enc` ([Rails::Application](https://api.rubyonrails.org/classes/Rails/Application.html), [ActiveSupport::EncryptedConfiguration](https://api.rubyonrails.org/classes/ActiveSupport/EncryptedConfiguration.html)). Nothing in these pages says where a vendor client object or a wrapper class for it should be defined; `lib` is described only as "Extended modules" and is not autoloaded unless `config.autoload_lib` is called (see the last section).

### Shared page code

The page frame is a layout found by convention under `app/views/layouts`. "To find the current layout, Rails first looks for a file in `app/views/layouts` with the same base name as the controller", and when none exists "Rails will use `app/views/layouts/application.html.erb` or `app/views/layouts/application.builder`" ([Layouts and Rendering](https://guides.rubyonrails.org/layouts_and_rendering.html)); the Action View Overview repeats the rule ([Action View Overview](https://guides.rubyonrails.org/action_view_overview.html)). The file is generated: the app templates hold `application.html.erb.tt`, `mailer.html.erb.tt` and `mailer.text.erb.tt` under `app/views/layouts` ([templates/app/views/layouts](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app/views/layouts)), and the generated layout carries `<title>`, `csrf_meta_tags`, `csp_meta_tag`, `yield :head`, the stylesheet tag and a body of `<%= yield %>` ([application.html.erb.tt](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/app/views/layouts/application.html.erb.tt)). The Getting Started guide tells the reader this layout "is where you put HTML that you want to include in every page like a header or footer" ([Getting Started](https://guides.rubyonrails.org/getting_started.html)). Inside a layout, "`yield` identifies a section where content from the view should be inserted" and named regions such as `yield :head` are allowed; the guide names "three tools for combining different bits of output to form the overall response: Asset tags, `yield` and `content_for`, and Partials" ([Layouts and Rendering](https://guides.rubyonrails.org/layouts_and_rendering.html)).

Reusable fragments are partials, named by the framework's convention. "Partial file names start with leading underscore character by convention. The file name distinguishes partials from regular views. However, no underscore is used when referring to partials for rendering within a view" ([Action View Overview](https://guides.rubyonrails.org/action_view_overview.html)); a partial rendered from a layout can be looked up through the template chain, so a call for `menu` "will pull in the partial from `app/views/application/_menu.html.erb`" ([Layouts and Rendering](https://guides.rubyonrails.org/layouts_and_rendering.html)). The scaffold generates `_form.html.erb` and `_post.html.erb` ([Command Line](https://guides.rubyonrails.org/command_line.html)) and the Getting Started guide writes `app/views/products/_form.html.erb`, noting "The filename starts with an underscore to denote this is a partial", rendered with `<%= render "form", product: @product %>` ([Getting Started](https://guides.rubyonrails.org/getting_started.html)).

Small formatters are either framework helpers or application helpers in `app/helpers`. The Action View Helpers guide documents `number_to_currency` as "Formats a number into a currency string (e.g., $13.65)" with `number_to_currency(1234567890.50) # => $1,234,567,890.50`, and `time_ago_in_words` as "Reports the approximate distance in time between a `Time` or `Date` object, or integer as seconds, and `Time.current`" ([Action View Helpers](https://guides.rubyonrails.org/action_view_helpers.html)); the API places them in `ActionView::Helpers::NumberHelper` ("Provides methods for converting numbers into formatted strings. Methods are provided for phone numbers, currency, percentage, precision, positional notation, file size, and pretty printing") and `ActionView::Helpers::DateHelper` ("Like distance_of_time_in_words, but where to_time is fixed to Time.now") ([NumberHelper](https://api.rubyonrails.org/classes/ActionView/Helpers/NumberHelper.html), [DateHelper](https://api.rubyonrails.org/classes/ActionView/Helpers/DateHelper.html)). For an application's own formatters the framework generates the folder and the module: `rails new` ships `app/helpers/application_helper.rb.tt`, whose entire content is `module ApplicationHelper` and `end` ([templates/app/helpers](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app/helpers), [application_helper.rb.tt](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/app/helpers/application_helper.rb.tt)); every controller and scaffold generation adds `app/helpers/<name>_helper.rb` ([Command Line](https://guides.rubyonrails.org/command_line.html)), which the Getting Started guide describes as "A helper file for extracting logic in our views" ([Getting Started](https://guides.rubyonrails.org/getting_started.html)). The inclusion is a framework rule, not a habit: "By default, each controller will include all helpers", with `config.action_controller.include_all_helpers = false` restoring the older behaviour in which only the helper matching the controller name was included, and `helper` adding others explicitly ([ActionController::Helpers](https://api.rubyonrails.org/classes/ActionController/Helpers.html)). The Action View Helpers guide and Action View Overview themselves do not explain the `app/helpers` mechanism; they list what the built in helpers do ([Action View Helpers](https://guides.rubyonrails.org/action_view_helpers.html), [Action View Overview](https://guides.rubyonrails.org/action_view_overview.html)).

So the names of all three places, `app/views/layouts/application.html.erb`, the underscore partial, and `app/helpers/application_helper.rb` with `ApplicationHelper`, are given by the framework: generated by `rails new` or the controller generator, and read back by convention in layout lookup, partial lookup and helper inclusion.

### What the framework names versus what is habit

Rails reads one rule rather than a list of folders: every subdirectory of `app` is an autoload root. The Zeitwerk guide states that "By default, the autoload paths of an application consist of all the subdirectories of `app` that exist when the application boots" except `assets`, `javascript` and `views`, "plus the autoload paths of engines it might depend on", and adds that the concerns directories under `app/models` and `app/controllers` are also root directories ([Autoloading and Reloading Constants](https://guides.rubyonrails.org/autoloading_and_reloading_constants.html)). File names must match constants, "with directories acting as namespaces", so "the file `app/models/user.rb` should define `User`" and `UsersHelper` in `app/helpers/users_helper.rb` "is autoloadable, you do not need (and should not write) a `require` call for it" ([Autoloading and Reloading Constants](https://guides.rubyonrails.org/autoloading_and_reloading_constants.html)). The engine API lists the paths the framework knows by name: `paths["app"]`, `paths["app/controllers"]`, `paths["app/helpers"]`, `paths["app/models"]`, `paths["app/views"]`, `paths["lib"]`, `paths["lib/tasks"]`, `paths["config"]`, `paths["config/initializers"]`, `paths["config/locales"]` and `paths["config/routes.rb"]`, with the note that "all folders under `app` are automatically added to the load path" ([Rails::Engine](https://api.rubyonrails.org/classes/Rails/Engine.html)).

Folders that are named by the framework, meaning generated by `rails new` and described in the Getting Started table or the guides: `app/` ("Contains the controllers, models, views, helpers, mailers, jobs, and assets for your application"), `config/`, `lib/` ("Extended modules for your application"), `vendor/` (for code from third parties), `db/`, `test/`, `public/`, `bin/`, `log/`, `script/`, `storage/`, `tmp/` ([Getting Started](https://guides.rubyonrails.org/getting_started.html)); under `app`, the generator templates hold `assets/stylesheets`, `controllers`, `helpers`, `jobs`, `mailers`, `models` and `views`, and the builder adds `app/assets/images`, `app/controllers/concerns` and `app/models/concerns` as keep files ([templates/app](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app), [app_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/app_generator.rb)); `app/views/layouts` holds the three generated layouts ([templates/app/views/layouts](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app/views/layouts)); `config/initializers` and `lib/tasks` are created by `AppBuilder#config` and `AppBuilder#lib` ([app_generator.rb](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/app_generator.rb)).

`lib` is a special case: it is generated but not autoloaded by default. "By default, the `lib` directory does not belong to the autoload paths of applications or engines"; `config.autoload_lib` "adds the `lib` directory to `config.autoload_paths` and `config.eager_load_paths`. It has to be invoked from `config/application.rb` or `config/environments/*.rb`", and "Normally, `lib` has subdirectories that should not be managed by the autoloaders. Please, pass their name relative to `lib` in the required `ignore` keyword argument", with the example `config.autoload_lib(ignore: %w(assets tasks))` ([Autoloading and Reloading Constants](https://guides.rubyonrails.org/autoloading_and_reloading_constants.html)). The generated `config/application.rb` contains that call, `config.autoload_lib(ignore: %w[assets tasks])`, under a comment asking the developer to add "any other `lib` subdirectories that do not contain `.rb` files, or that should not be reloaded or eager loaded. Common ones are `templates`, `generators`, or `middleware`" ([application.rb.tt](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/config/application.rb.tt)).

Folders that are habit: `app/services`, form objects, presenters, query objects and the like are neither generated nor documented by name anywhere in the fetched guides or generator templates ([templates/app](https://github.com/rails/rails/tree/main/railties/lib/rails/generators/rails/app/templates/app), [Getting Started](https://guides.rubyonrails.org/getting_started.html), [Rails Guides](https://guides.rubyonrails.org/)). The framework makes them work without saying what they should be: "Rails adds custom directories under `app` to the autoload paths automatically. For example, if your application has `app/presenters`, you don't need to configure anything in order to autoload presenters; it works out of the box" ([Autoloading and Reloading Constants](https://guides.rubyonrails.org/autoloading_and_reloading_constants.html)). That sentence is the only official acknowledgement that such folders exist, and `app/presenters` is its only example; `app/services` is not mentioned. In other words Rails names `models`, `controllers`, `helpers`, `views/layouts`, `jobs`, `mailers`, the two `concerns` folders, `config/initializers` and `lib`, and leaves a service layer unnamed but mechanically supported.

### The business layer

Phoenix's answer to where "start an order" lives is a named context module under `lib/my_app`, never the controller and never the schema. The Directory structure guide draws the line at the top of `lib`: "The `lib/hello` directory is responsible for hosting all of your business logic and business domain. It typically interacts directly with the database" and is the Model in MVC, while "`lib/hello_web` is responsible for exposing your business domain to the world, in this case, through a web application. It holds both the View and Controller from MVC" ([Directory structure](https://phoenix.hexdocs.pm/directory_structure.html)). The Contexts guide (in 1.8 a six chapter "Data modelling" sequence that "are meant to be read in order") defines the business layer as "where we encapsulate data access and data validation. We call these modules contexts. They often talk to a database, using Ecto, or APIs, using an HTTP client such as Req" ([Contexts](https://phoenix.hexdocs.pm/contexts.html)). The second chapter restates it: "Your context modules are dedicated modules that expose and group related functionality. Phoenix generates generic functions, such as `list_products` and `update_product`, but they only serve as a basis for you to grow your business logic and application from" ([Your first context](https://phoenix.hexdocs.pm/your_first_context.html)).

The controller is explicitly kept out of that role. The Request life cycle guide says "the job of the controller is to retrieve request information, talk to your business domain, and prepare data for the presentation layer" ([Request life cycle](https://phoenix.hexdocs.pm/request_lifecycle.html)); the Controllers guide describes controllers as "intermediary modules" whose actions "gather all the necessary data and perform all the necessary steps before invoking the view layer" ([Controllers](https://phoenix.hexdocs.pm/controllers.html)); and the Contexts guide is blunt: "Our Phoenix controller is the web interface into our greater application. It shouldn't be concerned with the details of how products are fetched from the database or persisted into storage. We only care about telling our application to perform some work for us. This is great because our business logic and storage details are decoupled from the web layer of our application" and "we can reuse our context code from any other interface in our application, be it a channel, mix task, or a long running process (the guide gives CSV import as the example)" ([Your first context](https://phoenix.hexdocs.pm/your_first_context.html)). The schema is not a candidate either: in every example the schema module (`Catalog.Product`, `ShoppingCart.Cart`, `Orders.Order`) only defines fields and changesets, and the FAQ describes schemas and other modules inside a context as private: "The context is your public API, the other modules are private" ([Contexts FAQ](https://phoenix.hexdocs.pm/faq.html)).

The order example is the guide's own case for the operation in question. Chapter 5 generates `mix phx.gen.context Orders Order orders total_price:decimal` and `mix phx.gen.context Orders LineItem order_line_items price:decimal quantity:integer order_id:references:orders product_id:references:products --no-scope`, then says "Now we can implement our `Orders.complete_order/2` function" ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). The function has the signature `def complete_order(%Scope{} = scope, %ShoppingCart.Cart{} = cart)` and, in the order the guide shows, maps the cart items into line item maps with `Enum.map`, builds a bare changeset with `Ecto.Changeset.change/2` whose total comes from `ShoppingCart.total_cart_price/1`, then inside `Repo.transact/2` calls `Repo.insert` for the order and `ShoppingCart.prune_cart_items/2` to empty the cart, and finally broadcasts the order ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). The prose that follows explains: "The job of the order line item record is to capture the price of the product at payment transaction time, so we reference the product's price here. Next, we create a bare order changeset with `Ecto.Changeset.change/2` and associate our user UUID, set our total price calculation, and place our order line items in the changeset", and on the transaction: "The function wrapped inside `Repo.transact/2` must either return `{:ok, result}` or error, which halts and rolls back the transaction" ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). The controller then does one call and a redirect: `OrderController.create` calls `Orders.complete_order(conn.assigns.current_scope, conn.assigns.cart)`, on `{:ok, order}` puts the flash "Order created successfully." and redirects to `~p"/orders/#{order}"`, and on error puts an error flash and redirects to `~p"/cart"` ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). So the sequencing of a multi step business operation is placed in the context function, and the controller only translates its result into HTTP.

What the generators create follows the same split. `mix phx.new` lays out `lib/hello`, `lib/hello.ex`, `lib/hello_web` and `lib/hello_web.ex` ([Directory structure](https://phoenix.hexdocs.pm/directory_structure.html)); the installer maps `phx_single/lib/app_name_web.ex.eex` to `lib/:lib_web_name.ex`, with `:lib_web_name` set to `"#{app}_web"`, and the `phx_web` templates to `lib/:lib_web_name/endpoint.ex`, `router.ex`, `components/core_components.ex`, `components/layouts.ex`, `components/layouts/root.html.heex`, `controllers/page_controller.ex`, `controllers/page_html.ex` and `controllers/page_html/home.html.heex` ([installer/lib/phx_new/single.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/lib/phx_new/single.ex)). `mix phx.gen.html Catalog Product products title:string description:string price:decimal views:integer` is the guide's command, and the printed file list is `lib/hello_web/controllers/product_controller.ex`, the five templates under `lib/hello_web/controllers/product_html/`, `lib/hello_web/controllers/product_html.ex`, `lib/hello/catalog/product.ex`, a migration, `lib/hello/catalog.ex`, and tests and fixtures ([Your first context](https://phoenix.hexdocs.pm/your_first_context.html)). The task docs for all three generators repeat the same sentence, "The context is an Elixir module that serves as an API boundary for the given resource": `phx.gen.html` "Generates controller with view, templates, schema and context for an HTML resource" into `lib/my_app_web/controllers/` and `lib/my_app/accounts.ex` plus `lib/my_app/accounts/user.ex`, and "If the context already exists, it will be augmented with functions for the given resource" ([mix phx.gen.html](https://phoenix.hexdocs.pm/Mix.Tasks.Phx.Gen.Html.html)); `phx.gen.live` "Generates LiveView, templates, and context for a resource" with LiveViews in `lib/app_web/live/user_live/show.ex`, `index.ex` and `form.ex` and "a components module in `lib/app_web/components/core_components.ex` if none exists" ([mix phx.gen.live](https://phoenix.hexdocs.pm/Mix.Tasks.Phx.Gen.Live.html)); `phx.gen.context` "Generates a context with functions around an Ecto schema" with no web files at all ([mix phx.gen.context](https://phoenix.hexdocs.pm/Mix.Tasks.Phx.Gen.Context.html)). The context template itself is nearly empty, a module with `@moduledoc "The <name> context."`, `import Ecto.Query` and a `Repo` alias, into which the resource functions are injected ([priv/templates/phx.gen.context/context.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/priv/templates/phx.gen.context/context.ex.eex)); the generated controller's `create` calls `Context.create_resource(params)` and on success redirects, on `%Ecto.Changeset{}` error re renders `:new` ([priv/templates/phx.gen.html/controller.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/priv/templates/phx.gen.html/controller.ex.eex)).

### The vendor integration

The Contexts guide places external APIs inside contexts by definition, but only in one sentence: contexts "often talk to a database, using Ecto, or APIs, using an HTTP client such as Req" ([Contexts](https://phoenix.hexdocs.pm/contexts.html)). That is the only mention of external services in the whole six chapter sequence. The chapter on cross context boundaries discusses only dependencies between the application's own contexts: "Our `ShoppingCart` context will have a data dependency on the `Catalog` context. With that in mind, we have two options. One is to expose APIs on the `Catalog` context that allows us to efficiently fetch product data for use in the `ShoppingCart` system, which we would manually stitch together. Or we can use database joins to fetch the dependent data", and later "We proceed to fetch the product with `Catalog.get_product!/1`, showing how contexts can naturally invoke other contexts if required" ([Cross context boundaries](https://phoenix.hexdocs.pm/cross_context_boundaries.html)). The words "external", "third party", "service" and "payment" do not occur in that chapter. There is no section that says contexts should wrap external services; the one sentence in the introduction is the entire basis for that reading, so the claim "the Contexts guide has a section on contexts wrapping external services" is not supported by the current text (not verified as a section; verified only as the single sentence quoted).

Payments are named and then deferred. Chapter 5 opens: "We won't go as far as integrating payment processing or order fulfillment, but we'll get you started in that direction", and closes: "We haven't added payments, but we can already see how our `ShoppingCart` and `Orders` context splitting is driving us towards a maintainable solution. With our cart items separated from our order line items, we are well equipped in the future to add payment transactions, cart price detection, and more" ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). The guide never says where a payment client module would live.

Following the guide's own pattern, the party that sequences "write the order, call the provider, redirect" would be the `Orders` context for the first two steps and the controller for the third, because `complete_order/2` already sequences insert and cart pruning inside `Repo.transact/2` and the controller's whole job is `case Orders.complete_order(...)` followed by `redirect` ([Bringing it home](https://phoenix.hexdocs.pm/more_examples.html)). The guide never shows a schema module calling anything but Ecto changeset functions; `Orders.Order`, `Orders.LineItem`, `ShoppingCart.Cart` and `ShoppingCart.CartItem` are data definitions, and the FAQ treats them as private to the context ([Contexts FAQ](https://phoenix.hexdocs.pm/faq.html)). No schema calls an external service anywhere in the guides read.

### Shared page code

The page frame and the layouts have fixed, generated homes. The Components and HEEx guide: "All Phoenix applications have one component called the 'root layout'. This page is where you will find the `<head>` and `<body>` tags of your HTML page", configured in the router by `plug :put_root_layout, html: {HelloWeb.Layouts, :root}`, with "The template itself can be found at `lib/hello_web/components/layouts/root.html.heex`" and `{@inner_content}` marking where the rendered template is injected ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). The application frame is not a template but a function: "Any dynamic functionality of your application is then implemented as function components. For example, your application menu and sidebar is typically part of the `app` component in `lib/hello_web/components/layouts.ex`, which is invoked in every template" as `<Layouts.app flash={@flash}> ... </Layouts.app>`, and "if you want to create an admin layout, you can simply add a new function in the `Layouts` module, and then invoke `Layouts.admin` instead of `Layouts.app`" ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). The Request life cycle guide says the same from the other side: "Our index template is actually rendered into a separate layout: `lib/hello_web/components/layouts/root.html.heex`", "The root layout, as the name implies, is a barebone layout with mostly the `<head>` tag and a structure that is shared across all of your pages", and "there is an `HelloWeb.Layouts.app` function, that defines our application layout, which we invoke with our custom content" ([Request life cycle](https://phoenix.hexdocs.pm/request_lifecycle.html)).

The generated source matches. The installer's `layouts.ex.eex` carries `@moduledoc "This module holds layouts and related functionality used by your application."`, `use <web_namespace>, :html`, `embed_templates "layouts/*"`, and `def app(assigns)` documented as "Renders your app layout. This function is typically invoked from every template, and it often contains your application menu, sidebar, or similar", with `attr :flash, :map, required: true`, `attr :current_scope, :map, default: nil` and `slot :inner_block, required: true`; it also defines `flash_group/1` and `theme_toggle/1` ([layouts.ex.eex on main](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_web/components/layouts.ex.eex), same moduledoc, use, embed_templates and `def app` on the [v1.8.15 tag](https://raw.githubusercontent.com/phoenixframework/phoenix/v1.8.15/installer/templates/phx_web/components/layouts.ex.eex)). The `components/layouts` template directory holds only `root.html.heex.eex`, on both `main` and `v1.8.15`; there is no `app.html.heex` in a 1.8 project, the app layout exists only as the `app/1` function component ([layouts dir on main](https://api.github.com/repos/phoenixframework/phoenix/contents/installer/templates/phx_web/components/layouts), [layouts dir at v1.8.15](https://api.github.com/repos/phoenixframework/phoenix/contents/installer/templates/phx_web/components/layouts?ref=v1.8.15)). The `phx.gen.html` index template opens with `<Layouts.app flash={@flash} ...>` and closes with `</Layouts.app>` ([index.html.heex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/priv/templates/phx.gen.html/index.html.heex.eex)).

Small shared pieces go in `lib/hello_web/components/core_components.ex`: "In a new Phoenix application, you will also find a `core_components.ex` module inside the `components` folder", "automatically imported into all HTML views via `use HelloWeb, :html`" as configured in `lib/hello_web.ex`, and it "performs `use Phoenix.Component` instead of `use HelloWeb, :html`" because the latter "would cause a deadlock as we would try to import `CoreComponents` into itself" ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). The generated module's moduledoc says its "goal is to provide core building blocks for your application, such as tables, forms, and inputs", and it defines `flash/1`, `button/1`, `input/1`, `header/1`, `table/1`, `list/1`, `icon/1`, `show/2`, `hide/2` plus the plain helpers `translate_error/1` and `translate_errors/2` ([core_components.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_web/components/core_components.ex.eex)). Formatters such as money and time are not addressed anywhere in the guides read; the only placement rule given for page specific helpers is "If we want to write a function component to be invoked from `show.html.heex`, we can simply add it to `HelloHTML`" ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). The web module's own moduledoc forbids putting such functions in `lib/hello_web.ex`: "Do NOT define functions inside the quoted expressions below. Instead, define additional modules and import those modules here" ([app_name_web.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_single/lib/app_name_web.ex.eex)). So a money formatter would, by the generated pattern, be a function in `CoreComponents` (imported everywhere) or in the HTML module that uses it; the framework does not name a `helpers` folder.

The names are given by the framework rather than by habit. `components/`, `components/layouts.ex`, `components/layouts/root.html.heex` and `components/core_components.ex` are written by `mix phx.new` ([single.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/lib/phx_new/single.ex)), and the generated `lib/hello_web.ex` wires them in: `html_helpers` does `import <web_namespace>.CoreComponents` and `alias <web_namespace>.Layouts`, and `html` and `live_view` both `unquote(html_helpers())` ([app_name_web.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_single/lib/app_name_web.ex.eex)). The generated `PageHTML` and the guide's `HelloHTML` take everything through `use HelloWeb, :html` and `embed_templates "page_html/*"` ([page_html.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_web/controllers/page_html.ex.eex), [Request life cycle](https://phoenix.hexdocs.pm/request_lifecycle.html)).

### What the framework names versus what is habit

Phoenix does not read folders. Elixir's compiler takes `:elixirc_paths`, "directories to find source files. Defaults to `["lib"]`" ([mix compile.elixir](https://mix.hexdocs.pm/Mix.Tasks.Compile.Elixir.html)), and the generated `mix.exs` sets `defp elixirc_paths(:test), do: ["lib", "test/support"]` and `defp elixirc_paths(_), do: ["lib"]` ([mix.exs.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_single/mix.exs.eex)). Everything under `lib` compiles regardless of subfolder, so `lib/hello`, `lib/hello_web`, `controllers`, `components`, `components/layouts` and `live` are never consulted at runtime; the module names are what matter. The Directory structure guide does not say this in so many words. It says only that `lib` is "a directory that holds your application source code" and that `lib/hello_web` holds the parts of the application that relate to the web; the words "convention", "compile" and "free to" do not appear on the page ([Directory structure](https://phoenix.hexdocs.pm/directory_structure.html)). The claim that Mix compiles everything under `lib` therefore rests on the Mix documentation and the generated `mix.exs`, not on a Phoenix guide (the Phoenix guide's silence is verified; the Mix rule is verified).

What the framework does fix are module names and the files it generates. The HTML module convention is enforced by `render/3`: "the controller and view must share the same root name (in this case `Hello`), and the `HelloHTML` module must include an `embed_templates` definition specifying where its templates live", with templates by default in `lib/hello_web/controllers/hello_html/` ([Controllers](https://phoenix.hexdocs.pm/controllers.html)). The root layout is bound by module and function, `{HelloWeb.Layouts, :root}`, not by path ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). The `Web` suffix is computed: `web_module/1` returns the base module unchanged if it already ends in "Web", otherwise `"#{base}Web"` ([lib/mix/phoenix.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/mix/phoenix.ex)). The generators do fix paths: `web_path/2` returns `Path.join(["lib", "#{this_app}_web", rel_path])` and `context_lib_path/2` builds `Path.join(["lib", to_string(ctx_app), rel_path])` ([lib/mix/phoenix.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/mix/phoenix.ex)); the context struct computes `basedir = Phoenix.Naming.underscore(context_name)`, `dir = Mix.Phoenix.context_lib_path(ctx_app, basedir)` and `file = dir <> ".ex"` ([lib/mix/phoenix/context.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/mix/phoenix/context.ex)); `phx.gen.html` writes `controllers/#{singular}_controller.ex` and `controllers/#{singular}_html.ex` ([phx.gen.html.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/mix/tasks/phx.gen.html.ex)); and `phx.gen.live` writes to `Path.join([web_prefix, "live", web_path, "#{schema.singular}_live"])` ([phx.gen.live.ex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/lib/mix/tasks/phx.gen.live.ex)). So `controllers/`, `components/`, `components/layouts/` and `lib/my_app/<context>.ex` are generated by `phx.new` and the resource generators, and `live/` is generated by `phx.gen.live` but not by `phx.new` (the installer's `phx_web` templates contain only `components`, `controllers`, `endpoint.ex.eex`, `router.ex.eex` and `telemetry.ex.eex`, and the documented `phx.new` tree has no `live` directory) ([phx_web templates](https://api.github.com/repos/phoenixframework/phoenix/contents/installer/templates/phx_web), [Directory structure](https://phoenix.hexdocs.pm/directory_structure.html)).

The `MyAppWeb` module is both generated and documented as the single entrypoint: "The entrypoint for defining your web interface, such as controllers, components, channels, and so on. This can be used in your application as: use <web_namespace>, :controller, use <web_namespace>, :html. The definitions below will be executed for every controller, component, etc, so keep them short and clean, focused on imports, uses and aliases", and it defines `controller` (`use Phoenix.Controller, formats: [:html, :json]`, Gettext, `import Plug.Conn`, verified routes), `html` (`use Phoenix.Component`, a narrow `import Phoenix.Controller`, `html_helpers`), `live_view` (`use Phoenix.LiveView`, `html_helpers`), `router`, and `defmacro __using__(which) when is_atom(which), do: apply(__MODULE__, which, [])` ([app_name_web.ex.eex](https://raw.githubusercontent.com/phoenixframework/phoenix/main/installer/templates/phx_single/lib/app_name_web.ex.eex)). The Directory structure guide, the Request life cycle guide and the Controllers guide show `use HelloWeb, :controller` and `use HelloWeb, :html` without once naming `lib/hello_web.ex`; only the Components guide points at "`lib/hello_web.ex`" as where the CoreComponents import is configured ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)).

Documented as a rule, with reasons given: the `lib/hello` versus `lib/hello_web` split (Model versus View and Controller) ([Directory structure](https://phoenix.hexdocs.pm/directory_structure.html)); contexts as the place for business logic and the controller as the thin web interface ([Your first context](https://phoenix.hexdocs.pm/your_first_context.html)); the root layout as a `Layouts` function and the app frame as `Layouts.app` ([Components and HEEx](https://phoenix.hexdocs.pm/components.html)). Left to habit, with the guide saying so: what goes on inside a context, "One important benefit of contexts is that this decision does not matter much. The context is your public API, the other modules are private" ([Contexts FAQ](https://phoenix.hexdocs.pm/faq.html)); whether two resources share a context, "It's OK to have multiple resources in the same context as long as they are closely related" but "if you are unsure, you should prefer separate modules (contexts)" ([In context relationships](https://phoenix.hexdocs.pm/in_context_relationships.html)). Not said at all: where a payment client lives, where money or time formatters live, and whether the folder layout under `lib/hello_web` may be changed.

### The business layer

Django does not name a place for an operation such as "start an order". The closest statements are about models and views. The Models topic says, in its "Model methods" section, to define custom methods on a model to add what it calls row level functionality to objects, that Manager methods are for table wide things while model methods act on a particular instance, and then adds the one sentence that comes nearest to a rule: "This is a valuable technique for keeping business logic in one place" followed by the words "the model" ([Models](https://docs.djangoproject.com/en/stable/topics/db/models/#model-methods)). The Managers topic mirrors this: "Adding extra Manager methods is the preferred way to add" table level "functionality to your models", with row level functionality pointed back at model methods ([Managers](https://docs.djangoproject.com/en/stable/topics/db/managers/#adding-extra-manager-methods)). The design philosophies page states under "Models" the heading "Include all relevant domain logic" and the sentence "Models should encapsulate every aspect of an 'object,' following Martin Fowler's Active Record design pattern", explaining that both the data and information about it are defined in the model class ([Design philosophies](https://docs.djangoproject.com/en/stable/misc/design-philosophies/#models)). That is the whole of the official position on where logic belongs: the model, by Active Record.

The tutorial shows the opposite in practice. Its `vote` view loads the question with `get_object_or_404`, reads `request.POST["choice"]`, sets `selected_choice.votes = F("votes") + 1`, calls `selected_choice.save()` and returns `HttpResponseRedirect(reverse("polls:results", args=(question.id,)))`; the state change lives inside the view and the only commentary is that `F("votes") + 1` "instructs the database to increase the vote count by 1" and that one should "Always return an HttpResponseRedirect after successfully dealing with POST data" ([Tutorial 4](https://docs.djangoproject.com/en/stable/intro/tutorial04/)). No sentence in that part suggests moving the write into the model or anywhere else ([Tutorial 4](https://docs.djangoproject.com/en/stable/intro/tutorial04/)). The only custom model method the tutorial adds is `was_published_recently`, a read ([Tutorial 2](https://docs.djangoproject.com/en/stable/intro/tutorial02/)). The "Writing views" topic defines a view as "a Python function that takes a web request and returns a web response" and says of its location: "This code can live anywhere you want, as long as it's on your Python path" and "For the sake of putting the code somewhere, the convention is to put views in a file called views.py, placed in your project or application directory" ([Writing views](https://docs.djangoproject.com/en/stable/topics/http/views/)). ### The vendor integration

Stripe has no Django sample in this repository. The `server/` folder lists `dotnet`, `go`, `java`, `nextjs`, `node`, `php`, `python`, `ruby`; the README names "8 server implementations" and never mentions Django ([server/](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server), [README](https://github.com/stripe-samples/checkout-one-time-payments)). The Python server is Flask: `server/python/` contains `README.md`, `requirements.txt`, `server.py`, and the README runs it with `export FLASK_APP=server.py` and `python3 -m flask run --port=4242` ([server/python](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/python)).

One file does everything. `server.py` imports `stripe`, `json`, `os`, `flask` and `dotenv`, sets the key at module level, builds the Flask app, and defines two routes. The sequencing of "call the provider, redirect the browser" is the route function itself; there is no "create the record" step at all, because the file has no database, ORM or model import, and the webhook handler only prints on `checkout.session.completed` ([server.py](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)). The load bearing lines are:

```python
stripe.api_key = os.getenv('STRIPE_SECRET_KEY')
app = Flask(__name__, static_folder=static_dir,
            static_url_path="", template_folder=static_dir)

@app.route('/create-checkout-session', methods=['POST'])
def create_checkout_session():
    quantity = request.form.get('quantity', 1)
    domain_url = os.getenv('DOMAIN')
    try:
        checkout_session = stripe.checkout.Session.create(
            success_url=domain_url + '/success.html?session_id={CHECKOUT_SESSION_ID}',
            mode='payment',
            line_items=[{'price': os.getenv('PRICE'), 'quantity': quantity}]
        )
        return redirect(checkout_session.url, code=303)
    except Exception as e:
        return jsonify(error=str(e)), 403
```
([server.py](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py))

So `stripe.api_key` is set in `server.py`, `stripe.checkout.Session.create` is called in `server.py`, and the HTTP handler is the sequencer. The comment above the key reads "Don't put any keys in code. Use an environment variable (as shown here) or secrets vault to supply keys to your integration" ([server.py](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)). The docs.stripe.com quickstart for Python is the same shape, also Flask (`export FLASK_APP=server.py`), but uses the newer client object: `client = stripe.StripeClient('<<YOUR_SECRET_KEY>>')` followed by `checkout_session = client.v1.checkout.sessions.create(params={...})` and `return redirect(checkout_session.url, code=303)`. Its prose says "Add an endpoint on your server that creates a Checkout Session", "After creating the session, redirect your customer to the URL for the Checkout page returned in the response", and, on fulfilment, "Wait to fulfill orders (for example, shipping or sending email receipts) until the payment succeeds". It does not mention Django and does not mention saving an order record before or after creating the session ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=python)). No model imports the provider in either source, because neither source has a model.

### Shared page code

The page frame is a template that other templates extend. The template language reference says template inheritance "allows you to build a base 'skeleton' template that contains all the common elements of your site and defines blocks that child templates can override", introduces the example with "This template, which we'll call base.html, defines an HTML skeleton document" for a page with two columns, and shows the child starting with `{% extends "base.html" %}` ([Template language](https://docs.djangoproject.com/en/stable/ref/templates/language/#template-inheritance)). The same page recommends a three level approach: "Create a base.html template that holds the main" look and feel "of your site", then "a base_SECTIONNAME.html template for each 'section' of your site. For example, base_news.html, base_sports.html", then "individual templates for each type of page" ([Template language](https://docs.djangoproject.com/en/stable/ref/templates/language/#template-inheritance)). The design philosophies page gives the motive: "The Django template system should make it easy to store those elements in a single place, eliminating duplicate code. This is the philosophy behind template inheritance" ([Design philosophies](https://docs.djangoproject.com/en/stable/misc/design-philosophies/#template-system)). The name `base.html` is the docs' running example, not something the loader looks for.

Where templates live is set by configuration. The Templates topic says `DIRS` "defines a list of directories where the engine should look for template source files, in search order" and `APP_DIRS` "tells whether the engine should look for templates inside installed applications. Each backend defines a conventional name for the subdirectory inside applications where its templates should be stored", and that "When APP_DIRS is True, DjangoTemplates engines look for templates in the templates subdirectory of installed applications" ([Templates](https://docs.djangoproject.com/en/stable/topics/templates/)). Tutorial 3 applies it: "First, create a directory called templates in your polls directory. Django will look for templates in there", then argues for the extra `polls/` level because "Django will choose the first template it finds whose name matches, and if you had a template with the same name in a different application, Django would be unable to distinguish between them", so the fix is "namespacing them. That is, by putting those templates inside another directory named for the application itself" ([Tutorial 3](https://docs.djangoproject.com/en/stable/intro/tutorial03/)). Generic views bind to this layout: "By default, the DetailView generic view uses a template called <app name>/<model name>_detail.html" ([Tutorial 4](https://docs.djangoproject.com/en/stable/intro/tutorial04/)).

Small formatters are template filters, and custom ones have a fixed home. The custom tags how to says "The most common place to specify custom template tags and filters is inside a Django app", that "When a Django app is added to INSTALLED_APPS, any tags it defines in the conventional location described below are automatically made available to load within templates", and then the exact rule: "The app should contain a templatetags directory, at the same level as models.py, views.py, etc. If this doesn't already exist, create it" with a reminder about `__init__.py`. Its layout example is `polls/` holding `__init__.py`, `models.py`, `templatetags/__init__.py`, `templatetags/poll_extras.py`, `views.py`, loaded with `{% load poll_extras %}`; "The app that contains the custom tags must be in INSTALLED_APPS in order for the {% load %} tag to work" ([Custom template tags and filters](https://docs.djangoproject.com/en/stable/howto/custom-template-tags/#code-layout)). A filter is "Python functions that take one or two arguments", the value and an optional argument ([Custom template tags and filters](https://docs.djangoproject.com/en/stable/howto/custom-template-tags/#writing-custom-template-filters)).

For time and numbers the framework ships filters: `date` "Formats a date according to the given format", `timesince` "Formats a date as the time since that date (e.g., '4 days, 6 hours')", `floatformat` rounds a floating point number "to one decimal place" when used without an argument ([Built in filters](https://docs.djangoproject.com/en/stable/ref/templates/builtins/)). There is no money or currency filter in the built in set ([Built in filters](https://docs.djangoproject.com/en/stable/ref/templates/builtins/)). `django.contrib.humanize` is "A set of Django template filters useful for adding a 'human touch' to data", enabled by adding `'django.contrib.humanize'` to `INSTALLED_APPS` and `{% load humanize %}`; it provides `apnumber`, `intcomma`, `intword`, `naturalday`, `naturaltime`, `ordinal`, where `intcomma` "Converts an integer or float (or a string representation of either) to a string containing commas every three digits" and `naturaltime` "returns a string representing how many seconds, minutes or hours ago it was" ([humanize](https://docs.djangoproject.com/en/stable/ref/contrib/humanize/)). A money formatter is therefore an app's own filter in `templatetags/`.

Summary of naming: `templates/` and `templatetags/` are read by the framework (the first through `APP_DIRS`, the second through `{% load %}` discovery in `INSTALLED_APPS`); the `polls/` namespace inside `templates/` is advice the tutorial gives and generic views assume; `base.html` is a documented example name only.

### What the framework names versus what is habit

Read or generated by the framework. `models.py`: the Applications reference describes the registry's second stage as "Django attempts to import the models submodule of each application, if there is one", requires that "you must define or import all models in your application's models.py or models/__init__.py", and exposes the result as `AppConfig.models_module` ([Applications](https://docs.djangoproject.com/en/stable/ref/applications/#how-applications-are-loaded)). `admin.py`: `AdminConfig` "calls autodiscover() when Django starts" and `autodiscover()` "attempts to import an admin module in each installed application. Such modules are expected to register models with the admin" ([Admin](https://docs.djangoproject.com/en/stable/ref/contrib/admin/#django.contrib.admin.autodiscover)). `templatetags/`: discovered as quoted above ([Custom template tags and filters](https://docs.djangoproject.com/en/stable/howto/custom-template-tags/#code-layout)). `templates/`: looked up when `APP_DIRS` is `True` ([Templates](https://docs.djangoproject.com/en/stable/topics/templates/)). `migrations/`: "The migration files for each app live in a 'migrations' directory inside of that app, and are designed to be committed to, and distributed as part of, its codebase" ([Migrations](https://docs.djangoproject.com/en/stable/topics/migrations/)). `management/commands/`: "add a management/commands directory to the application. Django will register a manage.py command for each Python module in that directory whose name doesn't begin with an underscore" ([Custom management commands](https://docs.djangoproject.com/en/stable/howto/custom-management-commands/)). `apps.py`: generated by `startapp`, and `INSTALLED_APPS` entries are "a dotted Python path to: an application configuration class (preferred), or a package containing an application" ([Tutorial 2](https://docs.djangoproject.com/en/stable/intro/tutorial02/), [Settings reference](https://docs.djangoproject.com/en/stable/ref/settings/#installed-apps)). `settings.py`: generated by `startproject` and named by `DJANGO_SETTINGS_MODULE` ([Settings](https://docs.djangoproject.com/en/stable/topics/settings/)).

Named by setting, not by file name. `urls.py` is the generated name in the project package, but what Django reads is `ROOT_URLCONF`, "A string representing the full Python import path to your root URLconf"; the URL dispatcher "determines the root URLconf module to use. Ordinarily, this is the value of the ROOT_URLCONF setting" and then "looks for the variable urlpatterns" ([Settings reference](https://docs.djangoproject.com/en/stable/ref/settings/#root-urlconf), [URL dispatcher](https://docs.djangoproject.com/en/stable/topics/http/urls/#how-django-processes-a-request)). The app level `polls/urls.py` is not generated: tutorial 1 says "To define a URLconf for the polls app, create a file polls/urls.py", wired in by `include()` ([Tutorial 1](https://docs.djangoproject.com/en/stable/intro/tutorial01/)). `views.py` is generated but, per the Writing views topic, the view code "can live anywhere you want"; the file name is "the convention" only ([Writing views](https://docs.djangoproject.com/en/stable/topics/http/views/)).

Habit only. `forms.py` is not in the app template on `main` ([app_template](https://github.com/django/django/tree/main/django/conf/app_template)); the Forms topic labels its example code block `forms.py` but gives no sentence making that a rule ([Forms](https://docs.djangoproject.com/en/stable/topics/forms/)). `services.py` and `selectors.py` appear nowhere on the site; the search for `services.py` returns "0 results" ([search](https://docs.djangoproject.com/en/stable/search/?q=services.py)), and `selectors.py` was not searched (not verified). `base.html` is an example name in the inheritance docs and is not looked up by anything ([Template language](https://docs.djangoproject.com/en/stable/ref/templates/language/#template-inheritance)). The Applications reference lists what an app may hold, "some combination of models, views, templates, template tags, static files, URLs, middleware, etc.", and that list is the full official vocabulary; a business or service layer is not in it ([Applications](https://docs.djangoproject.com/en/stable/ref/applications/)).

### The vendor integration

In Cashier's documented Checkout, the route closure sequences the operation: it calls `checkout` on the authenticated user and returns the result, and the return value is itself the redirect. The Product Checkouts example is:

```php
Route::get('/checkout', function (Request $request) {
    $stripePriceId = 'price_deluxe_album';
    $quantity = 1;

    return $request->user()->checkout([$stripePriceId => $quantity], [
        'success_url' => route('checkout-success'),
        'cancel_url' => route('checkout-cancel'),
    ]);
})->name('checkout');
```

([Laravel Cashier (Stripe), Product Checkouts](https://laravel.com/docs/12.x/billing#product-checkouts)). The doc explains "we will utilize Cashier's provided checkout method to redirect the customer to Stripe Checkout for a given "price identifier"" and "If necessary, the checkout method will automatically create a customer in Stripe and connect that Stripe customer record to the corresponding user in your application's database" ([Laravel Cashier (Stripe)](https://laravel.com/docs/12.x/billing)). The variant for a single charge is `return $request->user()->checkoutCharge(1200, 'T-Shirt', 5, ['success_url' => ..., 'cancel_url' => ...]);` ([Laravel Cashier (Stripe), Single Charge Checkouts](https://laravel.com/docs/12.x/billing#single-charge-checkouts)), and for a visitor without an account `Checkout::guest()->chargeProduct('price_tshirt', 5, [...])` ([Laravel Cashier (Stripe), Guest Checkouts](https://laravel.com/docs/12.x/billing#guest-checkouts)). Writing the order is not part of the documented sequence: the example writes nothing to the application database before redirecting, except for the Stripe customer link that `checkout` creates on the user.

The redirect is produced by the returned object. In source, `checkout()` on the `PerformsCharges` concern returns `Checkout::customer($this, $this)->create($items, $sessionOptions, $customerOptions)`, and `checkoutCharge()` builds `price_data` with `unit_amount_decimal` and the model's `preferredCurrency()` and delegates to `checkout()` ([PerformsCharges.php](https://raw.githubusercontent.com/laravel/cashier-stripe/16.x/src/Concerns/PerformsCharges.php)). `Laravel\Cashier\Checkout` implements `Responsable`; its `toResponse($request)` returns `$this->redirect()`, which is `Redirect::to($this->session->url, 303)` ([Checkout.php](https://raw.githubusercontent.com/laravel/cashier-stripe/16.x/src/Checkout.php)). That is why the route can return the `Checkout` directly.

The provider client lives on the `User` model. The doc says "Cashier assumes your billable model will be the App\Models\User class that ships with Laravel" and shows `use Laravel\Cashier\Billable; class User extends Authenticatable { use Billable; }`, with `Cashier::useCustomerModel(User::class)` in `AppServiceProvider::boot` to change it ([Laravel Cashier (Stripe), Billable Model](https://laravel.com/docs/12.x/billing#billable-model)). The `Billable` trait composes `HandlesTaxes`, `ManagesCustomer`, `ManagesInvoices`, `ManagesPaymentMethods`, `ManagesSubscriptions`, `ManagesUsageBilling` and `PerformsCharges` ([Billable.php](https://raw.githubusercontent.com/laravel/cashier-stripe/16.x/src/Billable.php)). So the Stripe calls are reached through methods on the Eloquent `User` model. The model file itself does not import Stripe: the documented `User` imports only `Laravel\Cashier\Billable` ([Laravel Cashier (Stripe)](https://laravel.com/docs/12.x/billing)); the `use Stripe\StripeClient` import sits in `Laravel\Cashier\Cashier`, whose `stripe()` method builds the client with `'api_key' => $options['api_key'] ?? config('cashier.secret')` and `app(StripeClient::class, ['config' => $config])` ([Cashier.php](https://raw.githubusercontent.com/laravel/cashier-stripe/16.x/src/Cashier.php)). Keys come from `.env` as `STRIPE_KEY`, `STRIPE_SECRET` and `STRIPE_WEBHOOK_SECRET` ([Laravel Cashier (Stripe), API Keys](https://laravel.com/docs/12.x/billing#api-keys)), read by `config/cashier.php` as `'key' => env('STRIPE_KEY')`, `'secret' => env('STRIPE_SECRET')` and `'webhook' => ['secret' => env('STRIPE_WEBHOOK_SECRET'), ...]` ([config/cashier.php](https://raw.githubusercontent.com/laravel/cashier-stripe/16.x/config/cashier.php)); the file is published with `php artisan vendor:publish --tag="cashier-config"` ([Laravel Cashier (Stripe)](https://laravel.com/docs/12.x/billing)). The doc also states "Cashier exposes the underlying Stripe SDK client via the Cashier::stripe() method. You may use this method to access the Stripe client for any functionality that Cashier does not directly support" ([Laravel Cashier (Stripe), Stripe SDK](https://laravel.com/docs/12.x/billing#stripe-sdk)).

Stripe's own PHP sample is plain PHP, not a framework. Its `composer.json` requires only `stripe/stripe-php` and `vlucas/phpdotenv` and starts with `php -S 0.0.0.0:4242 -t public` ([server/php/composer.json](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/php/composer.json)); the README says to run `composer install`, then `cd public` and `php -S localhost:4242` ([server/php/README.md](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/php/README.md)). The web root `public/` holds `create-checkout-session.php`, `get-checkout-session.php`, `shared.php`, `webhook.php`, `index.html`, `success.html`, `script.js` and `css` ([server/php/public](https://api.github.com/repos/stripe-samples/checkout-one-time-payments/contents/server/php/public)). The key is set and the Session created in the same script: `create-checkout-session.php` requires `../vendor/autoload.php`, loads `.env` with Dotenv, calls `\Stripe\Stripe::setApiKey($_ENV['STRIPE_SECRET_KEY'])`, then `\Stripe\Checkout\Session::create([... 'mode' => 'payment', 'line_items' => [[...]]])` and ends with `header("HTTP/1.1 303 See Other"); header("Location: " . $checkout_session->url);` ([create-checkout-session.php](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/php/public/create-checkout-session.php)). `shared.php` repeats the autoload and a `\Stripe\Stripe::setApiKey(...)` call of its own, reading `config.ini` rather than `.env` ([shared.php](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/php/public/shared.php)). Stripe's Checkout quickstart for PHP shows the newer client style in one script: `$stripe = new \Stripe\StripeClient($stripeSecretKey);`, `$checkout_session = $stripe->checkout->sessions->create([...]);`, then `header("HTTP/1.1 303 See Other"); header("Location: " . $checkout_session->url);`, with `$stripeSecretKey = '<<YOUR_SECRET_KEY>>';` set in the server code, a form posting to `/checkout.php`, and the server run as `php -S 127.0.0.1:4242 --docroot=public` ([Stripe Checkout quickstart, PHP](https://docs.stripe.com/checkout/quickstart?lang=php)). In both Stripe sources the one request script owns the key, the provider call and the redirect; there is no model and no separate client file.

### Shared page code

Views live in `resources/views`: "Views separate your controller / application logic from your presentation logic and are stored in the resources/views directory", files carry the `.blade.php` extension, `php artisan make:view greeting` creates one, and subdirectories are addressed with dots, so `resources/views/admin/profile.blade.php` is `view('admin.profile')`; "View directory names should not contain the . character" ([Views](https://laravel.com/docs/12.x/views)). The page frame is documented two ways. With components, the layout is `resources/views/components/layout.blade.php` containing `{{ $slot }}`, used from `resources/views/tasks.blade.php` as `<x-layout>...</x-layout>` with an optional `<x-slot:title>` ([Blade Templates, Layouts Using Components](https://laravel.com/docs/12.x/blade#layouts-using-components)). With template inheritance, the layout is `resources/views/layouts/app.blade.php` using `@yield('title')`, `@section('sidebar') ... @show` and `@yield('content')`, and the child view starts with `@extends('layouts.app')`; the doc notes this "was the primary way of building applications prior to the introduction of components" ([Blade Templates, Layouts Using Template Inheritance](https://laravel.com/docs/12.x/blade#layouts-using-template-inheritance)). Smaller shared fragments are components: `php artisan make:component Alert` writes the class to `app/View/Components` and the view to `resources/views/components`; `php artisan make:component forms.input --view` writes an anonymous component at `resources/views/components/forms/input.blade.php` rendered as `<x-forms.input />`; "components are automatically discovered within the app/View/Components directory and resources/views/components directory, so no further component registration is typically required", and extra anonymous component paths can be added with `Blade::anonymousComponentPath` in a provider's `boot` ([Blade Templates, Components](https://laravel.com/docs/12.x/blade#components); [Anonymous Components](https://laravel.com/docs/12.x/blade#anonymous-components)). Data shared by every view goes through `View::share('key', 'value')` in `AppServiceProvider::boot` or a view composer ([Views](https://laravel.com/docs/12.x/views)).

Money and time formatting are framework utilities, not application files. `Number::currency(1000)` yields `$1,000.00`, with `in: 'EUR'`, `locale: 'de'` and `precision: 0` variants, and `Number::format(100000)` yields `100,000` with `precision`, `maxPrecision` and `locale` arguments ([Helpers, Numbers](https://laravel.com/docs/12.x/helpers#numbers)). For time, the Helpers page's "Dates and Time" subsection says "Laravel includes Carbon, a powerful date and time manipulation library", that `now()` is "globally available within your Laravel application", that `Illuminate\Support\Carbon` can be used directly, that Laravel adds `plus` and `minus` methods, and it defers the rest to "the official Carbon documentation"; `now()` and `today()` are also listed under Miscellaneous as creating `Illuminate\Support\Carbon` instances ([Helpers](https://laravel.com/docs/12.x/helpers); [helpers.md source](https://raw.githubusercontent.com/laravel/docs/12.x/helpers.md)). `diffForHumans` is a Carbon method and is not mentioned on the Laravel Helpers page (not verified against Carbon's own documentation, which was not fetched).

Laravel documents no place for custom helper functions. The Helpers page introduces "a variety of global "helper" PHP functions" that "you are free to use" and contains no sentence about writing your own, no `helpers.php`, and no `composer.json` `autoload` `files` entry ([Helpers](https://laravel.com/docs/12.x/helpers); [helpers.md source](https://raw.githubusercontent.com/laravel/docs/12.x/helpers.md)); the skeleton's `composer.json` has no `files` key either ([laravel/laravel composer.json](https://raw.githubusercontent.com/laravel/laravel/12.x/composer.json)). So the names are split: `resources/views` is read by the framework and named in the docs, `resources/views/components` and `app/View/Components` are discovery paths named in the docs, while `layouts` appears only as the example path `resources/views/layouts/app.blade.php` and is a habit the docs model rather than a path the framework reads ([Blade Templates](https://laravel.com/docs/12.x/blade)).

### What the framework names versus what is habit

Named by the framework, either read, generated or documented as a rule: the `app` directory "is namespaced under App and is autoloaded by Composer using the PSR-4 autoloading standard", so any folder under `app/` works once Composer can autoload it ([Directory Structure](https://laravel.com/docs/12.x/structure); [laravel/laravel composer.json](https://raw.githubusercontent.com/laravel/laravel/12.x/composer.json)). `resources/views` is where the `view()` helper resolves names and where `make:view` writes ([Views](https://laravel.com/docs/12.x/views)). `App\Models` is the generator default when the `Models` directory exists ([ModelMakeCommand.php](https://raw.githubusercontent.com/laravel/framework/12.x/src/Illuminate/Foundation/Console/ModelMakeCommand.php)) and the anchor for policy discovery: "the policies must be in a Policies directory at or above the directory that contains your models. So, for example, the models may be placed in the app/Models directory while the policies may be placed in the app/Policies directory. In this situation, Laravel will check for policies in app/Models/Policies then app/Policies. In addition, the policy name must match the model name and have a Policy suffix", overridable with `Gate::guessPolicyNamesUsing`, `Gate::policy` or the `#[UsePolicy]` attribute ([Authorization, Policy Discovery](https://laravel.com/docs/12.x/authorization#policy-discovery)); `make:policy` writes to `app/Policies` and creates it if missing ([Authorization](https://laravel.com/docs/12.x/authorization)). `App\Http\Controllers` is the `make:controller` default ([ControllerMakeCommand.php](https://raw.githubusercontent.com/laravel/framework/12.x/src/Illuminate/Routing/Console/ControllerMakeCommand.php); [Controllers](https://laravel.com/docs/12.x/controllers)). `App\Providers` holds providers registered in `bootstrap/providers.php`, which `make:provider` edits automatically ([Service Providers](https://laravel.com/docs/12.x/providers)). Event listeners are discovered "by scanning your application's Listeners directory" for methods beginning with `handle` or `__invoke`, and `app/Events` and `app/Listeners` are created by `make:event` and `make:listener` ([Events](https://laravel.com/docs/12.x/events)). Artisan "automatically registers all commands within the app/Console/Commands directory", with `withCommands` in `bootstrap/app.php` for other paths ([Artisan Console](https://laravel.com/docs/12.x/artisan)). Blade components are discovered in `app/View/Components` and `resources/views/components` ([Blade Templates](https://laravel.com/docs/12.x/blade)). The other optional `app` subdirectories named by the Directory Structure page (`Broadcasting`, `Console`, `Exceptions`, `Jobs`, `Mail`, `Notifications`, `Rules`) each exist because a `make` command creates them ([Directory Structure](https://laravel.com/docs/12.x/structure)).

Habit only: `app/Services`, `app/Repositories`, `app/Support` and `app/Contracts` appear in the docs solely as namespaces inside code examples (`App\Services\AppleMusic`, `App\Services\Transistor`, `App\Repositories\UserRepository`, `App\Support\DripEmailer`, `App\Contracts\EventPusher`) and are never listed by the Directory Structure page, never created by the skeleton and never targeted by a `make` command ([Service Container](https://laravel.com/docs/12.x/container); [Controllers](https://laravel.com/docs/12.x/controllers); [Artisan Console](https://laravel.com/docs/12.x/artisan); [Directory Structure](https://laravel.com/docs/12.x/structure); [laravel/laravel app](https://api.github.com/repos/laravel/laravel/contents/app?ref=12.x)). `app/Actions` and `app/helpers.php` appear in none of the fetched pages or source files. The `layouts` view folder is an example path in the Blade doc, not a path the framework reads ([Blade Templates](https://laravel.com/docs/12.x/blade)). The framework's own summary of the rule is the intro sentence that Laravel "imposes almost no restrictions on where any given class is located" provided Composer can autoload it ([Directory Structure](https://laravel.com/docs/12.x/structure)).

### The vendor integration

Stripe publishes no Play or Scala sample. The Java sample therefore has no layer at all: the route lambda holds the Stripe call and the redirect.

Play's own documented pattern for a provider client is a component bound through dependency injection. The Dependency Injection page says: "Sometimes you may have a component that holds some state, such as a cache, or a connection to an external resource, or a component might be expensive to create", and shows the `@Singleton` annotation for that case; it shows `app`'s root package `Module extends AbstractModule` with `bind(classOf[Hello]).annotatedWith(Names.named("en")).to(classOf[EnglishHello])`, and states "If you call this module `Module` and place it in the root package, it will automatically be registered with Play. Alternatively, if you want to give it a different name or put it in a different package, you can register it with Play by appending its fully qualified class name to the `play.modules.enabled` list in `application.conf`" ([Dependency Injection](https://www.playframework.com/documentation/3.0.x/ScalaDependencyInjection)). The starter sample's `app/Module.scala` does exactly this, binding `Clock` to an instance, `ApplicationTimer` as an eager singleton and `Counter` to `AtomicCounter`, with the comment "Play will automatically use any class called `Module` that is in the root package" ([Module.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-starter-example/app/Module.scala)). Compile time DI replaces the module with a components class: "compile time DI can be achieved by manually constructing and wiring dependencies", with `class MyComponents(context: Context) extends BuiltInComponentsFromContext(context)` holding `lazy val applicationController = new controllers.Application(controllerComponents)` and `lazy val router` ([Compile Time Dependency Injection](https://www.playframework.com/documentation/3.0.x/ScalaCompileTimeDependencyInjection)).

The documented way to call an external HTTP API is `WSClient`, and the page's example injects it into a controller: `class Application @Inject() (ws: WSClient, val controllerComponents: ControllerComponents) extends BaseController {}`, followed by "When making a request from a controller, you can map the response to a `Future[Result]`. This can be used in combination with Play's `Action.async` action builder" and `def wsAction = Action.async { ws.url(url).get().map { response => Ok(response.body) } }` ([Calling REST APIs with Play WS](https://www.playframework.com/documentation/3.0.x/ScalaWS)). The page also says that "any component that wants to use WS will have to declare a dependency on the `WSClient`" (paraphrased by the fetch; wording not verified verbatim), and that outside Play "you can use the standalone version of Play WS". Configuration follows the same injection route: "Typically, you'll obtain a `Configuration` object through Dependency Injection, or simply by passing an instance of `Configuration` to your component", shown as `class MyController @Inject() (config: Configuration, c: ControllerComponents) extends AbstractController(c)` reading `config.get[String]("foo")` ([Configuration](https://www.playframework.com/documentation/3.0.x/ScalaConfig)); the Anatomy page names `conf/application.conf` as "the main configuration file for the application" ([Anatomy](https://www.playframework.com/documentation/3.0.x/Anatomy)). A Stripe secret key would by these pages live in `conf/application.conf` and be read by an injected `Configuration`; the docs do not say whether the reader is the controller or a separate class, because both WS and Configuration examples inject into a controller.

On sequencing: no Play page describes a write, then external call, then redirect sequence. In the documented pattern and in every sample fetched, the Action in the controller is the sequencer: the slick `addPerson` action binds the form, calls `repo.create`, then returns `Redirect(...).flashing(...)` ([PersonController.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-slick-example/samples/person/app/controllers/PersonController.scala)), and the anorm `save` action does the same with `computerService.insert` and `Home.flashing` ([HomeController.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-anorm-example/app/controllers/HomeController.scala)). The one sample with an intermediate class, `PostResourceHandler`, still sequences only repository calls and link building, and the Action still owns the HTTP result ([PostResourceHandler.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-rest-api-example/app/v1/post/PostResourceHandler.scala)). No model in the samples fetched imports an external client: `PersonRepository` imports `play.api.db.slick.DatabaseConfigProvider` and `slick.jdbc.JdbcProfile` ([PersonRepository.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-slick-example/samples/person/app/models/PersonRepository.scala)), `ComputerRepository` imports `anorm._` and `play.api.db.DBApi` ([ComputerRepository.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-anorm-example/app/models/ComputerRepository.scala)), and `PostRepositoryImpl` imports only Pekko, Play and standard library classes ([PostRepository.scala](https://raw.githubusercontent.com/playframework/play-samples/3.0.x/play-scala-rest-api-example/app/v1/post/PostRepository.scala)). The only external client in the docs, `WSClient`, is shown injected into a controller.

### Shared page code

Templates are Twirl files that compile to Scala objects named after their folder path. The Templates page: "Play comes with Twirl, a powerful Scala-based template engine, whose design was inspired by ASP.NET Razor", "Templates are compiled as standard Scala functions, following a simple naming convention. If you create a `views/Application/index.scala.html` template file, it will generate a `views.html.Application.index` class that has an `apply()` method", and "You can then call this from any Scala code as you would normally call a method on a class: `val content = views.html.Application.index(c, o)`" ([Templates](https://www.playframework.com/documentation/3.0.x/ScalaTemplates)). The page frame is a template with a second parameter group taking `Html`: the Use Cases page's "Layout" section shows `views/main.scala.html` declared `@(title: String)(content: Html)` rendering `<section class="content">@content</section>`, called from `views/Application/index.scala.html` as `@main(title = "Home") { <h1>Home page</h1> }`; it extends this to `@(title: String)(sidebar: Html)(content: Html)` and to `@(title: String, scripts: Html = Html(""))(content: Html)` for optional script blocks ([Template use cases](https://www.playframework.com/documentation/3.0.x/ScalaTemplateUseCases)). The seed's `app/views/main.scala.html` follows that convention verbatim: `@(title: String)(content: Html)` with a comment that it "handles the rendering of the page header and body tags" and links through `@routes.Assets.versioned("stylesheets/main.css")` ([main.scala.html](https://raw.githubusercontent.com/playframework/play-scala-seed.g8/3.0.x/src/main/g8/app/views/main.scala.html)), and `app/views/index.scala.html` is `@()` then `@main("Welcome to Play") { <h1>Welcome to Play!</h1> }` ([index.scala.html](https://raw.githubusercontent.com/playframework/play-scala-seed.g8/3.0.x/src/main/g8/app/views/index.scala.html)).

Small reusable pieces have two documented homes. Inside a template, "Declaring reusable blocks" shows `@display(product: Product) = { ... }` and a pure code block `@title(text: String) = @{ text.split(' ').map(_.capitalize).mkString(" ") }`, and "Declaring reusable values" shows `@defining(...) { fullName => ... }`; imports go after the parameters, `@import utils._`, with `_root_` for absolute paths and `TwirlKeys.templateImports += "org.abc.backend._"` in `build.sbt` for imports shared by all templates ([Templates](https://www.playframework.com/documentation/3.0.x/ScalaTemplates)). Across templates, the "Tags" section puts a reusable fragment in `views/tags/notice.scala.html` declared `@(level: String = "error")(body: (String) => Html)` and used after `@import tags._` as `@notice("error") { color => ... }`, and the "Includes" section calls `@common.sideBar()` ([Template use cases](https://www.playframework.com/documentation/3.0.x/ScalaTemplateUseCases)). Play's own form helpers live in the `views.html.helper` package: "You can find several input helpers in the `views.html.helper` package", "You can use `@import helper._` in the template to avoid prefixing helpers with `@helper.`", "The source code for each of these templates is defined as Twirl templates under `views/helper` package", and "For complex form elements, you can also create your own custom view helpers (using scala classes in the `views` package) and custom field constructors" ([Forms](https://www.playframework.com/documentation/3.0.x/ScalaForms)). No page fetched names a folder for money or time formatters; the documented options are a reusable block inside a template, a tag template under `views/<subfolder>`, a Scala object imported with `@import`, or a Scala class in the `views` package. The `utils._` import in the Templates page is an example package name, not a convention the framework reads.

Who gives the names: `views.html.*` follows from the folder path, since the generated package mirrors the directory and the `html` segment comes from the file extension ([Templates](https://www.playframework.com/documentation/3.0.x/ScalaTemplates)). The Play sbt layout does not single out `app/views`: `PlayLayoutPlugin` sets `Compile / TwirlKeys.compileTemplates / sourceDirectories := Seq((Compile / sourceDirectory).value)` where `Compile / sourceDirectory := baseDirectory.value / "app"`, so every `.scala.html` anywhere under `app` is compiled and the `views` package name is produced by the convention of placing templates in `app/views` ([PlayLayoutPlugin.scala](https://github.com/playframework/playframework/blob/main/dev-mode/sbt-plugin/src/main/scala/play/sbt/PlayLayoutPlugin.scala)). Outside Play, Twirl's own README says "Twirl template files are expected to be placed under `src/main/twirl` or `src/test/twirl`" ([Twirl README](https://github.com/playframework/twirl/blob/main/README.md)). The name `main` for the layout is a habit the docs and the seed share; nothing in the framework reads it. `helper` is a framework name, since `views.html.helper` ships with Play.

### What the framework names versus what is habit

The framework reads one source root and one resource root. `PlayLayoutPlugin`, whose doc comment calls it the "Play layout plugin to switch to the traditional Play web app layout instead of the standard Maven layout" and which "is enabled automatically with the PlayWeb plugin", sets `Compile / sourceDirectory`, `Compile / scalaSource` and `Compile / javaSource` to `baseDirectory.value / "app"`, the `Test` equivalents to `"test"`, `Compile / resourceDirectory` to `"conf"`, the Twirl template source directories to the `Compile` source directory, `Assets / sourceDirectory` to `(Compile / sourceDirectory).value / "assets"`, `Assets / resourceDirectory` to `baseDirectory.value / "public"` and `Universal / sourceDirectory` to `"dist"` ([PlayLayoutPlugin.scala](https://github.com/playframework/playframework/blob/main/dev-mode/sbt-plugin/src/main/scala/play/sbt/PlayLayoutPlugin.scala)). The Anatomy page states the same in prose: "The `app` directory contains all executable artifacts: Java and Scala source code, templates and compiled assets' sources", with "an optional directory called `app/assets` for compiled assets such as LESS sources and CoffeeScript sources"; "Resources stored in the `public` directory are static assets that are served directly by the Web server"; and "The `conf` directory contains the application's configuration files. There are two main configuration files: `application.conf` is the main configuration file for the application; `routes` is the routers' definition file" ([Anatomy](https://www.playframework.com/documentation/3.0.x/Anatomy)). The Build Overview lists `/app` as "Where your application code will be stored", `/conf`, `/public` and `/test`, and says the Play sbt plugin adds "support for Play-specific features such as the twirl compiler and the routes compiler" ([Build overview](https://www.playframework.com/documentation/3.0.x/BuildOverview)). The sub projects page shows the Play layout `app`, `conf`, `public` beside a library sub project with `src/main/java` and `src/main/scala`, and adds that "there must be only one `application.conf` file and only one `routes` file" ([sbt sub projects](https://www.playframework.com/documentation/3.0.x/sbtSubProjects)).

Routes are a rule: "Routes are defined in the `conf/routes` file, which is compiled. This means that you'll see route errors directly in your browser", and the call "must define a valid call to a method returning a `play.api.mvc.Action` value, which will typically be a controller action method", written as "the fully-qualified method name: `GET / controllers.Application.homePage()`" ([Routing](https://www.playframework.com/documentation/3.0.x/ScalaRouting)). The page does not state that `controllers` is a default package; every example is fully qualified, and the reverse router mirrors whatever package the controller is in: "There is a `routes` subpackage for each controller package" ([Routing](https://www.playframework.com/documentation/3.0.x/ScalaRouting)). The seed's `conf/routes` has `GET / controllers.HomeController.index()` and `GET /assets/*file controllers.Assets.versioned(path="/public", file: Asset)` ([routes](https://raw.githubusercontent.com/playframework/play-scala-seed.g8/3.0.x/src/main/g8/conf/routes)); the Assets page confirms "By convention public assets are stored in the `public` folder of your application" and that "Play comes with a built-in controller to serve public assets" ([Assets](https://www.playframework.com/documentation/3.0.x/AssetsOverview)). So `controllers.Assets` is a framework name, while `controllers` for the application's own classes is a convention the Anatomy page says "can be changed if needed".

The folders that are only habit are the three MVC packages and anything beside them. The Anatomy page's own words: "the `controllers`, `models`, and `views` package names are simply conventions that can be changed if needed (such as prefixing everything with `com.yourcompany`)" and "You can add your own packages, for example, an `app/services` package" ([Anatomy](https://www.playframework.com/documentation/3.0.x/Anatomy)). Of these, `views` has the strongest pull because the generated object name `views.html.X` follows the folder, so moving templates changes every call site ([Templates](https://www.playframework.com/documentation/3.0.x/ScalaTemplates)). `app/models` appears in the slick and anorm samples as the home of repositories, `app/services` in the starter sample as the home of an injected trait and its `@Singleton` implementation, `app/repositories` in none of the samples fetched, and the rest api sample uses neither, packaging controller, repository, handler and router together under `app/v1/post` ([v1/post listing](https://api.github.com/repos/playframework/play-samples/contents/play-scala-rest-api-example/app/v1/post?ref=3.0.x)). The sbt plugin reads none of these names; it compiles whatever is under `app`.

### The business layer

The Spring Boot reference never says where an operation such as "start an order" lives. The closest it comes is the package layout in Structuring Your Code, introduced by one sentence, "The following listing shows a typical layout:", with no sentence assigning responsibilities to any file in it ([Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)). The only statement of what a service is comes from the Spring Framework, not from Boot. The reference says `@Repository`, `@Service` and `@Controller` "are specializations of @Component for more specific use cases (in the persistence, service, and presentation layers, respectively)" and that "if you are choosing between using @Component or @Service for your service layer, @Service is clearly the better choice" ([Classpath Scanning and Managed Components](https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html)). The `@Service` javadoc defines the stereotype by borrowing from Evans: a Service is "an operation offered as an interface that stands alone in the model, with no encapsulated state", and the class "May also indicate that a class is a "Business Service Facade"" in the Core J2EE patterns sense; it closes by saying the annotation is a general purpose stereotype whose semantics individual teams may narrow as they see fit ([Service javadoc](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/stereotype/Service.html)). Boot's own dependency injection page shows a `@Service public class MyAccountService implements AccountService` that takes a `RiskAssessor` through its constructor, and only comments on constructor injection making the field `final` ([Spring Beans and Dependency Injection](https://docs.spring.io/spring-boot/reference/using/spring-beans-and-dependency-injection.html)).

Serving Web Content has one `@Controller GreetingController` in `com.example.servingwebcontent` that puts a request parameter into the `Model` and returns the view name `greeting` ([Serving Web Content with Spring MVC](https://spring.io/guides/gs/serving-web-content)). Accessing Data with JPA has a `@Entity Customer`, a `CustomerRepository extends CrudRepository<Customer, Long>`, both in `com.example.accessingdatajpa`, and a `CommandLineRunner` `@Bean` in the application class that calls `save`, `findAll`, `findById` and `findByLastName` directly; no `@Service` appears ([Accessing Data with JPA](https://spring.io/guides/gs/accessing-data-jpa)). Building REST services with Spring has `@RestController class EmployeeController` in package `payroll` whose constructor takes an `EmployeeRepository`, and the tutorial states "An `EmployeeRepository` is injected by constructor into the controller"; no `@Service` appears anywhere in it ([Building REST services with Spring](https://spring.io/guides/tutorials/rest), [EmployeeController.java](https://github.com/spring-guides/tut-rest/blob/main/rest/src/main/java/payroll/EmployeeController.java)). ### The vendor integration

Stripe's documented Java sample for Checkout is a single file, `server/java/src/main/java/com/stripe/sample/Server.java`, written against Spark Java, not Spring: the imports are `import static spark.Spark.get; import static spark.Spark.post; import static spark.Spark.port; import static spark.Spark.staticFiles;` ([Server.java](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/java/src/main/java/com/stripe/sample/Server.java)), and the `pom.xml` lists `com.sparkjava:spark-core`, `com.stripe:stripe-java`, `com.google.code.gson:gson`, `io.github.cdimascio:java-dotenv`, `org.slf4j:slf4j-simple` and `org.apache.httpcomponents:httpclient`, with no Spring artifact and no database driver ([pom.xml](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/java/pom.xml)). The provider client is configured in that same file by the static assignment `Stripe.apiKey = dotenv.get("STRIPE_SECRET_KEY");`. The sequencing of "call the provider, redirect the browser" happens inside the route lambda, and there is no "create the record" step because the sample persists nothing:

```java
post("/create-checkout-session", (request, response) -> {
    String domainUrl = dotenv.get("DOMAIN");
    Long quantity = Long.parseLong(request.queryParams("quantity"));
    String price = dotenv.get("PRICE");

    SessionCreateParams.Builder builder = new SessionCreateParams.Builder()
            .setSuccessUrl(domainUrl + "/success.html?session_id={CHECKOUT_SESSION_ID}")
            .setMode(SessionCreateParams.Mode.PAYMENT);

    LineItem item = new LineItem.Builder().setQuantity(quantity).setPrice(price).build();
    builder.addLineItem(item);

    SessionCreateParams createParams = builder.build();
    Session session = Session.create(createParams);

    response.redirect(session.getUrl(), 303);
    return "";
});
```

([Server.java](https://github.com/stripe-samples/checkout-one-time-payments/blob/main/server/java/src/main/java/com/stripe/sample/Server.java)). No entity imports the provider because the sample has no entity; the only domain fact, the price, is an environment variable. The webhook route in the same file verifies the signature with `Webhook.constructEvent` and prints "Payment succeeded!" on `checkout.session.completed`. The README runs it with `java -cp target/sample-jar-with-dependencies.jar com.stripe.sample.Server` ([server/java](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/java)). The repository offers eight servers, `dotnet`, `go`, `java`, `nextjs`, `node`, `php`, `python`, `ruby` ([server](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server)). The docs.stripe.com quickstart for Java shows the newer client style, `StripeClient client = new StripeClient("<<YOUR_SECRET_KEY>>");`, builds `SessionCreateParams.builder()...build()`, and ends the handler with `response.redirect(session.getUrl(), 303); return "";`, the same Spark idiom and the same run command naming `com.stripe.sample.Server`; the import lines were not present in the fetched text, so the framework of the quickstart file is inferred from the idiom (not verified) ([Checkout quickstart, Java](https://docs.stripe.com/checkout/quickstart?lang=java)). The quickstart describes the flow in prose as: add an endpoint that creates a Checkout Session, "After creating the session, redirect your customer to the URL for the Checkout page returned in the response", then a success page, and "Wait to fulfill orders ... until the payment succeeds" ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=java)).

The other Java sample checked, accept-a-payment `custom-payment-flow/server/java`, is also Spark, with the same `com.stripe.sample.Server` and `Stripe.apiKey = dotenv.get("STRIPE_SECRET_KEY");` ([Server.java](https://github.com/stripe-samples/accept-a-payment/blob/main/custom-payment-flow/server/java/src/main/java/com/stripe/sample/Server.java)). A search of the stripe-samples organisation's repositories for "spring" returns "No repositories matched your search" ([stripe-samples repositories](https://github.com/orgs/stripe-samples/repositories?q=spring)); GitHub code search requires sign in and could not be run, so the absence of a Spring Boot sample is verified only at repository name and description level (not verified beyond that).

By Spring Boot's documented patterns, there is no page that says where a third party SDK client lives. What the docs do say: `@SpringBootApplication` includes `@SpringBootConfiguration`, which exists to "enable registration of extra beans in the context or the import of additional configuration classes" ([Using the @SpringBootApplication Annotation](https://docs.spring.io/spring-boot/reference/using/using-the-springbootapplication-annotation.html)). For keys, Externalized Configuration lets "strongly typed beans govern and validate the configuration of your application" with `@ConfigurationProperties("my.service") public class MyProperties`, registered either per class with `@Configuration(proxyBeanMethods = false) @EnableConfigurationProperties(SomeProperties.class)` or by `@ConfigurationPropertiesScan`, which "Typically ... is added to the main application class" ([Externalized Configuration](https://docs.spring.io/spring-boot/reference/features/external-config.html)). For HTTP clients, Calling REST Services says Boot creates and configures a prototype `RestClient.Builder` bean, and that it provides no single auto configured `RestTemplate` bean but does auto configure a `RestTemplateBuilder`; both examples are a `@Service public class MyService` that builds the client in its own constructor, not a `@Bean` in a `@Configuration` class, and the page says nothing about which package such a class belongs in ([Calling REST Services](https://docs.spring.io/spring-boot/reference/io/rest-client.html)). Nothing in these pages mentions a payment provider or an SDK with a static API key; whether `Stripe.apiKey` is set in a `@Configuration`, a `@Service` or the main class is left to the application.

### Shared page code

Spring Boot names two folders and reads them by auto configuration. For templates: "When you use one of these templating engines with the default configuration, your templates are picked up automatically from `src/main/resources/templates`", the engines being FreeMarker, Groovy, Thymeleaf and Mustache ([Servlet Web Applications, Template Engines](https://docs.spring.io/spring-boot/reference/web/servlet.html)). The Thymeleaf defaults are constants in `org.springframework.boot.thymeleaf.autoconfigure.ThymeleafProperties`, bound to `spring.thymeleaf`: `DEFAULT_PREFIX = "classpath:/templates/"`, `DEFAULT_SUFFIX = ".html"`, and `checkTemplateLocation = true`, documented as "Whether to check that the templates location exists" ([ThymeleafProperties.java](https://github.com/spring-projects/spring-boot/blob/main/module/spring-boot-thymeleaf/src/main/java/org/springframework/boot/thymeleaf/autoconfigure/ThymeleafProperties.java)). For static files: "By default, Spring Boot serves static content from a directory called `/static` (or `/public` or `/resources` or `/META-INF/resources`) in the classpath or from the root of the ServletContext", configurable through `spring.web.resources.static-locations`; the welcome page is "an `index.html` file in the configured static content locations" and, failing that, "an `index` template" ([Servlet Web Applications, Static Content](https://docs.spring.io/spring-boot/reference/web/servlet.html)). The Serving Web Content guide follows exactly these two names, `src/main/resources/templates/greeting.html` and `src/main/resources/static/index.html` ([Serving Web Content with Spring MVC](https://spring.io/guides/gs/serving-web-content)).

A page frame or layout has no framework name in Spring. Spring Framework's own page on Thymeleaf says only that "The Thymeleaf integration with Spring MVC is managed by the Thymeleaf project" and hands over to thymeleaf.org ([Spring MVC View Technologies, Thymeleaf](https://docs.spring.io/spring-framework/reference/web/webmvc-view/mvc-thymeleaf.html)). Thymeleaf's tutorial does layout with fragments: "In our templates, we will often want to include parts from other templates, parts like footers, headers, menus…", and "Thymeleaf needs us to define these parts, 'fragments', for inclusion, which can be done using the `th:fragment` attribute"; a fragment is pulled in with `th:insert`, which inserts it as the body of the host tag, or `th:replace`, which replaces the host tag, while `th:include` is deprecated ([Using Thymeleaf, Template Layout](https://www.thymeleaf.org/doc/tutorials/3.1/usingthymeleaf.html)). The tutorial's example fragment file is `/WEB-INF/templates/footer.html`, a file at the templates root, and the chapter does not name a `fragments/` folder or a `layout.html` file; neither name appears in any Boot or Spring page fetched. The decorator style of layout, where a content page names the layout that wraps it, comes from the Thymeleaf Layout Dialect, "A dialect for Thymeleaf that lets you build layouts and reusable templates in order to improve code reuse", published by the GitHub user ultraq as a separate dependency with `layout:decorate` and `layout:fragment`; it is not part of Thymeleaf core ([thymeleaf-layout-dialect](https://github.com/ultraq/thymeleaf-layout-dialect)).

Small formatters have two homes. In the template, Thymeleaf's expression utility objects include `#numbers`, `#dates`, `#calendars` and `#temporals`, the last "for dealing with dates and times using the java.time API" ([Using Thymeleaf, Expression Utility Objects](https://www.thymeleaf.org/doc/tutorials/3.1/usingthymeleaf.html)). `org.thymeleaf.expression.Numbers` is the "Expression Object for performing numeric operations (esp. number formatting)" and exposes `public String formatCurrency(Number target)` plus `formatDecimal` and `formatPercent` ([Numbers javadoc](https://www.thymeleaf.org/apidocs/thymeleaf/3.1.3.RELEASE/org/thymeleaf/expression/Numbers.html)). `org.thymeleaf.expression.Temporals`, "usually available in variable evaluation expressions with the name `#temporals`", is marked Since 3.1.0 in the core javadoc, with `format(Temporal)`, `format(Temporal, String pattern)`, `format(Temporal, String pattern, Locale)` and `formatISO` ([Temporals javadoc](https://www.thymeleaf.org/apidocs/thymeleaf/3.1.3.RELEASE/org/thymeleaf/expression/Temporals.html)). The older thymeleaf-extras-java8time README still calls itself "a thymeleaf extras module, not a part of the Thymeleaf core" and targets Thymeleaf 3.0 ([thymeleaf-extras-java8time](https://github.com/thymeleaf/thymeleaf-extras-java8time)); the migration note in Thymeleaf's 3.1 release article could not be fetched (not verified). On the Java side, Spring Framework offers the `Formatter<T> extends Printer<T>, Parser<T>` SPI, the field annotations `@NumberFormat(style=Style.CURRENCY)`, `@DateTimeFormat(iso=ISO.DATE)` and `@DurationFormat`, and a `FormatterRegistry` "for configuring formatting rules centrally, instead of duplicating such configuration across your controllers" ([Spring Field Formatting](https://docs.spring.io/spring-framework/reference/core/validation/format.html)); in MVC "formatters for various number and date types are installed" by default and custom ones are registered by a `@Configuration class WebConfiguration implements WebMvcConfigurer` overriding `addFormatters(FormatterRegistry registry)` ([Spring MVC Conversion and Formatting](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-config/conversion.html)). None of these pages says in which package a money or time formatter class should live.

So `templates/` and `static/` (and `public/`, `resources/`, `META-INF/resources/`) are framework names: Boot reads them and Initializr creates the first two. `fragments/`, `layout.html`, a `util/` or `format/` package for formatters, are not named by any fetched Spring, Boot, Initializr or Thymeleaf source.

### What the framework names versus what is habit

The framework reads, generates or documents as a rule the following. Component scanning starts from the package of the `@SpringBootApplication` class: the annotation enables "@Component scan on the package where the application is located" ([Using the @SpringBootApplication Annotation](https://docs.spring.io/spring-boot/reference/using/using-the-springbootapplication-annotation.html)), and in Spring Framework terms `basePackages` is "a common parent package" for the classes to detect, so nothing in the mechanism depends on what the subpackages are called ([Classpath Scanning and Managed Components](https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html)). The same root is the search package for persistence: "the package of the @SpringBootApplication annotated class is used to search for @Entity items" ([Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)); the auto configuration packages page generalises this: they are the packages that the various auto configured features look in by default when scanning for entities and Spring Data repositories, determined by `@EnableAutoConfiguration` "either directly or through its presence on @SpringBootApplication" and extendable with `@AutoConfigurationPackage` ([Auto configuration packages](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html)); the SQL page adds that `@Entity`, `@Embeddable` and `@MappedSuperclass` classes in those packages are the entity classes and that `@EntityScan` and `@EnableJpaRepositories` override the locations ([SQL Databases](https://docs.spring.io/spring-boot/reference/data/sql.html)). The JPA guide states the subpackage reach in plain words: Boot "looks in the package (and its subpackages) where @SpringBootApplication is located" ([Accessing Data with JPA](https://spring.io/guides/gs/accessing-data-jpa)). Configuration is read from `application.properties` and `application.yaml` at "The classpath root", "The classpath /config package", the current directory, its `config/` subdirectory and that directory's immediate children ([Externalized Configuration](https://docs.spring.io/spring-boot/reference/features/external-config.html)). Views are read from `src/main/resources/templates` and static files from `/static`, `/public`, `/resources` and `/META-INF/resources` ([Servlet Web Applications](https://docs.spring.io/spring-boot/reference/web/servlet.html)). Initializr generates precisely the application class, its `Tests` class, the properties file and, for web projects, the `static` and `templates` directories ([USING.adoc](https://github.com/spring-io/start.spring.io/blob/main/USING.adoc), [WebFoldersContributor.java](https://github.com/spring-io/initializr/blob/main/initializr-generator-spring/src/main/java/io/spring/initializr/generator/spring/configuration/WebFoldersContributor.java)). The default package is the one thing the docs forbid in practice: its use "is generally discouraged and should be avoided" because with it "every class from every jar is read" ([Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)).

Everything else is habit. No fetched page of the Spring Boot reference, the Spring Framework reference, the Initializr documentation or the official guides names a `controller/`, `service/`, `repository/`, `model/`, `config/` or `dto/` package. The only layout the reference shows groups by feature, `customer` and `order`, each holding its own entity, controller, service and repository, and it is labelled "a typical layout", a recommendation with the stated motive of making scanning "apply only on your project", not a rule the framework enforces ([Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)). The guides are flatter still: one package per guide (`com.example.servingwebcontent`, `com.example.accessingdatajpa`, `payroll`) with controller, entity and repository side by side and no service ([Serving Web Content with Spring MVC](https://spring.io/guides/gs/serving-web-content), [Accessing Data with JPA](https://spring.io/guides/gs/accessing-data-jpa), [Building REST services with Spring](https://spring.io/guides/tutorials/rest)). The stereotype names are the one place the framework speaks in layers, persistence, service and presentation, but those are annotations on classes, read by scanning and by aspects, not folder names read by the framework ([Classpath Scanning and Managed Components](https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html)).

### The business layer

The framework answers the question twice, once for the model and once for the controller, and the two answers point in slightly different directions. The MVC overview, under "Model Responsibilities", says "The Model in an MVC application represents the state of the application and any business logic or operations that should be performed by it. Business logic should be encapsulated in the model, along with any implementation logic for persisting the state of the application. Strongly-typed views typically use ViewModel types designed to contain the data to display on that view. The controller creates and populates these ViewModel instances from the model." Under "Controller Responsibilities" a note adds "To keep controller logic from becoming overly complex, push business logic out of the controller and into the domain model" ([MVC overview](https://learn.microsoft.com/en-us/aspnet/core/mvc/overview?view=aspnetcore-10.0)). The controllers document repeats the model answer, "Generally, business decisions should be performed within the model", then gives the service answer in the next paragraph: "The controller is a *UI-level* abstraction. Its responsibilities are to ensure request data is valid and to choose which view (or result for an API) should be returned. In well-factored apps, it doesn't directly include data access or business logic. Instead, the controller delegates to services handling these responsibilities." Under "Defining Actions" it says "Action methods should contain logic for mapping a request to a business concern. Business concerns should typically be represented as services that the controller accesses through dependency injection" ([Handle requests with controllers](https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/actions?view=aspnetcore-10.0)). The DI document closes the loop from the other side: "Keep in mind that Razor Pages page model classes and MVC controller classes should focus on UI concerns" ([Dependency injection](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0)). So the stated rule is: an operation such as "start an order" lives in the model or in a service, not in the controller or PageModel. No framework page names a folder for either.

### The vendor integration

Stripe's documented ASP.NET Core sample is `stripe-samples/checkout-one-time-payments/server/dotnet`, which contains `Configuration/`, `Models/`, `Properties/`, `Program.cs`, `README.md`, `appsettings.Development.json`, `appsettings.json` and `server.csproj`; there is no `Controllers/` folder ([server/dotnet](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/dotnet)). `Program.cs` uses minimal APIs. It sets `StripeConfiguration.ApiKey = Environment.GetEnvironmentVariable("STRIPE_SECRET_KEY");` at startup, binds a `StripeOptions` class with `builder.Services.Configure<StripeOptions>(options => { options.PublishableKey = ...; options.SecretKey = ...; options.WebhookSecret = ...; options.Price = ...; options.Domain = ...; })` from environment variables, and defines the endpoint that creates the session:

```csharp
app.MapPost("/create-checkout-session", async (IOptions<StripeOptions> stripeOptions, HttpContext context) =>
{
    var options = new SessionCreateOptions
    {
        SuccessUrl = $"{stripeOptions.Value.Domain}/success.html?session_id={{CHECKOUT_SESSION_ID}}",
        Mode = "payment",
        LineItems = new List<SessionLineItemOptions>
                {
                    new SessionLineItemOptions
                    {
                        Quantity = long.Parse(context.Request.Form["quantity"]),
                        Price = stripeOptions.Value.Price,
                    },
                },
        // AutomaticTax = new SessionAutomaticTaxOptions { Enabled = true }
    };

    var service = new SessionService();
    var session = await service.CreateAsync(options);
    return Results.Redirect(session.Url);
});
```

The same file holds `/config` (a `PriceService().GetAsync`), `/checkout-session` and `/webhook`, the last using `EventUtility.ConstructEvent` to verify the signature. The sequence "call the provider, redirect the browser" is entirely inside the endpoint lambda in `Program.cs`; no database or order record is created anywhere, so there is no "create the record" step to sequence ([Program.cs](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/dotnet/Program.cs)). `Configuration/StripeOptions.cs` is a plain class with five string properties (`PublishableKey`, `SecretKey`, `WebhookSecret`, `Price`, `Domain`) and no `using Stripe` ([StripeOptions.cs](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/dotnet/Configuration/StripeOptions.cs)). `Models/ConfigResponse.cs` imports only `Newtonsoft.Json` ([ConfigResponse.cs](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/dotnet/Models/ConfigResponse.cs)). The provider client is therefore a static singleton (`StripeConfiguration.ApiKey`) plus per request `new SessionService()` instances, both living in `Program.cs`; no model imports the provider.

The Stripe Checkout quickstart for .NET shows a different shape. Its C# fragments register the client as a DI singleton, `services.AddSingleton(new StripeClient("<<YOUR_SECRET_KEY>>"));`, and the action body builds `SessionCreateOptions`, calls `Session session = _client.V1.Checkout.Sessions.Create(options);`, then `Response.Headers.Add("Location", session.Url); return new StatusCodeResult(303);`. The `_client` field and `Response.Headers` imply a controller receiving `StripeClient` through its constructor, and `services.AddSingleton` implies a `Startup.ConfigureServices` style registration, but the rendered page does not show the file names or the class declaration, so the controller file name is not verified ([Checkout quickstart, dotnet](https://docs.stripe.com/checkout/quickstart?lang=dotnet)). The quickstart's prose says "Add an endpoint on your server that creates a Checkout Session" and "After creating the session, redirect your customer to the URL for the Checkout page returned in the response"; it says nothing about saving an order first, and its fulfillment guidance is to "Wait to fulfill orders (for example, shipping or sending email receipts) until the payment succeeds" via webhooks ([Checkout quickstart](https://docs.stripe.com/checkout/quickstart?lang=dotnet)).

By the framework's own documented patterns, a provider client would be a service. The DI document's convention is an interface plus implementation registered in `Program.cs` with `AddScoped`, `AddSingleton` or `AddTransient`, and it notes that `builder.Services.AddSingleton<MyDependency>();` registers an implementation as its own service type ([Dependency injection](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0)). Configuration would use the options pattern: "The options pattern uses classes to provide strongly typed access to groups of related settings", with a `PositionOptions` class containing `public const string Position = "Position";`, bound in `Program.cs` by `builder.Services.Configure<PositionOptions>(builder.Configuration.GetSection(PositionOptions.Position));` and consumed as `IOptions<PositionOptions>` through a page model constructor ([Options pattern](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/options?view=aspnetcore-10.0)). An HTTP client to a vendor would be a typed client: `IHttpClientFactory` "Provides a central location for naming and configuring logical `HttpClient` instances", typed clients "Provide a single location to configure and interact with a particular `HttpClient`. For example, a single typed client might be used for a single backend endpoint, or to encapsulate all logic dealing with the endpoint", registered with `builder.Services.AddHttpClient<GitHubService>();` where `GitHubService` takes `HttpClient` in its constructor ([IHttpClientFactory](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/http-requests?view=aspnetcore-10.0)). None of the three documents says what folder these classes live in; the DI document's `Services/MyDependency.cs` caption is the only folder name shown, and the typed client page shows none. The Stripe sample follows the options pattern for settings but not DI for the client, and the Stripe quickstart follows DI for the client but hardcodes the key.

### Shared page code

The page frame is the layout. "By convention, the default layout for an ASP.NET Core app is named `_Layout.cshtml`. The layout files for new ASP.NET Core projects created with the templates are: Razor Pages: `Pages/Shared/_Layout.cshtml` ... Controller with views: `Views/Shared/_Layout.cshtml`." A view sets it with `Layout = "_Layout";`, and "When a partial name is provided, the Razor view engine searches for the layout file using its standard discovery process. The folder where the handler method (or controller) exists is searched first, followed by the *Shared* folder. This discovery process is identical to the process used to discover partial views." "Code that needs to run before each view or page should be placed in the `_ViewStart.cshtml` file. By convention, the `_ViewStart.cshtml` file is located in the *Pages* (or *Views*) folder." "Directives shared by many views might be specified in a common `_ViewImports.cshtml` file", which supports `@addTagHelper`, `@removeTagHelper`, `@tagHelperPrefix`, `@using`, `@model`, `@inherits`, `@inject` and `@namespace` and "doesn't support other Razor features, such as functions and section definitions"; both files are hierarchical, and "`_ViewStart.cshtml` and `_ViewImports.cshtml` are **not** typically placed in the */Pages/Shared* (or */Views/Shared*) folder. The app-level versions of these files should be placed directly in the */Pages* (or */Views*) folder" ([Layout](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/layout?view=aspnetcore-10.0)). The Razor Pages page adds "The layout file should go in the *Pages/Shared* folder. We recommend you **not** put the layout file in the *Views/Shared* folder. *Views/Shared* is an MVC views pattern. Razor Pages are meant to rely on folder hierarchy, not path conventions" ([Razor Pages introduction](https://learn.microsoft.com/en-us/aspnet/core/razor-pages/?view=aspnetcore-10.0)).

Reusable markup without logic is a partial view: "A partial view is a `.cshtml` markup file without an `@page` directive maintained within the *Views* folder (MVC) or *Pages* folder (Razor Pages)." "Partial view file names often begin with an underscore (`_`). This naming convention isn't required, but it helps to visually differentiate partial views from views and pages." Discovery for Razor Pages searches the "Currently executing page's folder", the "Directory graph above the page's folder", `/Shared`, `/Pages/Shared`, `/Views/Shared`; for MVC it searches `/Areas/<Area-Name>/Views/<Controller-Name>`, `/Areas/<Area-Name>/Views/Shared`, `/Views/Shared`, `/Pages/Shared`. The page also says "Partial views shouldn't be used to maintain common layout elements. Common layout elements should be specified in `_Layout.cshtml` files" and "Don't use a partial view where complex rendering logic or code execution is required to render the markup. Instead of a partial view, use a view component" ([Partial views](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/partial?view=aspnetcore-10.0)). Reusable markup with logic is a view component, identified by "Deriving from `ViewComponent`", "Decorating a class with the `[ViewComponent]` attribute, or deriving from a class with the `[ViewComponent]` attribute", or "Creating a class where the name ends with the suffix `ViewComponent`"; its view is searched at `/Views/{Controller Name}/Components/{View Component Name}/{View Name}`, `/Views/Shared/Components/{View Component Name}/{View Name}`, `/Pages/Shared/Components/{View Component Name}/{View Name}` and `/Areas/{Area Name}/Views/Shared/Components/{View Component Name}/{View Name}`; "The default view name for a view component is `Default`, which means view files will typically be named `Default.cshtml`", and the walkthrough states "Create the *Views/Shared/Components* folder. This folder **must** be named *Components*." The document names no folder for the class itself ([View components](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/view-components?view=aspnetcore-10.0)).

Small formatters have three documented homes, none of them a folder for C# helper classes. First, `@functions`: "The `@functions` directive enables adding C# members (fields, properties, and methods) to the generated class", with the example `@functions { public string GetHello() { return "Hello"; } }` and the note that "`@functions` methods serve as templating methods when they have markup"; the same page documents templated Razor delegates (`Func<dynamic, object> petTemplate = @<p>...</p>;`) and `@inject`, which "enables the Razor Page to inject a service from the service container into a view" ([Razor syntax](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/razor?view=aspnetcore-10.0)). The views DI page qualifies `@inject`: "This can be useful for view-specific services, such as localization or data required only for populating view elements. Most of the data views display should be passed in from the controller", and its sample registers `builder.Services.AddTransient<StatisticsService>();` and `builder.Services.AddTransient<MyHtmlHelper>();` in `Program.cs`, the latter used as `@inject MyHtmlHelper Html` to replace the default HTML helpers ([Dependency injection into views](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/dependency-injection?view=aspnetcore-10.0)). Second, data annotations on the model: the tutorial's `Movie` carries `[Display(Name = "Release Date")]`, `[DataType(DataType.Date)]` and `[Column(TypeName = "decimal(18, 2)")]`, and explains "The `[Column(TypeName = "decimal(18, 2)")]` data annotation enables Entity Framework Core to correctly map `Price` to currency in the database" while the Index page renders `@Html.DisplayFor(modelItem => item.Price)` ([Update the generated pages](https://learn.microsoft.com/en-us/aspnet/core/tutorials/razor-pages/da1?view=aspnetcore-10.0)). The validation part says `[DataType]` attributes "Can provide a date selector `DataType.Date` in browsers that support HTML5", that "`DataType.Date` doesn't specify the format of the date that's displayed. By default, the data field is displayed according to the default formats based on the server's `CultureInfo`", that `[DisplayFormat(DataFormatString = "{0:yyyy-MM-dd}", ApplyFormatInEditMode = true)]` sets the format explicitly, that "in currency values, the currency symbol is usually not wanted in the edit UI", and that "The `[DataType]` attribute can enable the ASP.NET Core framework to choose the right field template to render the data" ([Add validation](https://learn.microsoft.com/en-us/aspnet/core/tutorials/razor-pages/validation?view=aspnetcore-10.0)). The movie tutorial does not call `ToString("C")` anywhere in the pages fetched (not verified). Third, display and editor templates: "A `DisplayTemplate` is a Razor file placed in the `DisplayTemplates` folder: For Razor Pages apps, in the `Pages/Shared/DisplayTemplates` folder. For MVC apps, in the `Views/Shared/DisplayTemplates` folder or the `Views/ControllerName/DisplayTemplates` folder", named after the type and picked up because "The view engine automatically looks for a file in the `DisplayTemplates` folder that matches the name of the type"; editor templates live in `Pages/Shared/EditorTemplates` or `Views/Shared/EditorTemplates` ([DisplayTemplates and EditorTemplates](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/display-templates?view=aspnetcore-10.0)).

Which names are the framework's and which are habit: `Shared` is read by the view engine for layouts, partials, view components and display templates; `_ViewStart.cshtml` and `_ViewImports.cshtml` are found by name and location; `Pages` is the routing root; `Components` and `DisplayTemplates` must be spelled that way. `_Layout` is the template's name and the layout doc calls it a convention, since `Layout = "_Layout"` is an explicit string and any file name resolves through the same discovery. The leading underscore on partials is explicitly "not required". Nothing in the framework names a folder for a C# `Money` or `TimeAgo` helper; the options are `@functions` in the page, a service behind `@inject`, a tag helper, or a display template keyed by type.

### What the framework names versus what is habit

Read by the framework. `Pages/`: "The runtime looks for Razor Pages files in the *Pages* folder by default", with `/Pages/Store/Contact.cshtml` matching `/Store/Contact` ([Razor Pages introduction](https://learn.microsoft.com/en-us/aspnet/core/razor-pages/?view=aspnetcore-10.0)). `Views/{Controller}/` and `Views/Shared/`: "view discovery searches for a matching view file in this order: 1. `Views/[ControllerName]/[ViewName].cshtml` 2. `Views/Shared/[ViewName].cshtml`", customizable through `IViewLocationExpander` ([Views](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/overview?view=aspnetcore-10.0)). `wwwroot/`: "By default, store static files within the project's web root directory. The default directory is `{CONTENT ROOT}/wwwroot` ... Only files in the `wwwroot` folder are addressable", changeable with `UseWebRoot` ([Static files](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/static-files?view=aspnetcore-10.0)). `Areas/`: for controllers, "only the view files are required to use this folder structure", searched at `/Areas/<Area-Name>/Views/<Controller-Name>/<Action-Name>.cshtml`, `/Areas/<Area-Name>/Views/Shared/<Action-Name>.cshtml`, `/Views/Shared/<Action-Name>.cshtml`, `/Pages/Shared/<Action-Name>.cshtml`, while the controller is associated by `[Area("Products")]`, not by folder; for Razor Pages, "Areas with Razor Pages require an `Areas/<area name>/Pages` folder in the root of the app"; the `Areas` name itself is configurable through `RazorViewEngineOptions.AreaViewLocationFormats` ([Areas](https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/areas?view=aspnetcore-10.0)). `_ViewStart.cshtml` and `_ViewImports.cshtml` by name, hierarchically from the root of `Pages` or `Views` ([Layout](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/layout?view=aspnetcore-10.0)). `Views/Shared/Components/{Name}/Default.cshtml` and `Pages/Shared/Components/{Name}/Default.cshtml` for view component views ([View components](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/view-components?view=aspnetcore-10.0)). `Pages/Shared/DisplayTemplates` and `Views/Shared/DisplayTemplates` for display templates ([DisplayTemplates](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/display-templates?view=aspnetcore-10.0)).

Habit only. `Controllers/`: the controllers document says "By convention, controller classes: Reside in the project's root-level *Controllers* folder. Inherit from `Microsoft.AspNetCore.Mvc.Controller`", but what makes a class a controller is that "The class name is suffixed with `Controller`", or "The class inherits from a class whose name is suffixed with `Controller`", or "The `[Controller]` attribute is applied to the class", with `[NonController]` as the opt out ([Handle requests with controllers](https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/actions?view=aspnetcore-10.0)). The routing document confirms the mapping of `{controller=Home}/{action=Index}/{id?}` "Is based on the controller and action names **only**. Isn't based on namespaces, source file locations, or method parameters" and that "Class namespaces have no effect on MVC's routing" ([Routing to controller actions](https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/routing?view=aspnetcore-10.0)). `Models/`: the views document says "Usually, viewmodel classes are either stored in the `Models` folder or a separate `ViewModels` folder at the root of the app" and "Nothing prevents you from using the same classes for both your viewmodel types and your business model types" ([Views](https://learn.microsoft.com/en-us/aspnet/core/mvc/views/overview?view=aspnetcore-10.0)); the tutorials create `Models/Movie.cs` by hand ([Add a model](https://learn.microsoft.com/en-us/aspnet/core/tutorials/razor-pages/model?view=aspnetcore-10.0)). `Data/`: created by the scaffolder for the `DbContext` and by the templates only under individual authentication; nothing reads it ([Add a model](https://learn.microsoft.com/en-us/aspnet/core/tutorials/razor-pages/model?view=aspnetcore-10.0), [template.json](https://raw.githubusercontent.com/dotnet/aspnetcore/release/10.0/src/ProjectTemplates/Web.ProjectTemplates/content/RazorPagesWeb-CSharp/.template.config/template.json)). `Services/` and `Interfaces/`: appear only as file captions in the DI document and in the architecture eBook's description of the template, and do not exist in the template source ([Dependency injection](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0), [Common web application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures), [StarterWeb-CSharp](https://github.com/dotnet/aspnetcore/tree/main/src/ProjectTemplates/Web.ProjectTemplates/content/StarterWeb-CSharp)). The MVC overview's own words for the whole arrangement are "In an MVC project, logical components like Model, Controller, and View are kept in different folders, and MVC uses naming conventions to create the relationship between these components" ([MVC overview](https://learn.microsoft.com/en-us/aspnet/core/mvc/overview?view=aspnetcore-10.0)); the view folders are the part the runtime reads, the class folders are the part it does not.

## Flask

Versions verified: Flask 3.1.3, released 2026-02-19 ([PyPI: Flask](https://pypi.org/project/Flask/)); the stable docs header reads "Flask Documentation (3.1.x)" and the tutorial's "example code" links point at the `3.1.3` tag of pallets/flask ([Tutorial](https://flask.palletsprojects.com/en/stable/tutorial/), [Large Applications as Packages](https://flask.palletsprojects.com/en/stable/patterns/packages/)). Jinja2 3.1.6, released 2025-03-05 ([PyPI: Jinja2](https://pypi.org/project/Jinja2/)); the Jinja stable docs header reads "Jinja 3.1.x" ([Jinja: Template Designer Documentation](https://jinja.palletsprojects.com/en/stable/templates/)). The pallets/flask repository listing was read on the `main` branch ([pallets/flask examples/tutorial](https://github.com/pallets/flask/tree/main/examples/tutorial)). The Stripe sample stripe-samples/checkout-one-time-payments has `main` as its default branch ([stripe-samples/checkout-one-time-payments](https://github.com/stripe-samples/checkout-one-time-payments)); its Python server pins `Flask==3.1.2`, `Jinja2==3.1.6` and `stripe==15.6.0` in the requirements shown on the Stripe quickstart ([Stripe Checkout quickstart, Python](https://docs.stripe.com/checkout/quickstart?lang=python)).

### The business layer

Flask has no generator and does not prescribe a place for an operation such as "start an order". The Tutorial index states the position directly: "Flask is flexible. It doesn't require you to use any particular project or code layout. However, when first starting, it's helpful to use a more structured approach" ([Tutorial](https://flask.palletsprojects.com/en/stable/tutorial/)). The Design Decisions page says the same from the other side: "Flask won't make many decisions for you, such as what database to use", "Flask will never have a database layer. It will not have a form library or anything else in that direction", and "As your codebase grows, you are free to make the design decisions appropriate for your project" ([Design Decisions in Flask](https://flask.palletsprojects.com/en/stable/design/)). The exact phrase "does not enforce any project layout" does not appear on the Project Layout page or the Design Decisions page; the wording quoted above from the Tutorial index is the closest primary statement (verified by reading both pages). The tutorial has you create every file by hand with shell commands such as `mkdir flaskr` followed by writing `flaskr/__init__.py` ([Tutorial: Application Setup](https://flask.palletsprojects.com/en/stable/tutorial/factory/)), and the Project Layout page says "A Flask application can be as simple as a single file" before listing the final tree, which contains `flaskr/__init__.py`, `db.py`, `schema.sql`, `auth.py`, `blog.py`, `templates/`, `static/` and a `tests/` folder, with no models, services or forms module ([Tutorial: Project Layout](https://flask.palletsprojects.com/en/stable/tutorial/layout/)). The repository listing of `examples/tutorial/flaskr` on `main` confirms the same five files plus `static/` and `templates/`, and nothing named `models.py` or `services/` ([pallets/flask examples/tutorial/flaskr](https://github.com/pallets/flask/tree/main/examples/tutorial/flaskr)).

What the tutorial shows is the view function doing the write. The `create` view in `flaskr/blog.py` validates the form, then calls `db = get_db()`, executes `'INSERT INTO post (title, body, author_id) VALUES (?, ?, ?)'` with `(title, body, g.user['id'])`, calls `db.commit()` and returns `redirect(url_for('blog.index'))`, all inside the function decorated with `@bp.route('/create', methods=('GET', 'POST'))` and `@login_required` ([Tutorial: Blog Blueprint](https://flask.palletsprojects.com/en/stable/tutorial/blog/)). The repository copy of `blog.py` on `main` has the identical shape: `db.execute("INSERT INTO post (title, body, author_id) VALUES (?, ?, ?)", (title, body, g.user["id"]))` followed by `db.commit()` inside `create()` ([blog.py on main](https://raw.githubusercontent.com/pallets/flask/main/examples/tutorial/flaskr/blog.py)). The `register` view in `flaskr/auth.py` does the same for users, executing `"INSERT INTO user (username, password) VALUES (?, ?)"` inside the view ([Tutorial: Blueprints and Views](https://flask.palletsprojects.com/en/stable/tutorial/views/)). The only extraction the tutorial makes is `get_post(id, check_author=True)`, a plain function in `blog.py` that runs the SELECT and raises `abort(404)` or `abort(403)`, introduced "To avoid duplicating code" between `update` and `delete` ([Tutorial: Blog Blueprint](https://flask.palletsprojects.com/en/stable/tutorial/blog/)). There is no models module because the tutorial uses the standard library directly: the database page notes that Python ships SQLite support in its standard `sqlite3` module, and `flaskr/db.py` holds only connection helpers (`get_db`, `close_db`), the `init_db` and `init_db_command` setup functions, and an `init_app(app)` function that registers `close_db` with `app.teardown_appcontext` and the `init-db` command with `app.cli.add_command` ([Tutorial: Define and Access the Database](https://flask.palletsprojects.com/en/stable/tutorial/database/)). The `get_db` helper stores the connection on `g`, "a special object that is unique for each request", and reads the path from `current_app.config['DATABASE']` ([Tutorial: Define and Access the Database](https://flask.palletsprojects.com/en/stable/tutorial/database/)). The Tutorial index also notes that "The tutorial only uses what's provided by Flask and Python" ([Tutorial](https://flask.palletsprojects.com/en/stable/tutorial/)).

The patterns pages add names, but as examples rather than rules. Large Applications as Packages grows a single `yourapplication.py` into a package with `__init__.py`, `views.py`, `/static` and `/templates`; the checklist says only that "the Flask application object creation has to be in the `__init__.py` file" and that "all the view functions (the ones with a route() decorator on top) have to be imported in the `__init__.py` file", and the page does not mention `models.py` or a `views/` folder at all ([Large Applications as Packages](https://flask.palletsprojects.com/en/stable/patterns/packages/)). The Application Factories page shows a `create_app` that imports `db` from `yourapplication.model` and blueprints from `yourapplication.views.admin` and `yourapplication.views.frontend`, and says to put `db = SQLAlchemy()` "in model.py (or equivalent)" and the factory "in your application.py (or equivalent)" ([Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)). The SQLAlchemy pattern page says "it's encouraged to use a package instead of a module for your flask application and drop the models into a separate module", adding "While that is not necessary, it makes a lot of sense"; it shows a `database.py` holding the engine and `db_session`, and a `User` class with the instruction "put this into `models.py`, e.g." ([SQLAlchemy in Flask](https://flask.palletsprojects.com/en/stable/patterns/sqlalchemy/)). None of these pages names a service layer or says where an operation that spans a write and an external call should live.

### The vendor integration

In Stripe's own Flask sample the view function sequences everything, and there is no order record at all. The file `server/python/server.py` imports `stripe`, `json`, `os`, `Flask, render_template, jsonify, request, send_from_directory, redirect` from `flask`, and `load_dotenv, find_dotenv` from `dotenv`; it calls `load_dotenv(find_dotenv())` and then sets `stripe.api_key = os.getenv('STRIPE_SECRET_KEY')` at module top; it constructs the app with `app = Flask(__name__, static_folder=static_dir, static_url_path="", template_folder=static_dir)`; and it contains no import of any database library, ORM, sqlite or SQL module and defines no class ([server.py on main](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)). The repository README lists no database or persistence step, and the environment variables it documents are `STRIPE_PUBLISHABLE_KEY`, `STRIPE_SECRET_KEY`, `PRICE`, `DOMAIN`, `STATIC_DIR` and the optional `STRIPE_WEBHOOK_SECRET`, all read from a `.env` file for which the repository ships `.env.example` ([stripe-samples/checkout-one-time-payments](https://github.com/stripe-samples/checkout-one-time-payments), [.env.example](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/.env.example)). The `server/python` folder holds exactly `README.md`, `requirements.txt` and `server.py`, and the README runs it with `export FLASK_APP=server.py` and `python3 -m flask run --port=4242` ([server/python](https://github.com/stripe-samples/checkout-one-time-payments/tree/main/server/python)).

The checkout view reads form and environment values, calls the provider, and redirects; the exact lines are load bearing ([server.py on main](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)):

```python
@app.route('/create-checkout-session', methods=['POST'])
def create_checkout_session():
    quantity = request.form.get('quantity', 1)
    domain_url = os.getenv('DOMAIN')
    ...
        checkout_session = stripe.checkout.Session.create(
            success_url=domain_url + '/success.html?session_id={CHECKOUT_SESSION_ID}',
            mode='payment',
            # automatic_tax={'enabled': True},

    except Exception as e:
```

So "write the order, call the provider, redirect the browser" collapses to "call the provider, redirect the browser", performed by the view function itself. The provider client is the module level `stripe` package configured once by `stripe.api_key = os.getenv('STRIPE_SECRET_KEY')` in the same `server.py` that holds the routes; no model imports it because no model exists. The other routes are `/` (serves the page), `/config` (returns the publishable key and the retrieved Price), `/checkout-session` (retrieves a session by id) and `/webhook`, which verifies the signature and logs "Payment succeeded!" on completion ([server.py on main](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)). The Stripe quickstart for Python shows the same shape in a Flask server: `import stripe`, a client created as `client = stripe.StripeClient('<<YOUR_SECRET_KEY>>')` at module level with the comment "Don't put any keys in code", a `checkout_session = client.v1.checkout.sessions.create(params={...})` call inside the route, and `return redirect(checkout_session.url, code=303)`; it mentions no database or order model, and its fulfilment advice is to "Wait to fulfill orders ... until the payment succeeds" via webhooks ([Stripe Checkout quickstart, Python](https://docs.stripe.com/checkout/quickstart?lang=python)).

Flask itself documents a convention for third party clients, framed as extensions. The Extensions page says that "extensions pull their own configuration from app.config and are passed an application instance during initialization", with the example `foo = Foo()` at module level, `app.config.update(FOO_BAR='baz', FOO_SPAM='eggs')`, then `foo.init_app(app)` ([Extensions](https://flask.palletsprojects.com/en/stable/extensions/)). The Extension Development guide makes the rule explicit: "The most common pattern is to create a class that represents the extension's configuration and behavior, with an `init_app` method", "It is important that the app is not stored on the extension, don't do `self.app = app`", and the instance "exists independently of the application" so "other modules in a user's project can do `from project import hello` and use the extension in blueprints before the app exists"; per deployment values such as "a URL to an external resource, such as a database" belong in `app.config` with keys prefixed by the extension's name, and per request resources go on `g` under a prefixed name ([Flask Extension Development](https://flask.palletsprojects.com/en/stable/extensiondev/)). The Application Factories page repeats it for Flask-SQLAlchemy: define `db = SQLAlchemy()` in `model.py` and call `db.init_app(app)` in the factory so that, in the page's words, no state specific to one application is stored on the extension object ([Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)). For keys, `app.config` is "a subclass of a dictionary"; `from_prefixed_env()` loads "all environment variables starting with a specific prefix", `FLASK_` by default, so `FLASK_SECRET_KEY` becomes `app.config["SECRET_KEY"]`; the tutorial uses `app.config.from_mapping(SECRET_KEY='dev', DATABASE=...)` and `from_pyfile('config.py', silent=True)` against the instance folder ([Configuration Handling](https://flask.palletsprojects.com/en/stable/config/), [Tutorial: Application Setup](https://flask.palletsprojects.com/en/stable/tutorial/factory/)). The Stripe sample uses none of this: it reads `os.getenv` directly and never touches `app.config` ([server.py on main](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py)).

### Shared page code

The page frame lives in a template that the application names. The tutorial puts it at `flaskr/templates/base.html`, which defines `{% block title %}`, `{% block header %}` and `{% block content %}`, renders the navigation from `g.user`, links the stylesheet with `url_for('static', filename='style.css')`, and loops over `get_flashed_messages()`; every other page starts with `{% extends 'base.html' %}` ([Tutorial: Templates](https://flask.palletsprojects.com/en/stable/tutorial/templates/)). The tutorial states both the folder and the reason for the subfolders: "The template files will be stored in the `templates` directory inside the `flaskr` package", and "The base template is directly in the `templates` directory. To keep the others organized, the templates for a blueprint will be placed in a directory with the same name as the blueprint", giving `flaskr/templates/auth/register.html`, `flaskr/templates/auth/login.html` and `flaskr/templates/blog/index.html`, `create.html`, `update.html` ([Tutorial: Templates](https://flask.palletsprojects.com/en/stable/tutorial/templates/), [Tutorial: Project Layout](https://flask.palletsprojects.com/en/stable/tutorial/layout/)). The Template Inheritance pattern page calls the same file `layout.html` ("This template, which we'll call `layout.html`") with blocks `head`, `title`, `content` and `footer`, and the Large Applications page's example tree also lists `templates/layout.html` ([Template Inheritance](https://flask.palletsprojects.com/en/stable/patterns/templateinheritance/), [Large Applications as Packages](https://flask.palletsprojects.com/en/stable/patterns/packages/)). Jinja's own documentation uses `base.html` in its template inheritance section ([Jinja: Template Designer Documentation](https://jinja.palletsprojects.com/en/stable/templates/)). So `base.html` and `layout.html` are both habits documented by example; neither is read by the framework.

Small formatters have three documented homes, all registered on the application object rather than placed in a named folder. A filter can be registered with the `@app.template_filter('reverse')` decorator or by assignment `app.jinja_env.filters['reverse'] = reverse_filter`; "In case of the decorator the argument is optional if you want to use the function name as name of the filter" ([Templates](https://flask.palletsprojects.com/en/stable/templating/)). A context processor "is a function that returns a dictionary" whose keys "are then merged with the template context, for all templates in the app", and the documented example is exactly a money formatter: `@app.context_processor def utility_processor(): def format_price(amount, currency="€"): return f"{amount:.2f}{currency}"; return dict(format_price=format_price)`, used as `{{ format_price(0.33) }}`, with the remark "You could also build `format_price` as a template filter" ([Templates](https://flask.palletsprojects.com/en/stable/templating/)). The API lists `template_global()` as "A decorator that is used to register a custom template global function" alongside `template_filter()` and `context_processor` ([API: Flask](https://flask.palletsprojects.com/en/stable/api/)). Blueprints can carry the same: "Provide template filters, static files, templates, and other utilities through blueprints" ([Modular Applications with Blueprints](https://flask.palletsprojects.com/en/stable/blueprints/)). The Flask docs do not say in which module these functions should be defined.

Jinja ships no currency and no date filter. Its builtin filter list is `abs, attr, batch, capitalize, center, default, dictsort, escape, filesizeformat, first, float, forceescape, format, groupby, indent, int, items, join, last, length, list, lower, map, max, min, pprint, random, reject, rejectattr, replace, reverse, round, safe, select, selectattr, slice, sort, string, striptags, sum, title, tojson, trim, truncate, unique, upper, urlencode, urlize, wordcount, wordwrap, xmlattr`; the nearest are `format` (described as applying the given values to a printf style format string, like `string % values`), `round` ("Round the number to a given precision") and `filesizeformat` ([Jinja: List of Builtin Filters](https://jinja.palletsprojects.com/en/stable/templates/#list-of-builtin-filters)). Flask adds `tojson` and the standard context (`config`, `request`, `session`, `g`, `url_for()`, `get_flashed_messages()`) ([Templates](https://flask.palletsprojects.com/en/stable/templating/)). The tutorial therefore formats time by calling a Python method inside the template, `{{ post['created'].strftime('%Y-%m-%d') }}` in `blog/index.html` ([Tutorial: Blog Blueprint](https://flask.palletsprojects.com/en/stable/tutorial/blog/)).

The folder name is given by the framework, the file names are not. The `Flask` constructor's `template_folder` parameter is "the folder that contains the templates that should be used by the application. Defaults to `'templates'` folder in the root path of the application", and `static_folder` "Defaults to `'static'`" ([API: Flask](https://flask.palletsprojects.com/en/stable/api/)). The Quickstart spells out the lookup: "Flask will look for templates in the `templates` folder. So if your application is a module, this folder is next to that module, if it's a package it's actually inside your package", and "Just create a folder called `static` in your package or next to your module and it will be available at `/static` on the application" ([Quickstart](https://flask.palletsprojects.com/en/stable/quickstart/)). The tutorial relies on both: "Flask automatically adds a `static` view that takes a path relative to the `flaskr/static` directory and serves it" ([Tutorial: Static Files](https://flask.palletsprojects.com/en/stable/tutorial/static/)).

### What the framework names versus what is habit

The framework reads four locations by name. `templates/` and `static/` are the defaults of the `Flask` constructor's `template_folder` and `static_folder` parameters, resolved relative to `root_path`, which Flask derives from the `import_name` ("The app needs to know where it's located to set up some paths, and `__name__` is a convenient way to tell it that") ([API: Flask](https://flask.palletsprojects.com/en/stable/api/), [Tutorial: Application Setup](https://flask.palletsprojects.com/en/stable/tutorial/factory/)). The `instance/` folder is the default of `instance_path`: "By default the folder `'instance'` next to the package or module is assumed to be the instance path", and `instance_relative_config=True` makes config file names relative to it; the Configuration page describes it as "designed to not be under version control and be deployment specific", and the tutorial notes "Flask doesn't create the instance folder automatically" so the factory calls `os.makedirs(app.instance_path, exist_ok=True)` ([API: Flask](https://flask.palletsprojects.com/en/stable/api/), [Configuration Handling](https://flask.palletsprojects.com/en/stable/config/), [Tutorial: Application Setup](https://flask.palletsprojects.com/en/stable/tutorial/factory/)). A blueprint's `template_folder` and `static_folder` are opt in arguments to the `Blueprint` constructor, "either an absolute path or relative to the blueprint's location"; the blueprint template folder "is added to the search path of templates but with a lower priority than the actual application's template folder", and the docs recommend the extra subfolder `yourapplication/admin/templates/admin/index.html` "to avoid getting our template overridden by a template named `index.html` in the actual application template folder" ([Modular Applications with Blueprints](https://flask.palletsprojects.com/en/stable/blueprints/)). The tutorial's `templates/auth/` and `templates/blog/` subfolders are the same habit applied inside the application's own `templates/` folder, since its blueprints pass no `template_folder` ([Tutorial: Blueprints and Views](https://flask.palletsprojects.com/en/stable/tutorial/views/), [Tutorial: Templates](https://flask.palletsprojects.com/en/stable/tutorial/templates/)). The `flask` command also recognises a factory by name: "Flask will automatically detect the factory if it is named `create_app` or `make_app`" ([Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)), and the Quickstart adds that a file named `app.py` or `wsgi.py` needs no `--app` option ([Quickstart](https://flask.palletsprojects.com/en/stable/quickstart/)).

Everything else is habit shown by example. `models.py` appears only as "put this into `models.py`, e.g." on the SQLAlchemy page and as `model.py (or equivalent)` on the factories page ([SQLAlchemy in Flask](https://flask.palletsprojects.com/en/stable/patterns/sqlalchemy/), [Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)); `views.py` and `views/admin`, `views/frontend` appear as examples on the packages and factories pages ([Large Applications as Packages](https://flask.palletsprojects.com/en/stable/patterns/packages/), [Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)); `database.py` appears on the SQLAlchemy page; a `services/` folder appears nowhere in the fetched Flask documentation. The tutorial itself names its modules after blueprints, `auth.py` and `blog.py`, with `db.py` for connection helpers ([Tutorial: Project Layout](https://flask.palletsprojects.com/en/stable/tutorial/layout/)). The application factory is a documented pattern and the tutorial's default, but it is not required: the tutorial says "The most straightforward way to create a Flask application is to create a global `Flask` instance directly at the top of your code ... While this is simple and useful in some cases, it can cause some tricky issues as the project grows", and the Design Decisions page says the explicit application object "makes it possible to use a factory function to create the application" ([Tutorial: Application Setup](https://flask.palletsprojects.com/en/stable/tutorial/factory/), [Design Decisions in Flask](https://flask.palletsprojects.com/en/stable/design/)). The Stripe sample is the counter example in practice: a single `server.py` with a global `app`, `static_folder` and `template_folder` both pointed at the client directory via `STATIC_DIR`, no `templates/`, no `instance/`, no factory, and no blueprint ([server.py on main](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/server/python/server.py), [.env.example](https://raw.githubusercontent.com/stripe-samples/checkout-one-time-payments/main/.env.example)).

Where the eight converge:

- Not one of the eight names a folder, module or class for an operation that spans a write and a call to a third party. Phoenix comes closest with the context, which it defines as the place for "data access and data validation" that may talk to "APIs, using an HTTP client such as Req", and its own order example stops before payments. The other seven either assign business logic to the model as a category (Rails, Django, ASP.NET Core) or say nothing (Laravel, Play, Spring Boot, Flask).
- In every official example that performs a write, the HTTP handler sequences it: the Rails scaffold `create`, the Django `vote` view, the Flask `create` view, the Play Action, the Spring guide controller, the ASP.NET Core `OnPostAsync`. Only Phoenix's `complete_order/2` moves the sequence out of the handler, and Laravel's documented `store` leaves a comment where the sequence would be.
- Every Stripe sample is a single request handler that creates the Checkout Session and redirects with 303, with the API key set once at module, file or startup level and no order record written at all. The samples are written against the smallest server available for the language (Sinatra, Flask, Spark, plain PHP, a minimal API) rather than against Rails, Django, Play, Spring Boot or Laravel, and Stripe's quickstart tells the reader to "Wait to fulfill orders ... until the payment succeeds", so the write is deferred to the webhook rather than placed before the call. Laravel Cashier is the only framework owned integration, and it hides the client behind the `Billable` trait on the `User` model, so the route closure is a one liner that returns a redirecting object.
- No model, schema or entity imports the provider anywhere. In six frameworks that is because the sample has no model at all; in Phoenix because schemas are data definitions the FAQ calls private; in Laravel because `User` imports only `Billable` while `Stripe\StripeClient` is imported inside Cashier.
- The page frame has a framework given home in six of eight (Rails `layouts/application`, Phoenix `Layouts.app` and `root.html.heex`, Laravel `components/layout` or `layouts/app`, Play `main.scala.html` by seed, ASP.NET Core `Shared/_Layout` through `_ViewStart`, Flask `base.html` by tutorial). Django and Spring Boot show the mechanism (`{% extends %}`, `th:replace`) and leave the file name to the application; Spring's decorator style layout is a third party dialect.
- Small formatters are always a registration or an import, never a folder the framework reads for them: Rails includes every module under `app/helpers` into every controller, Django discovers `templatetags/`, Phoenix imports `CoreComponents` through `use MyAppWeb, :html`, Flask registers filters and context processors on the app, ASP.NET Core and Spring offer `@inject` and `Formatter` registries, Play and Laravel offer imports and framework utilities. Rails, Django and Phoenix are the three that generate the file where an application's own formatter goes.
- Every framework ships money or time formatting as a utility (`number_to_currency`, `floatformat` and `timesince`, `Number::currency` and Carbon, `#numbers.formatCurrency` and `#temporals`, `[DataType]` and `DisplayFormat`), except Jinja, which has no currency or date filter, and Phoenix, whose guides do not address formatting at all.

Where the eight split:

- Three camps on the business layer. Active Record frameworks (Rails, Django) say the model holds the logic and show the controller doing the write; the dependency injection frameworks (Spring Boot, ASP.NET Core, Play, Laravel) have a word for the layer (`@Service`, "services", `app/services`, `App\Services\...`) but never a folder or a generated file, and their own examples skip it; Phoenix alone generates the layer and routes the example through it; Flask declines to have an opinion.
- Package by layer versus package by feature. Spring Boot's only documented layout groups `Customer`, `CustomerController`, `CustomerService`, `CustomerRepository` under `customer/`; Play's REST sample packs controller, repository, handler and router under `app/v1/post`; Phoenix groups by context under `lib/my_app/<context>/`. Rails, Django (per app), Laravel, ASP.NET Core and the Play seed group by kind (`models`, `controllers`, `views`).
- Where the vendor client is configured. The Stripe samples set a static global (`Stripe.api_key`, `Stripe.apiKey`, `StripeConfiguration.ApiKey`); the Stripe quickstarts for Java, .NET, Ruby, PHP and Python have moved to a client object (`StripeClient`), registered as a DI singleton in .NET and held at module level elsewhere. Laravel is the one framework where the client is reached through the model (`$user->checkout`). Rails (`config/initializers`, credentials), Spring (`@ConfigurationProperties`, `@Bean`), ASP.NET Core (options pattern, typed clients), Play (`Module` bindings, `Configuration`) and Flask (`init_app`, `app.config`) document where configuration and injectable components go, but none of them names a payment client or a wrapper class.
- Layouts as files versus layouts as functions. Rails, Django, Laravel's `@extends`, ASP.NET Core and Flask use a template that other templates extend or that wraps the view; Phoenix 1.8 and Laravel's `<x-layout>` make the frame a component that is called with content; Play's `main.scala.html` is a compiled function taking `(content: Html)`; Thymeleaf has fragments only.
- How much is generated. Rails and Phoenix generate the most (model or context, controller, views, helper or components, layout); Laravel and Django generate a thin skeleton; ASP.NET Core generates pages and layout but no model or service; Spring Initializr generates one class; Play's seed generates a controller and two templates; Flask generates nothing.

Which conventions the framework enforces rather than shows:

- Enforced by a loader or a view engine: Rails autoloads every `app/*` subdirectory and includes every `app/helpers` module, and looks up layouts and partials by name; Django imports `models`, autodiscovers `admin`, discovers `templatetags/` and `templates/`; ASP.NET Core searches `Pages/`, `Views/{Controller}/`, `Views/Shared/`, `_ViewStart`, `_ViewImports`, `Shared/Components/`, `DisplayTemplates/`; Spring Boot reads `templates/` and the static locations and scans from the application package; Laravel resolves `resources/views` and discovers components, policies, listeners and commands by directory; Flask reads `templates/`, `static/` and `instance/` as constructor defaults; Play reads `conf/routes`, `conf/application.conf` and `public/`.
- Enforced by a generator but not by a loader: Phoenix's `lib/my_app` versus `lib/my_app_web` split, `components/layouts.ex`, `core_components.ex` and `controllers/<name>_html.ex` are written by `phx.new` and `phx.gen.*` and wired by `use MyAppWeb, :html`, while Mix compiles anything under `lib`; Laravel's `App\Models` and `App\Http\Controllers` are `make:` defaults under PSR-4; Rails' two `concerns` folders are keep files that Zeitwerk also treats as roots.
- Shown only: Play's `controllers`, `models` and `views` ("simply conventions that can be changed"), Spring's by feature packages ("a typical layout"), Django's `base.html` and `forms.py`, Flask's `models.py` and `views/`, ASP.NET Core's `Controllers/` (discovery is by class suffix) and `Models/`, Laravel's `layouts/` and every `App\Services\...` namespace in its examples, Rails' `app/services`. Across all eight, a service, action or operations layer is never generated and never read; the one official sentence that acknowledges such folders is Rails' remark that `app/presenters` "works out of the box".
