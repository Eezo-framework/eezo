# `sbt-eezo` is cross built for sbt 1 and sbt 2 from one source

**Status:** accepted

`modules/sbt-plugin` is a single source tree compiled twice, on the sbt 1 axis with Scala 2.12.21 and on the sbt 2 axis with Scala 3.8.4, and published under two artifactIds, `sbt-eezo_2.12_1.0` and `sbt-eezo_sbt2_3`. The two names are what makes the decision cheap: adding an axis creates a coordinate and dropping one removes a coordinate, and neither breaks resolution for anything that already resolves, so this is reversible in both directions rather than a promise eezo has to defend forever. The mechanism is a `crossScalaVersions` pair and a `pluginCrossBuild / sbtVersion` match applied to this project alone, and `+publishSigned`, which `ci-release` already runs, resolves each project's own `crossScalaVersions`, so the eight framework modules still publish once at 3.8.4 while the plugin publishes twice. The module carries none of eezo's build settings and none of eezo's modules: on the classpath a project that installs the plugin actually sees, it depends on sbt and the standard library, and on nothing else. Test scope is exempt from that rule, since a `Test` dependency never reaches the classpath of a project that merely installs the plugin; it is discussed under Consequences.

## Considered options

**The sbt 1 axis alone.** The whole cost of the decision is the shared subset the single source has to stay inside, and shipping for sbt 1 only removes that cost entirely. Rejected because the subset is small for this module in particular: the generator's world is `sbt.io.IO`, `java.io.File`, `sbt.Keys` and string handling, all of it common to Scala 2.12 and Scala 3, and it never touches `Classpath`, which is the sbt API the transition from 1 to 2 broke most often. Building the second axis from day one also means the second artifactId exists from the first release rather than appearing later as a coordinate users have to discover. This option remains the fallback: if the shared subset ever does bite, the sbt 2 axis can be dropped and nothing that resolved `sbt-eezo_2.12_1.0` notices.

**The sbt 2 axis alone.** Tempting because it removes the Scala 2.12 axis and with it every constraint on the source. Rejected because sbt 1.12.x is current, actively maintained, and the sbt eezo's own build runs on, so shipping for sbt 2 only would leave the users the plugin exists for with nothing to resolve. Of the three narrowing options this is the only one that is not reversible in practice, because it never publishes the artifact those users would need.

**A separate source tree per axis.** Rejected because it duplicates the generator, which is the only thing the module contains, and because the divergence it permits between the two copies is exactly the divergence eezo wants to be told about. The narrower version of the same escape hatch stays available if a genuine API break ever demands it: version specific directories, `src/main/scala-2.12` and `src/main/scala-3`, each holding an object of the same name. Nothing needs one yet.

**The plugin left out of the root's `aggregate` list, published by a named `CI_RELEASE` command.** `ci-release` runs `+publishSigned` on the root and an unaggregated project is never published, so leaving the plugin out of the list would release nothing for it unless something else named it. There is such a hatch: `sbt-ci-release` reads the `CI_RELEASE` environment variable and uses its value verbatim as the publish command, so the release workflow could name `sbtEezo/publishSigned` and keep the plugin unaggregated. Rejected because it moves the module list into a workflow file's environment, where it can drift from `build.sbt` with nothing to notice. Aggregating leaves one publish path that the build itself describes.

## Consequences

The module does not inherit `commonSettings`. `-no-indent`, `-Wvalue-discard` and `-release 25` are not a valid Scala 2.12 flag set, and the build level `scalaVersion` of 3.8.4 is not a version an sbt 1 plugin can be built with, so the module states `scalaVersion := Toolchain.PluginScalaVersion` itself and a plain `sbt compile` builds the sbt 1 axis rather than failing. Everything `commonSettings` would have supplied is therefore stated here or not stated at all, munit included, since that is where every other module picks it up. Adding `munit` as a plain `libraryDependencies +=` reads at first as one more line that widens the plugin's dependencies, the exact thing the previous paragraph rules out. It does not, because `Dependencies.munit` is scoped `% Test`: sbt never puts a `Test` scoped dependency on the classpath it hands to a project that merely installs the plugin, only on the classpath it uses to compile and run this module's own tests. The "nothing else" rule is about what a consuming build inherits, not about what this module needs to test itself, so a `Test` scoped dependency is exempt from it by construction rather than by exception. munit was already exempt before this module existed; the plugin merely needed to say so, in the same way every other module already does.

At compile scope, the classpath a consuming build actually inherits, it depends on sbt and the standard library alone, never on eezo's own modules, and this is a rule rather than an accident of what the generator happens to need. The sbt 1 axis physically cannot see eezo's Scala 3 artifacts. The sbt 2 axis could and must not, because a dependency there would weld eezo's Scala version to sbt's and put Jetty on the build classpath of every project that installs the plugin.

`-Xsource:3` on the 2.12 axis is permissive, not restrictive. It teaches Scala 2.12 to accept Scala 3 syntax and does nothing in the other direction, so it does not enforce the shared subset the single source depends on. Scala 2 constructs that 3.8.4 rejects, procedure syntax and `forSome` among them, still compile on the 2.12 axis without a warning, and constructs both axes accept with different meanings, a leading infix operand among them, diverge in silence. The guard is therefore compiling both axes, and compiling them in CI: the compile step is `+compile` rather than `compile`, so a divergence costs a red build instead of being discovered by `+publishSigned` after a release tag has already been cut. Warnings are fatal on both axes, `-Xfatal-warnings` on 2.12 and `-Werror` on 3.8.4, so a deprecation that a Scala or sbt upgrade introduces breaks the build on that axis instead of piling up unread, but value discard is checked on the Scala 3 axis only, because the 2.12 `-Ywarn-value-discard` rejects the `expr: Unit` ascription the Scala 3 check needs, and the `Setting[?]` wildcard that 3.8.4 demands compiles on 2.12 only while `-Xsource:3` stays.

The bytecode targets are sbt's floors and not eezo's, Java 8 on the sbt 1 axis and 17 on the sbt 2 axis, stated for scalac and javac on both so that no half of a published jar inherits a target from whichever JDK launched the build. They are deliberately not `Toolchain.JdkFloor` of 25. That floor is about the JVM an eezo server runs on and virtual threads are what justify it, whereas a plugin runs inside sbt at build time and touches none of that. What binds this module is the JVM sbt loads the plugin into, and somebody may well build an eezo application on JDK 25 with an sbt that starts on something older. The numbers are sbt's own published requirements, Java 8 in the 1.x manual and JDK 17 on the 2.x setup page, and aiming above either publishes a plugin that the sbt it targets cannot load. On the sbt 2 axis 17 is also the lowest `-release` Scala 3.8.4 accepts, so sbt's requirement and the compiler's floor coincide with no slack in either direction.

The accepted cost of aggregating the module is that a plain `sbt compile` also builds the plugin on Scala 2.12, which every contributor pays on every build for a module most of them are not touching. It is small, and it buys a release path that is described entirely by `build.sbt`.

The research that settled all of the above is not committed to this repository: it is `research/sbt-plugin.md` on the unmerged `research/sbt-plugin` branch, which `git show origin/research/sbt-plugin:research/sbt-plugin.md` prints, and it carries the Maven Central evidence for the two coordinate schemes and the measurements behind the generator's own decisions. An unmerged branch can be rebased away, so every conclusion this module rests on is stated above rather than deferred to it, and that branch is further reading rather than the record.
